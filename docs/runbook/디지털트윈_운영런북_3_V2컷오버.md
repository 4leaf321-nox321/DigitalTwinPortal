# 디지털 트윈 대시보드 — V2 컷오버 런북

작성 2026-07-31 · 대상: 운영 서버(오프라인) 작업자

---

## 이 문서를 쓰는 법

- **위에서부터 순서대로** 한다. 건너뛰지 않는다.
- 회색 상자의 명령을 **그대로 복사해** 실행한다.
- 각 단계 끝의 **확인**이 `[OK]` 면 다음으로, `[FAIL]` 이면 **멈추고** 그 단계의
  「막혔을 때」를 본다.
- **운영서버에는 AI 도 인터넷도 없다.** 판단이 필요한 지점은 전부 미리 적어 뒀다.
  여기 없는 상황을 만나면 **진행하지 말고** 개발 담당자에게 연락한다.
- 되돌리는 방법은 맨 아래 **R장**에 있다. 시작하기 전에 R장을 **먼저 한 번 읽는다.**

**소요 시간** 대략 40분 (백업 시간 제외). 사용자 접속이 적은 시간대에 한다.

**되돌릴 수 있는 마지막 지점은 6-2 다.** 거기까지는 손실 없이 되돌아갈 수 있고(R-1),
**7장에서 서비스를 켜는 순간부터** 사용자 저장이 시작돼 되돌리기 비용이 생긴다.

---

## 무엇을 하는 작업인가

지금까지 대시보드는 모든 과제·성과를 **`dashboard_data` 표의 한 줄에 JSON 으로 통째로**
저장해 왔다(V1). 이번에 **과제 1건 = 1행**인 정규화된 표(`dt2_*`)로 정본을 옮긴다(V2).

화면 모양은 바뀌지 않는다. 서버가 `dt2_*` 를 읽어 **V1 과 같은 형태로 다시 조립**해서
내려주기 때문이다. 사용자가 느끼는 변화는 아래 **공지 4건**뿐이다.

| | 상태 |
|---|---|
| 화면 리허설(활동로그·설정·간트·전체보기) | ✅ 2026-07-31 완료 |
| 저장 경로 V2 전환 | ✅ 10곳 중 9곳. 남은 1곳(`선행과제목록`)은 **의도적으로 V1** |
| manager 권한 입력 | ✅ 운영 실측 — manager 40명 전원 사업부 해석됨, 활성 과제 352건 전부 커버 |
| 소유자 없는 활성 과제 1건 | ✅ **조치하지 않기로 결정** (사무국·해당 사업부 manager 가 고칠 수 있다) |

> 그 필드를 바꾸면 저장이 V1 으로 물러선다. 사용자에게 알릴 필요는 없다.

## 1. 사전 공지 — 컷오버 **1일 전**

아래 4건을 사용자에게 알린다. 그대로 복사해 써도 된다.

> **[안내] 디지털 트윈 대시보드 데이터 구조 개선 — 0000년 00월 00일 00시**
>
> 화면과 사용법은 그대로입니다. 다만 아래 4가지가 달라집니다.
>
> 1. **과제 영구삭제는 관리자·사무국만** 할 수 있습니다.
>    (지금까지는 권한 검사가 없어 누구나 남의 과제를 영구삭제할 수 있었습니다)
> 2. **성과 ID 는 더 이상 바꿀 수 없습니다.** ID 가 바뀌면 그 성과를 쓰는 과제들의
>    연결이 한꺼번에 끊어지기 때문입니다. 이름·내용은 그대로 수정할 수 있습니다.
> 3. **과제 수정 권한 검사가 실제로 적용됩니다.** 지금까지는 사실상 검사가 없었습니다.
>    앞으로는 과제PL·참여인력·같은 사업부 관리자·사무국만 수정할 수 있습니다.
>    수정이 막히면 사무국에 문의해 주세요.
> 4. **'스냅샷 관리' 와 '서버에 저장' 메뉴가 없어집니다.** 저장은 항목을 고칠 때마다
>    자동으로 서버에 반영됩니다. 변경 이력은 **설정 ▸ 최근 수정 사항**에서 보실 수 있고,
>    이제 **어떤 항목이 무엇에서 무엇으로 바뀌었는지**까지 표시됩니다.

## 2. 개발 PC — 컷오버용 빌드 만들기

> ⚠️ **운영서버에서는 빌드하지 않는다.** 권한 오류로 부분 실패하면 `index.html` 이 없는
> CSS 를 가리키고, SPA 폴백이 200 을 돌려줘서 **에러 없이 화면 스타일만 조용히 사라진다.**

**2-1.** 스위치 3개를 컷오버 값으로 바꾼다.

| 파일 | 줄 | 바꿀 값 |
|---|---|---|
| `backend\.env` | `DT2_WRITE_ENABLED` | `true` |
| `frontend\src\modules\digital-twin-dashboard\services\settingsApi.js` | `DEFAULT_V2_READ` | `true` |
| 〃 | `DEFAULT_V2_WRITE` | `true` |

**2-2.** 화면을 다시 빌드한다.

```
cd frontend
npm run build
```

**2-3.** 스위치가 제대로 들어갔는지 확인한다.

```
cd ..\backend
python scripts\dt3_preflight.py --cutover
```

**확인** — `★` 가 붙은 4줄이 전부 `[OK]` 여야 한다.

```
[OK]  ★ DT2_WRITE_ENABLED 가 켜져 있다 (컷오버)
[OK]  ★ DEFAULT_V2_READ 가 true 다 (컷오버)
[OK]  ★ DEFAULT_V2_WRITE 가 true 다 (컷오버)
[OK]  ★ DB 마이그레이션이 코드와 같다
```

> 개발 PC 에서는 `FLASK_ENV`·`DATABASE_URL`·secret key 항목이 `[FAIL]` 로 나온다.
> **개발 값이니 정상이다.** 여기서는 `★` 4줄만 본다.

**2-4.** 압축 전에 개발 잔재를 지운다. (개발에서 돌린 점검 로그가 쌓여 있다)

```
rmdir /S /Q backend\scripts\out
```

**2-5.** 폴더를 통째로 압축한다. `frontend\node_modules` 는 빼도 된다(운영은 빌드하지 않는다).

> `backend\scripts` 는 **빼지 않는다** — 아래 4·5·6 장이 이 스크립트들을 쓴다.
>
> 시험 스크립트(`*_test_*.py`)도 같이 딸려가지만, **운영에서는 실행되지 않는다.**
> `FLASK_ENV=production` 이면 `create_app()` 이 거부한다 (2026-08-01 추가). 이 스크립트들은
> 시험용 과제를 만들고 지우므로 운영 데이터에 대고 돌면 안 된다 — 개발서버에서 실제로
> 사고가 났다. 운영 절차용(`dt2_import` · `dt2_verify` · `dt3_preflight` …)은 영향 없다.

> 압축에는 **`backend\.env` 와 `frontend\dist` 가 반드시 들어가야 한다.** `.env` 는 운영에서
> 되돌리지만(4-3) `DT2_WRITE_ENABLED` 한 줄을 옮겨 적을 참고용으로 필요하고, `dist` 는
> **운영에서 다시 만들 수 없다.**

## 3. 운영 — 백업 (되돌릴 수 있는 유일한 수단)

> **이 단계를 건너뛰면 되돌릴 수 없다.** R장의 모든 절차가 여기서 만든 백업에 기댄다.

**3-1.** DB 를 덤프한다. (DB 이름은 `backend\.env` 의 `DATABASE_URL` 에 적힌 이름)

```
pg_dump -h localhost -U postgres -d dxdigitaltwin -F c -f D:\backup\dt_before_cutover.dump
```

**3-2.** 지금 운영에서 쓰고 있는 것들을 복사해 둔다.

```
copy backend\.env                 D:\backup\env_before_cutover.txt
xcopy /E /I /Y backend\templates  D:\backup\templates_before_cutover
xcopy /E /I /Y backend\uploads    D:\backup\uploads_before_cutover
xcopy /E /I /Y frontend\dist      D:\backup\dist_before_cutover
```

**확인** — 네 개가 모두 만들어졌는지 눈으로 본다.

| 무엇 | 왜 필요한가 |
|---|---|
| `dt_before_cutover.dump` | R-2(저장 발생 후 되돌리기)의 유일한 수단 |
| `templates_before_cutover` · `uploads_before_cutover` | **반입 후 4-4 에서 그대로 되돌려 넣는다.** 압축본의 것으로 덮이면 운영 파일이 사라진다 |
| `dist_before_cutover` | 화면을 되돌릴 때 필요. **운영에서는 다시 빌드할 수 없다** |
| `env_before_cutover.txt` | R-1 에서 `.env` 를 통째로 되돌릴 때 쓴다 |

## 4. 운영 — 반입

> 지금까지 해 오던 방식 그대로다 — **프로젝트를 통째로 덮어쓰고, `backend\templates` 와
> `backend\uploads` 만 운영 것으로 되돌린다.** DB 이름·계정은 개발과 맞춰져 있어
> `DATABASE_URL` 은 손대지 않는다.

**4-0. ⚠️ 멈춘 직후 — dt2 를 V1 과 **깨끗이** 맞춘다** (2026-07-31 추가 · **빠뜨리지 말 것**)

> **왜 이 단계가 생겼나** — 첫 컷오버 시도에서 **완료 과제 수가 달라졌다.** 원인이 둘이었다.
>
> ① `v2_sync` 는 **백그라운드 스레드**다. 누가 저장한 직후 서비스를 내리면 **마지막 동기화가
>    안 끝난 채 끊기고**, dt2 가 V1 보다 낡은 상태로 컷오버된다.
> ② `dt2_import.py` 에는 **`DELETE` 가 한 줄도 없다** — upsert 만 한다. 그래서 V1 에서
>    **끊은 성과 연결이 dt2 에 그대로 남는다.** 첫 시도에서 유령 연결 2건이 발견됐다.
>
> **컷오버하면 `v2_sync` 가 멈추므로 그 뒤로는 저절로 고쳐지지 않는다.**
> 반대로 **한 번만 깨끗이 맞추면 다시는 안 생긴다** — 컷오버 후 연결 삭제는
> `PUT …/performances`(통째 교체)가 정확히 반영하기 때문이다.

**서비스를 멈춘 뒤**(4-1 을 먼저 해도 된다) 아래를 순서대로 한다.

```
cd backend
python scripts\dt2_import.py --commit --truncate
python scripts\dt2_verify.py
```

> ⚠️ **`--truncate-history` 는 절대 붙이지 않는다.** 이력은 재생성이 불가능하다.
> `--truncate` 만으로는 이력이 보존되고, `dt2_project_changes` 도 FK 가 없어 남는다.
> 본체(과제·성과·연결·첨부)는 V1 에서 그대로 다시 만들어진다.

> ⚠️ **`--truncate` 가 멈춰 서면 그건 고장이 아니다.** (2026-08-01 추가)
>
> `TRUNCATE ... CASCADE` 는 `dt2_projects` 를 참조하는 표를 **목록에 없어도 같이 비운다.**
> 그중 **V1 에 원본이 없는 것**은 재이관해도 되살아나지 않는다 — 지금은
> `dt2_project_kpi`(과제↔DX KPI 연결)가 그렇다. 실제로 2026-08-01 개발서버에서
> 이 경로로 연결 12건이 사라졌다.
>
> 그래서 스크립트가 실행 전에 영향 범위를 조회해 이렇게 멈춘다:
>
> ```
> ── TRUNCATE 영향 범위 ──
>   CASCADE 추가분 : 1개 — dt2_project_kpi
>   [경고] 아래는 V1 에 원본이 없어 재이관해도 복구되지 않습니다.
>       dt2_project_kpi              12건 삭제됨
>   중단합니다. 지우기 전에 백업하거나 --truncate-orphans 를 명시하세요.
> ```
>
> **할 일** — 백업을 뜬 뒤 `--truncate-orphans` 를 붙여 진행하고, 반입 후 되돌려 넣는다.
>
> ```
> pg_dump -t dt2_project_kpi dxdigitaltwin > D:\backup\dt2_project_kpi.sql
> python scripts\dt2_import.py --commit --truncate --truncate-orphans
> psql dxdigitaltwin < D:\backup\dt2_project_kpi.sql
> ```
>
> 백업을 놓쳤더라도 `dt2_project_changes` 의 `field='kpi_links'` 마지막 `after_value`
> 로 복원할 수 있다 (그 표는 FK 가 없어 CASCADE 대상이 아니다).

**확인** — `dt2_verify.py` 가 **전항 `[OK]`** 여야 한다.

> `고아 참조 3 · 중복 참조 1` 은 **V1 데이터 자체의 특성이라 그대로 남는다.**
> 2026-07-29 Phase 2 검증에서도 같은 값이었고 그때 판정은 `[OK]` 였다. 정상이다.
> **`V2 에만 있음`이 0 이 되는 것**이 이 단계의 목적이다.

`[FAIL]` 이면 **진행하지 말고** 개발 담당자에게 연락한다.

**4-1.** 서비스를 멈춘다. (운영에서 쓰는 방식대로)

> 멈춘 뒤에는 **아무도 저장하지 못하게 한다.** 4-0 이후에 저장이 하나라도 들어가면
> 그것이 다시 미동기화분이 된다.

**4-2.** 압축을 푼다. 기존 폴더를 덮어쓴다.

**4-3.** `backend\.env` 를 열어 **아래 두 줄을 확인한다.**

| 줄 | 있어야 할 값 | 비고 |
|---|---|---|
| `FLASK_ENV` | `production` | 압축본에는 `development` 로 들어 있다. **반드시 바꾼다** |
| `DT2_WRITE_ENABLED` | `true` | 이번 컷오버용. 압축본에 이미 들어 있다 |
| `SECRET_KEY` | **운영 전용 임의값** | 압축본에는 `dev-secret-key-change-in-production` 이 그대로 들어 있다 |
| `JWT_SECRET_KEY` | **운영 전용 임의값** | 압축본에는 `jwt-secret-key-change-in-production` 이 그대로 들어 있다 |

> `FLASK_ENV` 를 안 바꾸면 디버그·SQL 에코가 켜지고 **시험용 쓰기 우회 헤더까지 열린다**
> (`create_app` 이 이 값으로 설정을 고른다). 그 헤더가 열리면 유효한 토큰만 있으면 누구나
> dt2 에 직접 쓸 수 있다.
>
> ⚠️ **시크릿 두 줄은 반드시 바꾼다.** (2026-08-01 추가 — 이전 판에는 "손대지 않는다" 고
> 적혀 있었다) 압축본의 값은 **소스에 그대로 적혀 있던 플레이스홀더**다. 그 값을 아는
> 사람은 아무 사용자로든(관리자 포함) **유효한 JWT 를 스스로 만들 수 있다.**
>
> ```
> python -c "import secrets;print('SECRET_KEY=',secrets.token_urlsafe(48),sep='')"
> python -c "import secrets;print('JWT_SECRET_KEY=',secrets.token_urlsafe(48),sep='')"
> ```
>
> `JWT_SECRET_KEY` 를 바꾸면 **기존 로그인 세션이 전부 끊긴다.** 서비스를 멈춘 이
> 시점에 바꾸는 것이 그래서 맞다. 사용자에게 재로그인을 미리 알린다.
> PAT(`dtp_`)은 JWT 가 아니라 DB 해시 대조라 영향받지 않는다.
>
> `DATABASE_URL` 은 손대지 않는다 — 개발과 같은 값으로 맞춰져 있다.
> 단, 이제 값이 비어 있으면 **기동이 실패한다**(예전에는 조용히 localhost 로 붙었다).

**4-4.** 운영의 `templates` · `uploads` 를 되돌려 넣는다.

```
xcopy /E /I /Y D:\backup\templates_before_cutover backend\templates
xcopy /E /I /Y D:\backup\uploads_before_cutover   backend\uploads
```

## 5. 운영 — 데이터베이스 올리기

```
cd backend
flask db upgrade
```

**확인** — 오류 없이 끝나면 된다.

**막혔을 때**
- `Target database is not up to date` → 그대로 한 번 더 실행한다.
- `Can't locate revision` → 압축이 덜 풀렸다. 4-2 부터 다시 한다.
- 그 밖의 오류 → **진행하지 말고** R장 1번(즉시 되돌리기)으로 간다.

## 6. 운영 — 켜기 전 점검

```
python scripts\dt3_preflight.py --cutover
```

**확인** — 마지막 줄이 이래야 한다.

```
결과: [OK] NN/NN — 켜도 됩니다.
```

> ⚠️ **이 환경에서는 아래 3줄이 `[FAIL]` 로 나오는 것이 정상이다.** 이 셋 말고 다른
> `[FAIL]` 이 없으면 **그대로 진행한다.**
>
> ```
> [FAIL] SECRET_KEY 가 개발 기본값이 아니다
> [FAIL] JWT_SECRET_KEY 가 개발 기본값이 아니다
> [FAIL] 개발 기본 DSN 이 아니다
> ```
>
> · **secret key 2건** — 2026-07-31 에 **교체하지 않기로 결정**했다. 이번 작업과 무관한
>   기존 사안이고, `JWT_SECRET_KEY` 를 바꾸면 발급된 토큰이 전부 무효가 되어
>   **전원 재로그인**이 필요하다.
> · **개발 기본 DSN** — 이 프로젝트는 **개발과 운영의 DB 이름·계정을 일부러 맞춰 뒀다.**
>   그래서 이 검사는 여기서 항상 걸린다. `[정보] DATABASE_URL` 줄을 눈으로 보고
>   **DB 이름이 맞는지만** 확인하면 된다.
>
> 셋 말고 다른 `[FAIL]` 이 하나라도 있으면 **진행하지 않는다.**
> 특히 `FLASK_ENV=production` 이 `[FAIL]` 이면 **4-3 을 빠뜨린 것이다.**

**막혔을 때** — `[FAIL]` 줄을 보고 아래에서 찾는다.

| `[FAIL]` 내용 | 무엇이 잘못됐나 | 어떻게 |
|---|---|---|
| `FLASK_ENV=production` | 압축본의 `development` 가 그대로다 | **4-3 을 한다** |
| `★ DT2_WRITE_ENABLED 가 켜져 있다` | `.env` 에서 그 줄이 빠졌거나 `false` 다 | 4-3 표대로 고친다 |
| `★ DEFAULT_V2_READ/WRITE 가 true 다` | 컷오버용으로 빌드하지 않은 `dist` 가 들어왔다 | **개발 PC 에서 2장을 다시** 하고 4장부터 반복 |
| `★ DB 마이그레이션이 코드와 같다` | 5장을 빠뜨렸다 | 5장을 한다 |
| `index.html 이 가리키는 자산 …` | `dist` 가 깨졌거나 덜 풀렸다 | 4-2 를 다시 한다 |
| `dt2_* 테이블 10개가 모두 있다` | 마이그레이션이 덜 올라갔다 | 5장을 한다. 그래도면 R장 |

`[정보]` 로 찍히는 **과제·성과·연결 건수**를 종이에 적어 둔다. 8장에서 화면 숫자와 맞춰본다.

## 6-2. 운영 — 사전 조사 (켜기 전 마지막 판단 지점)

> **왜 여기인가** — 마이그레이션은 끝났지만 **서비스는 아직 안 켰다.** 이 시점의 되돌리기는
> **손실이 없다**(R-1). 결과가 나쁘면 **오늘 컷오버를 미루고** 데이터를 손볼 수 있다.
> 켜고 나면 그 선택지가 사라진다.
>
> 둘 다 **읽기 전용**이고 몇 초면 끝난다. 개발 DB 로는 알 수 없는 것들이라 여기서 처음 잰다.

**6-2-1. 참여인력 편집 권한**

```
python scripts\dt3_member_coverage.py
```

컷오버하면 **과제PL·참여인력 본인이 직접 고칠 수 있는지**가 계정 매칭에 달리게 된다.
(이메일 @앞부분 = `knoxId`, 또는 이름 정확 일치. **동명이인은 이름으로 매칭되지 않는다**)

| 마지막 줄 | 뜻 | 어떻게 |
|---|---|---|
| `[OK]` | 대부분 본인이 고칠 수 있다 | 그대로 7장으로 |
| `[확인 필요]` | 본인 편집자 없는 과제가 10% 넘는다 | **컷오버를 막지는 않는다.** 사무국·manager 가 커버하므로 못 고치는 과제는 없다. 다만 **"수정이 안 돼요" 문의가 몰릴 것**이니 사무국이 미리 알고 있어야 한다 |

출력의 **「매칭 안 되는 knoxId」** 목록을 적어 둔다. 표기만 틀린 것이면 나중에 고쳐서
그 사람들의 권한을 살릴 수 있다.

**6-2-2. 고쳐도 저장 안 되는 필드가 있는지**

```
python scripts\dt3_extra_fields.py --values
```

`extra_fields` 에 담긴 키는 **PATCH 를 받지 않는다.** 그 이름이 편집창 입력칸과 겹치면
**고쳐도 조용히 무시된다**(화면엔 성공이라 뜬다).

**「과제」 와 「성과」 표만 본다.** 연결·선행과제 표는 성격이 달라 안전하다고 출력에 적혀 있다.

| 나온 키 | 판단 |
|---|---|
| `_` 로 시작 (`_synthesizedTs` 등) | 화면 내부 표식이다. **무해** |
| `isEditing` · `_idChanged` | UI 임시값. **무해** |
| **`_` 없는 한글 필드명** (예: `비고`, `목표`) | ⚠️ **편집창에 그 입력칸이 있는지 확인한다.** 있으면 컷오버를 **미루고** 개발 담당자에게 연락 |

> 컷오버 후에도 이 문제는 드러난다 — `F12` ▸ Console 에 `[DT] 서버가 건너뛴 키` 경고가
> 찍힌다. 다만 그때는 이미 사용자가 쓰고 있다.

서비스를 시작한다. 기동 로그에서 이 줄을 확인한다.

> 실패했을 것이다. 서비스를 멈추고 4-3 부터 다시 한다.

`v2_sync`(V1→dt2 자동 동기화)는 **스스로 멈춘다.** 쓰기 스위치와 상호배타라 둘이 동시에

## R. 되돌리기 (롤백)

### R-0. 먼저 읽을 것 — 되돌리기 비용은 시간이 갈수록 커진다

| 시점 | 되돌리기 |
|---|---|
| **7장 이전** (서비스를 아직 안 켰다) | **손실 없음.** R-1 |
| **8장 중** (켰지만 사용자 저장 전) | **손실 없음.** R-1 |
| **사용자가 저장한 뒤** | **그 저장분을 잃는다.** R-2 |

**중요** — 켠 뒤에 되돌릴 때 **`.env` 만 끄고 끝내면 안 된다.** 쓰기 스위치를 끄면
`v2_sync` 가 다시 도는데, 이건 **V1 → dt2 방향**이라 컷오버 후 dt2 에 들어간 변경을
**낡은 V1 값으로 덮어쓴다.** 반드시 아래 절차를 그대로 따른다.

### R-1. 손실 없는 되돌리기

```
(1) 서비스를 멈춘다
(2) copy /Y D:\backup\env_before_cutover.txt backend\.env
(3) rmdir /S /Q frontend\dist
    xcopy /E /I /Y D:\backup\dist_before_cutover frontend\dist
(4) 서비스를 시작한다
```

> (2) 는 컷오버 전 운영 `.env` 를 통째로 되돌리는 것이다. `FLASK_ENV=production` 과
> `DT2_WRITE_ENABLED` 가 한 번에 원래대로 돌아간다. **`templates` · `uploads` 는
> 건드리지 않는다** — 4-4 에서 이미 운영 것으로 돌려놨다.

**확인** — 기동 로그에 「쓰기 **차단** (컷오버 전) — 정본=dashboard_data」가 보이고,
화면에서 과제 목록이 평소대로 뜬다.

> `flask db upgrade` 는 되돌리지 않는다. `dt2_*` 표가 남아 있어도 V1 동작에 지장이 없다.

### R-1-b. 폴더째 이전 버전으로 되돌리는 경우

버전별 폴더를 보관해 두고 **이전 배포본을 그대로 띄우는 방식**도 된다.
`flask db downgrade` 는 **하지 않는다.**

이번 배포로 올라가는 마이그레이션 3개가 **전부 더하기만** 하기 때문이다.

| 리비전 | 하는 일 |
|---|---|
| `c1e05b7d33a9` | `dt2_project_changes` 테이블 **신규 생성** |
| `d4a91f2b6c07` | `dt2_project_performance.position` **컬럼 추가**(nullable) |
| `e2c73f8a15b6` | `dt2_performances.created_by_user_id` **컬럼 추가**(nullable) |

`drop_column` · `drop_table` · `rename` · `NOT NULL 추가` 가 하나도 없다. 그래서 이전 버전
코드는 새로 생긴 것들을 **모른 채 그대로 동작한다.**

> ⚠️ 되돌린 뒤에는 **`flask db` 명령을 쓰지 않는다.** DB 의 head 는 `e2c73f8a15b6` 로 남는데
> 이전 폴더에는 그 리비전 파일이 없어서 `Can't locate revision` 오류가 난다.
> **앱 실행(`run.py`)은 아무 문제 없다** — 앱은 `alembic_version` 을 보지 않는다.
>
> ⚠️ **다음 배포 때 이 표를 그대로 믿지 말 것.** 그때의 마이그레이션이 무엇을 하는지
> 다시 봐야 한다. 지우거나 이름을 바꾸는 마이그레이션이 하나라도 있으면 이 방법은 못 쓴다.

**스키마가 호환된다고 데이터가 돌아오는 것은 아니다.** 컷오버 후 dt2 에 쌓인 변경은 V1 에
없고, 이전 버전 코드는 V1 을 정본으로 본다. 그래서 **컷오버 후 수정분은 안 보인다** —
사용자 저장이 이미 일어났다면 코드를 되돌리는 방식이어도 **R-2 가 필요하다.**

### R-2. 사용자 저장이 일어난 뒤 되돌리기

```
(1) 서비스를 멈춘다
(2) 무엇이 바뀌었는지 먼저 남긴다 — 복구 후 손으로 다시 넣어야 한다
    psql -h localhost -U postgres -d <운영DB이름> -c "\copy (SELECT project_uuid, row_version, field, before_value, after_value, actor_user_id, created_at FROM dt2_project_changes WHERE created_at >= '<컷오버시각 UTC>' ORDER BY id) TO 'D:\backup\lost_changes.csv' CSV HEADER"
(3) DB 를 컷오버 전으로 되돌린다
    pg_restore -h localhost -U postgres -d <운영DB이름> --clean --if-exists D:\backup\dt_before_cutover.dump
(4) R-1 의 (2)~(4) 를 그대로 한다
```

**확인** — 화면이 뜨고, 과제 건수가 6장에서 적어 둔 숫자와 같다.

**그다음** — `D:\backup\lost_changes.csv` 를 열어 컷오버 후 사용자가 바꾼 내용을 확인하고,
해당 사용자에게 **다시 입력해 달라고 안내**한다. 파일에는 과제 uuid·필드명·이전값·새값이
들어 있다.

## 부록 — 자주 틀리는 것

**스위치가 셋인데 있는 곳이 다르다.**

| 스위치 | 어디 | 바꾸려면 |
|---|---|---|
| `DT2_WRITE_ENABLED` | 서버 `backend\.env` | 재기동 |
| `DEFAULT_V2_READ` / `DEFAULT_V2_WRITE` | 화면 **소스** | **개발 PC 에서 `npm run build`** 다시 |
| `dtV2Read` / `dtV2Write` | 브라우저 localStorage | 주소에 `?dtV2Read=1` |

- **`.env` 는 압축에 딸려 온다.** 이 프로젝트는 DB 이름·계정을 개발과 맞춰 뒀기 때문에
  그대로 써도 되지만, **`FLASK_ENV` 만은 매번 `production` 으로 바꿔야 한다**(4-3).
  잊으면 preflight 가 잡는다.
- **`backend\templates` 와 `backend\uploads` 는 운영 것을 되돌려 넣는다**(4-4).
  압축본의 것으로 덮이면 운영 파일이 사라진다.
- **운영에서 `npm run build` 를 하지 않는다.** 실패해도 에러가 안 나고 화면만 깨진다.
- **`dt2_verify.py` · `dt2_compare_api.py` 는 컷오버 전용 도구다.** 컷오버 후에는
  V1 과 달라지는 게 정상이라 이걸로 판정하면 안 된다.
- 화면이 안 뜨는데 원인을 모르겠으면 → `F12` ▸ Console 에 **빨간 줄**이 있는지 본다.
  `[DT] V2 읽기 실패` 가 보이면 그 메시지를 그대로 적어 개발 담당자에게 전달한다.
