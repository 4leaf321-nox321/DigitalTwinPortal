# 운영서버 런북 1-2 — 보고서 이미지 파일 분리

> 대상: **운영서버에서 직접 실행** (AI 없음 · 인터넷 없음)
> 근거: [디지털트윈_대시보드_실행계획.md](./디지털트윈_대시보드_실행계획.md) Phase 1-2
> 선행: **[런북 0-0 백업](./디지털트윈_운영런북_0-0_백업.md) 완료** (특히 단계 1 `core_*.dump`)
> 소요: **약 1시간** (화면 확인 시간 포함)
> 서비스 영향: **배포 시 재시작 수 초.** 데이터 작업 중에도 사용자는 계속 쓸 수 있다

---

## 무엇을 왜 하는가

**문제** — 보고서 이미지가 과제 JSON 안에 base64 문자열로 들어 있다.

| 운영 실측 (2026-07-28) | 값 |
|---|---|
| 이미지 보유 과제 | 23건 |
| 이미지 용량 | **33.9 MB** |
| 저장 payload 중 비중 | **94.4%** |
| 실제 업무 데이터 | 3.5 MB |

과제 하나의 진행률만 바꿔도 **33.9 MB가 통째로 왕복**한다. 느린 이유의 대부분이 이것이다.

**조치** — 이미지를 파일로 분리하고 JSON 에는 `imageId` 참조만 남긴다.

```
전:  { "dataUrl": "data:image/jpeg;base64,....(수 MB)", "fileName": "...", "caption": "..." }
후:  { "imageId": 123,                                   "fileName": "...", "caption": "..." }
```

## ⚠️ 가장 중요한 원칙 — "이동"이 아니라 "복사"

**원본 base64 를 지우지 않고 파일로 복사한 뒤, 화면에서 정상 표시를 확인한 다음에야 원본을 제거한다.**

```
[단계 3] --extract    base64 → 파일 복사 + imageId 부여.  dataUrl 은 그대로 둔다
                      ↓ 이 시점에 데이터가 두 벌. 화면은 서버 이미지를 쓰고, 실패하면 dataUrl 로 폴백
[단계 4] 화면 확인      보고서 이미지가 전부 정상으로 보이는지 눈으로 확인
                      ↓
[단계 5] --strip      dataUrl 만 제거 → payload 급감.  파일과 DB 행은 그대로 남는다
```

각 단계가 독립적으로 되돌릴 수 있다. 단계 3에서 멈춰도 화면은 정상이다.

---

## 이 런북을 쓰는 법

- 명령은 **그대로 복사해서 붙여넣는다.**
- **"이 결과가 나와야 정상"** 과 다르면 **거기서 멈춘다.**
- **판단하지 않는다.** 예상과 다르면 화면을 캡처하고 담당자에게 전달한다.

# 단계 5. 원본 dataUrl 제거 — payload 감소

> **여기서 처음으로 원본이 사라진다.** 그래서 백업 파일이 필수다.
> 파일과 DB 행은 남으므로, 문제가 생기면 백업에서 JSON 만 되돌리면 된다.

```powershell
python scripts\dt_image_extract.py --strip --backup-file "$COREBK"
```

**기대 출력**

```
[OK]   백업 파일 확인: core_20260728_1830.dump / ...

── 무결성 검증 ──
  판정: [OK] 전부 정상          ← 통과해야만 진행한다

── dataUrl 제거 실행 ──
  제거 대상 : NN장
  절감 용량 : 33.9 MB

[OK]   커밋 완료 — NN장의 dataUrl 제거
       과제 payload: 3.5 MB (이미지 제거 후)
```

**판정** — `과제 payload` 가 **크게 줄어야 한다** (37.4 MB → 수 MB).

**실패 시** — 무결성 검증에서 걸리면 **아무것도 지우지 않고 중단**한다. 데이터는 그대로다.

> 스크립트는 **imageId 가 있고 파일이 실제로 존재하는** 원소의 dataUrl 만 지운다.
> 파일이 없으면 절대 지우지 않는다.

## 단계 5 이후 (dataUrl 제거됨)

이미지 파일과 DB 행이 남아 있으므로 **보통은 되돌릴 필요가 없다.**
그래도 JSON 을 원복해야 한다면, **먼저 staging 에 복원해 확인**한다.

```powershell
& "$PGBIN\psql.exe" -U postgres -h localhost -d postgres -c "DROP DATABASE IF EXISTS dxdigitaltwin_stg;"
& "$PGBIN\psql.exe" -U postgres -h localhost -d postgres -c "CREATE DATABASE dxdigitaltwin_stg;"
& "$PGBIN\pg_restore.exe" -h localhost -U postgres -d dxdigitaltwin_stg --no-owner --no-privileges "$COREBK"
```

그 뒤 담당자와 함께 진행한다. **혼자 판단해서 운영에 직접 복원하지 않는다.**

# 문제가 생겼을 때

1. **더 이상 아무 명령도 실행하지 않는다**
2. `scripts\out\` 의 최신 `dt_image_*.log` 를 확보한다
3. 화면 전체를 캡처한다
4. 담당자에게 전달한다

> 단계 3·5의 DB 변경은 **단일 트랜잭션**이다. 중간에 실패하면 전부 되돌려진다.

# 자주 나오는 상황

| 상황 | 답 |
|---|---|
| 단계 3 후에도 payload 가 그대로다 | **정상.** dataUrl 을 일부러 남겼다. 단계 5에서 줄어든다 |
| "중복 재사용" 이 많이 나온다 | **정상.** 같은 이미지가 여러 과제에 있으면 파일 하나만 만든다 |
| 이미지가 잠깐 흐릿하다 서버 것으로 바뀐다 | **정상.** 전환기에는 dataUrl 을 먼저 보여주고 서버 이미지로 교체한다 |
| 이미지 자리에 "불러오는 중…" 이 남아 있다 | 서버 요청 실패. Network 탭에서 report-images 응답 코드를 확인해 담당자에게 전달 |
| 새 이미지 업로드가 "업로드 중…" 에서 안 끝난다 | 파일이 크거나 형식이 지원되지 않는다. 20MB 이하 jpg/png 로 시도 |
| `--extract` 를 두 번 실행했다 | **안전하다.** 이미 처리된 것은 건너뛴다 |
| 신규 과제에서 이미지를 넣었더니 imageId 가 없다 | **정상.** 아직 과제 uuid 가 없어 압축본을 임시 보관한다. 저장 후 `--extract` 를 다시 돌리면 분리된다 |
