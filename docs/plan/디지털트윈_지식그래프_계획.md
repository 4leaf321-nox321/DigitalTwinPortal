# 디지털 트윈 — 지식 그래프 계획

작성 2026-08-08 · 대상 `digital_twin_dashboard` (백엔드 `dt2_*`, 프론트 V2 읽기/쓰기)

이 문서는 **왜 지금 것으로는 안 되는가**와 **무엇을 대신 만들 것인가**를 적는다.
착수 순서는 §6. 첫 삽은 §6-A(선행과제 V2)이고, 그래프 자체는 그 다음이다.

## 1. 지금 "서버에 지식 그래프 저장"이 실제로 하는 일

```
ServerKnowledgeGraphModal.jsx        이름·공개여부·사업부/연도 필터·연결유형 택1
  → DigitalTwinDashboardApp.jsx:2578 handleServerKnowledgeGraphSaveConfirm
  → importExportUtils.js:2354        generateKnowledgeGraphData
                      :2561          generatePersonnelKnowledgeGraphData
  → createGraph + saveGraphData      dx_work_process 모듈의 graphApi.js
  → dx_graphs / dx_nodes / dx_edges  ← **다른 모듈의 그래프 편집기 테이블**
```

즉 이것은 지식 그래프가 아니라 **"DX 업무 프로세스 그래프 편집기로 내보내기"** 다.

`backend/app/modules/knowledge_graph/routes.py` 는 `TODO: Implement with database` 로
빈 배열만 돌려주는 껍데기다. 프로젝트 이름은 지식그래프인데 그 모듈에 내용물이 없다.

### 성격 진단

| | 현재 |
|---|---|
| 만드는 곳 | 브라우저 메모리. 서버는 받아 적기만 한다 |
| 시점 | 저장 버튼을 누른 순간에 **얼어붙는다**. 과제명이 바뀌어도 옛 이름 그대로 |
| 범위 | 과제-성과 **또는** 과제-인력. 둘 중 하나. 동시에 못 본다 |
| 빠진 것 | KPI · 액션아이템 · 선행과제 · 부서 · 프로세스/도메인 분류 — 전부 |
| 노드 정체성 | `division_${사업부명}`, 사람은 이름 문자열. **표기가 흔들리면 다른 노드가 된다** |
| 저장 내용 | `color: {background:'#3B82F6'}`, `size: 28` — **데이터가 아니라 그림을 저장한다** |

## 2. 핵심 판단 — DT 데이터는 이미 그래프다

바꿀 게 아니라, **이미 그래프인 것을 그래프로 읽어주기만** 하면 된다.
`dt2_*` 에는 엣지 테이블이 이미 다 있다.

| 관계 | 테이블 / 컬럼 | 상태 |
|---|---|---|
| 과제 —측정→ 성과 | `dt2_project_performance` (기여도 포함) | 잘 쓰임 |
| 과제 —기여→ KPI | `dt2_project_kpi` (기여등급 포함) | 2026-08 화면 연결 |
| **과제 —선행→ 과제** | `dt2_project_dependencies` | **테이블·편집화면은 있는데 V2 쓰기가 없어 UI 를 숨겨둠** |
| 과제 —소속→ 사업부 | `dt2_projects.division_id` | 있음 |
| 과제 —사람 | `pl_knox_id`·`author_knox_id`·`members_json`·`dt2_project_editors` | **knoxId 있는 것만 노드가 된다** |
| 분류축 | `process_categories`·`project_domains`·`task_categories`·`performance_categories` | 테이블로 있음 |

없는 것은 그래프 저장소가 아니라 **두 가지**뿐이다.

1. **노드 정체성** — 사람·부서가 문자열로만 있다.
   2026-08-02 의 `owner-links` 감사 기능과 `_name_key()` 정규화가 그 증상이다.
   그것은 alias 테이블을 손으로 구현한 것이다.
2. **관계 카탈로그** — 관계 종류가 코드 여기저기 흩어져 있다.
   새 관계를 하나 늘리면 화면·API·AI 프롬프트를 각각 고쳐야 한다.

## 3. 참고 사례 — ReportArchive (WSL `~/projects/ReportArchive`)

같은 문제를 이미 푼 사내 프로젝트가 있다. **그대로 베낄 것과 베끼면 안 되는 것**이 명확하다.

### 가져올 것

| 설계 | 어디에 있나 | 왜 |
|---|---|---|
| `kind_class` 3분류 (`reference` / `record` / `system`) | `entities/models.py` | **가장 중요.** `system` = 기존 1급 테이블을 온톨로지에 *투영*한다. entities 행을 만들지 않고 ObjectRef 해석기가 원 테이블에서 라벨을 읽는다 |
| `ObjectLink` 의 문자열 ObjectRef `(type, id:str)` | 〃 | 정수 id(과제)와 문자열 키(knoxId·부서 slug)가 섞이므로 varchar 로 통일 |
| `relation_types` 카탈로그 | 〃 | 방향성·이행성·비순환·허용 축을 **테이블**로. 트래버설과 AI 가 같은 카탈로그를 읽는다 |
| `entity_aliases` | 〃 | 별칭 → canonical. 새 값이 안 생기고 사후 머지가 필요 없어진다 |
| **전환 경계 선언** | `entities/graph.py` 머리말 | "이 모듈의 공개 시그니처가 안정 계약. 지금은 Postgres 재귀 CTE, 나중에 그래프DB로 가면 **이 모듈 내부만** 교체" |
| 권한은 그래프 밖에서 | 〃 | graph.py 는 일부러 가시성을 안 다룬다. "그래프는 순수 구조, 가시성 교집합은 상위에서" |
| provenance | `EntityRelation.evidence_report_id` 등 | 누가·무엇을 근거로 이 링크를 주장했나 |

### 가져오지 않을 것

- **`entities` 테이블 자체.** DT 는 `divisions`·`departments`·`process_categories` … 가
  이미 마스터 테이블이다. 여기에 복제하면 정본이 둘이 된다.
- `EntityTemporalKind`(연도 정책 4종). DT 는 `dt2_projects.year` 가 과제에 직접 붙어 있어
  훨씬 단순하다.

## 4. 목표 구조 — "저장하지 말고 투영해라"

> **정본은 계속 `dt2_*`. 그래프는 그것을 읽는 뷰다. 노드를 따로 저장하지 않는다.**

동기화 문제가 아예 없어진다. 과제명을 바꾸면 그래프도 바뀐다.

```
백엔드 모듈 하나:  digital_twin_dashboard/graph_view.py

  ObjectRef = "project:<uuid>" | "perf:<uuid>"  | "kpi:<id>"
            | "division:<id>"  | "dept:<slug>"  | "person:<knoxId>"
            | "action:<uuid>"

  nodes(filters)                    dt2_* 를 읽어 노드를 만든다 (라벨·타입만. 색·크기 없음)
  edges(layers)                     켠 레이어들의 엣지 합집합
  neighbors(ref, depth, relations)  재귀 CTE 트래버설 — **이 시그니처가 안정 계약**
```

새로 **저장하는 것은 정본에 없는 것뿐**이다. 세 가지면 끝난다.

| 새 테이블 | 담는 것 |
|---|---|
| `dt_person_aliases` | knoxId 없는 이름을 canonical 사람으로 묶기 (owner-links 감사의 다음 단계) |
| `dt_object_links` | 사람이 손으로 걸거나 AI 가 제안한 링크. **정본 관계는 여기 안 들어온다** |
| `dt_relation_types` | 관계 카탈로그 |

지금의 "서버에 지식 그래프 저장" 모달은 **뷰 설정 저장**으로 성격을 바꾼다.
이름·공개여부·사업부/연도 필터는 그대로 쓰되 **노드·엣지 대신 쿼리를 저장**한다 —
링크로 공유되고, 열 때마다 최신이다.
지금의 스냅샷 저장은 "그 순간을 얼려 발표자료로 쓰는" 별개 용도로 남긴다.

### 이러면 열리는 것

- **로컬 그래프** — 과제 상세 모달에 "이 과제 주변 ±2 hop"
- **역방향 질의** — "이 KPI 를 올리는 과제 12개 → 그 과제들의 성과 → 사람" (지금은 불가능)
- **사람 중심 뷰** — "이 사람이 걸친 과제·성과·KPI". PL 계정 연결 작업의 목적지
- **구멍 찾기** — KPI 무연결 과제 · 성과 없는 과제 · 고립 노드 = degree 0 질의 하나
- **AI 에이전트의 툴** — 지금 AI 는 텍스트 필드만 본다.
  `neighbors(project:X, depth=2)` 툴 하나면 "비슷한 과제", "이 KPI 의 구멍" 이 된다

## 5. 미리 못 박아 두는 함정

- ~~**액션아이템에 안정적 id 가 없다.**~~ → **§6-B 에서 해결(2026-08-08).**
  `uuid` 가 정체성이고 `id` 는 여전히 순번이다. **그래프는 `uuid` 만 쓸 것.**
  `action_items_json` 은 저장할 때 **통째로 교체**되는 JSONB 라, 프론트가 uuid 를
  안 실어 보내면 날아갈 수 있었다 — 서버가 물려받아 채우는 것이 그 방어다.
- **노드에 색·크기를 저장하지 않는다.** 지금 코드가 하고 있는 것이고,
  그래서 그래프가 데이터가 아니라 그림이 돼 있다. 표현은 프론트가 정한다.
- **노드 id 를 이름으로 삼지 않는다.** 사람 이름 표기 흔들림은 이미 겪었다.
- **그래프DB 부터 도입하지 않는다.** 과제 수백~수천·엣지 수천이면 Postgres 재귀 CTE 로 충분하다.
  대신 전환 경계를 **모듈 하나로 격리**한다(§3 표 참조).
- **권한이 그래프로 우회되면 안 된다.** `is_division_public`·`permissions.py` 규칙이
  그래프 질의에도 똑같이 걸려야 한다. 그래프는 순수 구조, 가시성은 상위에서.
- **관계에 방향과 비순환 규칙을 처음부터 넣는다.** 나중에 넣으면 이미 들어간 사이클을
  사람이 손으로 풀어야 한다.

## 6. 착수 순서

### A. 선행과제(과제→과제 엣지) V2 부활 ← **지금 하는 것**

그래프의 첫 손님이자, 지금 유일하게 **끊겨 있는** 정본 엣지다.

현황
- `dt2_project_dependencies` 테이블 ○ · 이관 ○ · 읽기(`assemble.py`) ○
- **쓰기 API ✗** → 2026-07-31 컷오버에서 편집 UI 를 숨겼다
  (`EditProjectModal.jsx` 기타 탭, `dashboardWriteApi.RELATION_FIELDS_WITHOUT_API`)
- `ai_tools.UNSUPPORTED_FIELDS` 에 "수정을 시도하지 말 것" 으로 박혀 있다

할 일
1. `GET/PUT/DELETE /api/dt-v2/projects/<uuid>/dependencies` — 성과 연결 PUT 과 같은 모양
2. **비순환 가드** — A→B→A 를 400 으로 거절. 이 규칙이 그래프 트래버설의 종료를 보장한다
3. 대상 과제 **존재·자기참조·중복·조회권한** 검증
4. 변경 이력에 가상 필드 `dependencies` 로 기록 (`VIRTUAL_FIELD_LABELS`)
5. AI 쓰기는 **403** — KPI 연결과 같은 이유(사람이 선언하는 계보를 추측으로 채우면 가짜 이력이 된다)
6. 읽기 시 과제명·사업부를 **살아 있는 행에서** 채운다 (베껴 둔 사본은 이름이 바뀌면 낡는다)
7. 프론트 — `RELATION_FIELDS_WITHOUT_API` 에서 빼고, 편집창의 숨긴 블록을 되돌린다
8. 후속 과제(역방향)를 GET 응답에 함께 — 그래프의 첫 payoff

### B. 액션아이템 uuid 부여 ← **완료 (2026-08-08, 개발서버)**

노드가 되려면 필요하다. 그런데 **그래프와 무관하게 지금 이미 버그를 만들고 있었다.**

`id` 는 정체성이 아니라 **순번**이다 — `formUtils.processFormData` 가 저장할 때마다
위치 순서로 다시 매긴다(편집 저장은 `existingProjects` 로 빈 배열을 넘겨 항상 1..N).
실측: 항목 2개 이상인 과제 105개가 **전부** `1..N` 이었다. 예외 0건.

그래서 3개 중 **첫 번째**를 지우면 남은 둘의 id 가 1,2 로 당겨지고,
`logActionItemChanges` 는 "3번이 사라졌다" 로 본다 — **엉뚱한 항목이 삭제됐다고
기록된다.** 마지막 것을 지울 때만 우연히 맞았다.

한 일
1. `routes_v2._assign_action_uuids` — uuid 보장 + **물려받기**(제목 → 자리 → 새로 만들기)
2. `_derive_action_items(patch, previous)` · `_apply` 가 저장 전 값을 넘긴다
3. `scripts/dt3_backfill_action_uuids.py` — dry-run 기본, `--commit`, 멱등
4. 프론트 — 만들 때 `uuid` 부여, `logActionItemChanges` 가 uuid 로 비교
5. `id` 는 **그대로 둔다** (React key·기존 코드)

**반입 순서: 백엔드 → 백필(`--commit`) → 프론트.**
백필을 건너뛰면 uuid 는 사람이 그 과제를 저장할 때 붙고, 그때 "액션아이템목록 변경"
이력이 한 줄 남는다. 먼저 하면 안 남는다.

남긴 것 — 세부항목(`세부항목목록`)에는 아직 uuid 를 안 줬다. 그것을 가리키는 데이터가
없다(0건). 노드가 되는 것은 상위 액션아이템이다.

### C. 관계도 — 투영 API + 새 화면 ← **진행 중 (2026-08-08 착수)**

새 테이블 없이 지금 데이터만으로 만든다. **여기서 멈춰도 손해가 아니다.**

#### C-0. 렌더러 결정 — `react-force-graph-2d` (ReportArchive 방식)

이 저장소에는 `vis-network` 9.1.6 이 이미 있고 `modules/knowledge-graph` ·
`modules/dx-work-process` 가 쓴다. 그런데 **그쪽은 건드리지 않고** DT 전용으로
새 모듈을 세운다. 렌더러는 ReportArchive 와 같은 `react-force-graph-2d` 다.

| | vis-network (기존) | **react-force-graph-2d (선택)** |
|---|---|---|
| 방식 | 명령형(ref 로 인스턴스 조작) | 선언형 React + canvas 직접 페인트 |
| 유지보수 | 사실상 멈춤 | 활발 |
| 커스텀 | 옵션 안에서만 | 노드/엣지를 **직접 그린다** — 모양·배지·라벨 자유 |
| 도입 비용 | 0 | 패키지 16개 (설치 확인함) |

선택 이유는 **현대적인 방식 + 그리기 자유도**다. 관계도는 과제·성과·KPI·사람·조직이
섞이므로 타입마다 모양이 달라야 하는데, 그건 직접 페인트가 아니면 안 된다.

ReportArchive `reports/LinkGraphCanvas.jsx` 에서 가져올 것 둘:
- **lazy import** — 이 탭을 안 여는 사람이 비용을 안 내게 (지금 단일 청크 6.7MB)
- **응답을 매번 클론** — 라이브러리가 `graphData` 의 node/link 객체를 **직접 변형**한다
  (x·vx 주입, `source`/`target` 을 노드 참조로 치환). 서버 응답을 그대로 넘기면
  다음 렌더에서 모양이 깨진다

#### C-1. 백엔드 `graph_view.py` — 정본을 읽어 노드/엣지로 **투영**

저장하지 않는다. `dt2_*` 를 읽어 그때그때 만든다.

```
GET /api/dt-v2/graph?years=2026&divisions=MX,VD&layers=perf,kpi,dep,people,org,action
→ { nodes: [{ref, type, label, ...}], edges: [{source, target, relation, ...}],
    stats: {...}, truncated: bool }
```

`ObjectRef` = `"<type>:<id>"` — `project:<uuid>` · `perf:<uuid>` · `kpi:<id>` ·
`division:<name>` · `process:<사업부>|<프로세스>` · `perfcat:<대분류>` ·
`perfsub:<대분류>|<소분류>` · `kpicard:<id>` · `person:<knoxId>` · `action:<uuid>`

> ⚠️ **`kpicard` 의 화면 이름은 「성과 속성」이다.** 저장은 `kpi_dashboard_cards`
> 이고 서버 타입도 `kpicard` 지만, 사람에게 'KPI 카드' 라고 하면 같은 화면에 있는
> **DX KPI 지표**와 헷갈린다. 저장 이름을 바꾸면 다른 화면이 깨지므로
> **보이는 이름만** 바꿨다(`graphPaint.NODE_TYPES.kpicard.label`).

| 레이어 | 엣지 | 정본 |

#### C-1b. 노드를 **축과 개체**로 그린다 (2026-08-09)

처음에는 "무엇들을 담는 칸인가" 라는 **뜻**으로 갈랐다. 그 기준이면 KPI·사람은
개체가 맞다. 그런데 화면에서 중요한 것은 뜻이 아니라 **구조**였다 — 실측:

| 종류 | 개수 | 평균 연결 | 최대 |
|---|---:|---:|---:|
| **사람** | 8 | **62.5** | 150 |
| **DX KPI** | 16 | **19.4** | 35 |
| 과제 | 100 | 13.2 | 19 |
| 사업부 | 6 | 3.5 | 5 |

**가장 큰 허브 둘을 가장 작은 점으로 그리고 있었다.** 축이 하는 일은
"수가 적고 · 많은 것이 모이고 · **이름을 읽어 길을 찾는** 것" 인데 셋 다 해당했다.

- **축**(알약) 사업부 · 프로세스 · 성과 대/소분류 · 성과 속성 · **DX KPI · 사람 · 부서**
- **개체**(점) 과제 · 성과 · 액션아이템

과제는 연결 13.2 로 그 사이지만 **개체로 둔다** — 100개라 알약이 화면을 덮고,
과제명이 길어 알약이 거대해지며, 무엇보다 **이 그래프의 주인공**이다.

알약에는 **연결 수를 함께 적는다.** 알약은 이름 길이로 크기가 정해져 개체처럼
크기로 degree 를 못 보여주는데, 하필 그 신호가 제일 필요한 것이 사람·KPI 다.

원칙 셋 — 어기면 §5 의 함정으로 되돌아간다.
1. **색·크기를 서버가 정하지 않는다.** 라벨과 최소 속성만. 표현은 프론트.
2. **권한은 그래프 밖에서.** 볼 수 있는 과제만 고르고, 노드는 거기 매달린 것만.
3. **N+1 금지.** `assemble_data` 처럼 관계를 미리 묶는다.
