# 디지털 트윈 과제·성과 조회·수정

`digitaltwin` MCP 서버로 DT 대시보드의 **과제 한 건**과 그 과제에 붙는 **성과**를 읽고 고친다.

**판단은 전부 서버가 한다.** 여기서 권한이나 위험도를 자체적으로 판정하지 말 것 —
서버가 돌려준 `risk`·상태코드·`preview` 를 **그대로 따르고 그대로 사용자에게 전한다.**

**과제와 성과는 규칙이 다르다.** 안내도 따로다(`describe_fields` / `describe_performance_fields`).
과제 쪽 규칙을 성과에 적용하지 말 것 — 아래 '성과' 절이 다른 점을 따로 적어 둔다.

## 도구

**과제**

| 도구 | 하는 일 |
|---|---|
| `describe_data` | **찾기 전에.** 사업부·프로세스·진행상태·과제구분·연도·KPI 의 **실제 값 목록** |
| `describe_fields` | **고치기 전에 반드시 먼저.** 필드 키·위험도·선택지 |
| `list_projects` | 과제 찾기 (`q`·`status`·`division`·`process`·`year`·`is_key`·`progress_min/max`·`kpi_linked`·`mine_only`·`editable_only`) |
| `aggregate_projects` | **세기.** 몇 건·평균 진행률·사업부별 — 목록을 세지 말고 이걸 쓴다 |
| `get_project` | 과제 1건 상세 + `rowVersion` + `canEdit` |
| `get_project_changes` | 누가 무엇을 어떤 값에서 어떤 값으로 바꿨나 |
| `get_project_history` | 진척 지표가 어떻게 변해 왔나 |
| `find_people` | 이름 → **knoxId.** 사람을 넣기 전에 반드시 |
| `list_proposals` | 확인 대기 중인 변경 |
| `create_project` | **새 과제 만들기** (수정과 다르다 — 확인 대기가 없다) |
| `patch_project` | 수정 |

**성과** — 아래 '성과' 절을 먼저 읽을 것

| 도구 | 하는 일 |
|---|---|
| `describe_performance_fields` | **과제와 표가 다르다.** 성과를 건드리기 전에 반드시 |
| `list_performances` | 성과 찾기 (`q`·`year`·`category`) |
| `get_performance` | 성과 1건 + `rowVersion` + **`affectedProjects`** |
| `list_project_performances` | 과제에 붙은 성과. **`link_performances` 전에 반드시** |
| `create_performance` | **새 성과 만들기** (확인 대기가 없다) |
| `patch_performance` | 성과 수정 (**핵심 필드는 403** — 202 가 아니다) |
| `link_performances` | 과제-성과 연결 **통째 교체** |

**분석·관계도** — 전부 읽기 전용. 계산은 서버가 한다

| 도구 | 하는 일 |
|---|---|
| `analyze` | **분석 10종.** `kind=` gaps · risky · stalled · schedule · issues · hidden · key_projects · divisions · readiness · kpi |
| `get_graph` | 관계도 원본. ⚠️ 노드가 수백 개 — 통째로 늘어놓지 말 것 |
| `get_graph_options` | 고를 수 있는 연도·사업부·레이어 |
| `get_trend` | 시계열. `kind=` projects · performances · changes · notes |

**DX KPI 연결 · 선행 과제**

| 도구 | 하는 일 |
|---|---|
| `get_project_kpi_links` | 과제의 KPI 연결. **`set_project_kpi_links` 전에 반드시** |
| `get_kpi_matrix` | KPI × 사업부 매트릭스 원재료 (집계 전) |
| `set_project_kpi_links` | KPI 연결 **통째 교체 제안.** 항상 202 · `reason` 필수 |
| `get_project_dependencies` | 선행 과제 연결 — **읽기만** (쓰기는 화면에서) |

**공통**

| 도구 | 하는 일 |
|---|---|
| `confirm_change` | 확인받은 변경을 반영 |
| `cancel_change` | 취소 |

**삭제 전용 도구는 없다.** 지우는 방법은 셋으로 갈린다 — 섞지 말 것.

| 무엇 | 어떻게 |
|---|---|
| **과제를 휴지통으로** | `patch_project(uuid, {"_deleted": true})` → **202**. 확인을 받고 `confirm_change`. 되돌릴 수 있다 |
| **과제 영구삭제** | **못 한다.** 되돌릴 수 없고 휴지통에도 안 남아서, **관리자(admin·dt_office)가 화면에서**만 한다 |
| **성과 삭제** | **못 한다(403).** 성과를 지우면 **그 성과를 쓰던 모든 과제의 연결이 함께** 사라지고, 복구해도 연결은 돌아오지 않는다 |

⚠️ **과제 삭제는 되지만, 그래서 더 조심한다.** 사용자가 "지워줘" 라고 하면 **어느 과제인지
   먼저 확정하고**(`get_project` 로 과제명·과제코드를 보여준다) 202 의 `preview` 를 그대로
   보여준 뒤 동의를 받는다. 여러 건을 한 번에 지우지 않는다.

## 수정할 때 지키는 순서

**0. `describe_fields`** — 그 세션에서 처음 고치기 전에 한 번 부른다.
   여기 나온 `key` **만** 쓴다. 필드 이름을 지어내면 서버가 `ignored` 로 조용히 건너뛴다.

**1. 과제를 특정한다** — `list_projects(q="…", editable_only=true)`
   - 사용자가 말한 `MX-12` 같은 것은 **과제코드(`code`)이지 `uuid` 가 아니다.**
     도구는 전부 `uuid` 를 받으므로 목록에서 얻는다.
   - **두 건 이상 나오면 고르게 한다.** 제목이 비슷한 과제가 많다 — 임의로 고르면
     엉뚱한 과제를 고치게 되고, 그게 이 시스템에서 가장 흔한 사고다.
   - `editable_only=true` 를 켜면 권한 없는 과제를 붙잡고 헤매지 않는다.

**2. `get_project(uuid)`** — 세 가지를 여기서 확보한다.
   - `rowVersion` → 3단계의 `expected_version` 에 그대로 넣는다
   - `canEdit` 이 false 면 **고치려 하지 말고** 권한이 없다고 알린다
   - **현재 값** → 무엇을 무엇으로 바꾸는지 사용자에게 말할 수 있어야 한다

**3. `patch_project(uuid, patch, reason, expected_version)`**
   - `patch` 는 **바뀐 필드만.** 안 바뀐 값을 같이 보내지 않는다
   - `reason` 은 **반드시 적는다.** 변경 이력에 남아 나중에 사람이 판단 근거를 본다
   - `expected_version` 을 넣으면 남이 먼저 고쳤을 때 409 로 막힌다. 빼지 말 것

**4. 응답 갈래대로 처리한다** (아래 표)

## 응답 갈래

| 돌아온 것 | 뜻 | 할 일 |
|---|---|---|
| `applied` 있음 | 반영됐다 | 무엇이 바뀌었는지 알린다 |
| `ignored` 비어있지 않음 | **그 키는 저장되지 않았다** | **반드시 사용자에게 알린다.** 조용히 넘기지 말 것 |
| `status=needs_confirmation` (202) | **아직 안 바뀌었다.** 핵심 필드 | 아래 '확인 절차' 를 그대로 |
| `alsoPending` 있음 | 저위험인데도 **함께 대기 중이다** | `applied` 가 비어 있다. "그건 반영됐다" 고 말하면 **거짓**이다 |
| `normalized` 있음 | **서버가 값을 손댔다**(예: 성과 이름에 `[공통]` 을 붙였다) | 바뀐 값을 그대로 알린다. **그 값으로 굳는다** |
| `peoplePreview` 있음 | 사람 필드의 이름·knoxId·부서·연결여부 | 202 를 보여줄 때 **이 표까지 같이** 보여준다 |
| `affectedProjects` 있음 | 이 성과를 함께 쓰는 **다른 과제들** | 자기 과제만 보여주고 승인받지 말 것 |
| `status=conflict` (409) | 남이 먼저 고쳤다 | `get_project` 로 지금 값을 다시 보고 **사용자와 다시 정한다.** 자동으로 덮어쓰지 말 것 |
| `status=error`, 403 | 권한 없음 / AI 금지 필드 / **성과 핵심 필드** | 서버 메시지를 그대로 전한다. 403 에는 `confirm_change` 가 **없다** |

## 확인 절차 — 202 를 받았을 때

**핵심 필드(과제명·일정·진행상태·사업부·과제구분·PoC/중점…)는 즉시 반영되지 않는다.**

1. `data.preview` 의 **before → after 를 그대로 보여준다.** 요약하거나 "바꿨습니다" 로
   넘기지 말 것 — 확인의 요점은 사용자가 **값을 직접 보는 것**이다.
   `projectTitle`·`projectCode` 도 함께 보여서 **과제를 제대로 집었는지** 사용자가 판단하게 한다.

   ```
   [MX-12] 차체 강성 해석 자동화
     진행상태   정상진행 → 완료
     종료       9 → 11

   이대로 반영할까요?
   ```

2. **명시적으로 묻는다.**
3. 그렇다 → `confirm_change(proposalId)` / 아니다 → `cancel_change(proposalId, note)`

⚠️ **묻지 않고 바로 `confirm_change` 를 부르지 말 것.** 202 를 받자마자 이어 부르면
   이 단계가 통째로 없는 것과 같다. 사용자가 **먼저** "확인 없이 그냥 해" 라고 한
   경우에만 바로 진행한다.

⚠️ **거절당한 제안을 방치하지 말 것.** 사용자가 아니라고 하면 반드시 `cancel_change` 를
   부른다. 그냥 두면 대기 목록에 남아 나중에 무엇이 살아 있는 요청인지 알 수 없게 된다.

⚠️ `confirm_change` 에서 409 가 오면 그 사이 **누군가 같은 항목을 고친 것**이다.
   덮지 말고 `get_project` 로 지금 값을 다시 보여준 뒤 사용자와 다시 정한다.

### 핵심 필드와 저위험 필드를 **한 번에 섞어 보내지 않는다**

섞어 보내면 서버는 **저위험은 즉시 반영하고 핵심만 대기**시킨다. 그러면 사용자가
"아니오" 라고 해도 **이미 반영된 절반은 되돌아가지 않는다**(`cancel_change` 는 과제를
건드리지 않는다) — 한쪽만 바뀐 어긋난 상태가 남는다.

→ **핵심을 먼저 보내 확인·반영한 뒤, 저위험을 따로 보낸다.**
   이미 섞어 보내 202 를 받았다면 `applied`(이미 반영됨)와 `pendingFields`(대기 중)를
   **갈라서 그대로 알린다.** 한 덩어리로 뭉뚱그리지 말 것.

> **예외 하나 — 액션아이템 + 진행상태.** 이 둘은 갈라 보내면 오히려 막힌다(위 규칙과
> 반대다). 미착수·계획 과제의 액션아이템을 완료로 바꾸려면 액션아이템만 보내는 것이
> 400 이고, 진행상태를 먼저 바꾸려 해도 그것만으로는 모순이 안 풀린다.
> **같이 보내면** 서버가 반쪽 반영이 위험한 것을 알아채고 **둘 다 대기로 묶어** 준다
> (`applied` 가 비고 `alsoPending` 에 액션아이템목록이 들어온다). 승인하면 함께 반영된다.

## 새 과제를 만들 때 (`create_project`)

**수정과 성격이 다르다 — 확인 대기(202)가 없다. 부르면 바로 만들어진다.**
기존 값을 덮지 않아 잃는 것이 없어서 그렇게 뒀지만, **그래서 더 조심해야 한다** —
서버가 잡아 줄 단계가 없으므로 **묻는 책임이 전부 여기에 있다.**

1. **`describe_fields` 로 선택지를 확인한다.** 사업부·진행상태·프로세스·과제구분·과제영역은
   정해진 값만 들어간다. 지어내면 `ignored` 로 조용히 빠진다.
2. **만들 내용을 표로 보여주고 동의를 받는다.**

   ```
   새 과제를 이렇게 만들겠습니다.

     과제명     차체 강성 해석 자동화
     사업부     MX
     진행상태   미착수
     기간       2026년 3월 ~ 9월

   이대로 만들까요?
   ```

3. 동의를 받은 뒤 `create_project(fields, reason)`.
4. **여러 건이면 한 건씩** 만들고, 몇 건 만들었는지 알린다. 한 번에 몰아 만들지 않는다 —
   중간에 틀리면 어디까지 갔는지 알 수 없다.

- **`과제명` 은 필수**다. 없으면 400.
- `id`(과제코드)를 주면 그 값이 코드가 된다. **이미 있으면 409** — 다른 코드로 다시 부른다.
- **`과제참여인력목록`·`과제PL_knoxId` 는 여기서 바로 넣을 수 있다** — knoxId 를 붙였을 때만
  (아래 '사람을 지정할 때'). ⚠️ 생성은 확인 대기가 없어 **즉시 편집 권한이 생긴다.**
  짐작으로 고르지 말고 `find_people` 로 확정한 뒤 넣는다.
  `담당자`·`과제참여인력`(레거시)은 여기서도 못 넣는다(403).
- 만들고 나면 `uuid` 가 돌아온다. 이어서 고칠 일이 있으면 그 값을 쓴다.
- **모르는 값은 비워 두고 사용자에게 묻는다.** 그럴듯한 값을 지어내면 나중에 아무도
  그게 추측이었다는 걸 모른다.

## 사람을 지정할 때 (`과제참여인력목록` · `과제PL_knoxId`)

**이 두 필드는 knoxId 가 있어야만 통과한다. 이름만 보내면 400 이다.**
막아 둔 것이 아니라 **조건이 붙은 것**이다 — 이름은 동명이인을 가릴 수 없어서,
사용자가 확인 화면에서 "홍길동 추가" 를 보고 **어느 홍길동인지 모른 채** 승인하게 된다.

**1. `find_people(q="홍길동")`** — 넣기 전에 반드시.
   돌아오는 것: `[{"이름", "knoxId", "부서", "동명이인"}]` (가입한 활성 계정만)

**2. `동명이인: true` 가 있으면 마음대로 고르지 않는다.** 이름·부서를 보여주고
   **사용자에게 누구인지 묻는다.**

**3. 확정한 knoxId 로 보낸다.**

```
patch_project(uuid, {"과제참여인력목록": [
  {"knoxId": "hong.gd", "이름": "홍길동", "부서": "해석기술그룹"},
  ...기존 인원 전부...
]}, reason="...", expected_version=41)
```

- **통째 교체다.** `get_project` 로 현재 인원을 받아 **전부 포함해서** 보낸다.
- `과제PL_knoxId` 는 문자열 하나다(`"hong.gd"`). 표시용 이름은 `과제PL` 로 따로 있다.
- **핵심 필드라 202** 로 간다. 응답의 `peoplePreview` 에 이름·knoxId·부서·`연결` 이
  들어오니 **preview 와 함께 그 표를 그대로 보여준다.** 값만 보여주면 확인이 안 된다.

⚠️ **여기 들어간 사람은 이 과제를 고칠 수 있게 된다.** 되돌려도 그 사이엔 열려 있다.
   잘못 고르는 것이 이 필드에서 가장 나쁜 사고다.

⚠️ `find_people` 에 안 나오면 **아직 가입하지 않은 사람**일 수 있다. knoxId(사내 이메일
   `@` 앞부분)를 **사용자에게 물어** 넣어 두면 그 사람이 가입하는 순간 연결된다.
   `연결: 가입 대기(계정 없음)` 으로 표시되며, **지금은 권한이 안 생긴다**는 것도 함께 알린다.
   **knoxId 를 지어내지 말 것.**

## 성과

**성과는 과제와 규칙이 다르다.** 성과는 **여러 과제가 함께 쓰는 값**이라, 하나를 고치면
다른 과제의 숫자까지 움직인다. 그래서 확인 절차로 감싸는 대신 **아예 막아 둔 것**이 있다.

**`describe_performance_fields` 를 먼저 부른다.** 과제용 `describe_fields` 와 **표가 다르다** —
그걸 보고 성과를 고치려 들면 없는 필드를 보내게 되고 서버는 `ignored` 로 넘긴다.

| risk | 뜻 |
|---|---|
| `low` | 실적수준·조치사항·성과평가·설명·월별실적·보고현황목록 → **즉시 반영** |
| `core` | 성과항목·대분류·소분류·목표수준·현재수준 → **202.** 확인 후 반영 |
| `derived` | **`단위`·`isAchievementType`** → 아래 참고 |
| `immutable` | 서버가 정한다. **`_deleted`·`isActive` 도 여기다** — 성과는 못 지운다 |

> **성과의 202 는 과제와 하나 다르다 — `affectedProjects` 가 함께 온다.**
> 이 성과를 **함께 쓰는 다른 과제**들이다. `preview` 와 **같이** 보여줘야 한다 —
> 자기 과제만 보여주고 승인받으면 남의 과제 숫자가 조용히 틀어진다.
>
> ⚠️ 저위험(실적수준 등)을 핵심과 **같이** 보내면 그것도 함께 대기한다(`alsoPending`).
> 이때 `applied` 는 비어 있다 — "실적은 반영했습니다" 라고 말하면 거짓이다.

> **`단위` 는 성과의 값이 아니라 `소분류` 가 정하는 값이다.** 보내도 안 들어가고,
> 서버가 소분류의 단위로 채운다(화면도 이 칸을 잠근다). 403 이 아니라 **200 인데
> 값만 안 바뀐다** — 응답 `normalized` 와 `message` 가 그 사실을 알려주니 그대로 전한다.
>
> 단위를 바꾸려면 **`소분류` 를 바꾼다.** 그러면 단위가 따라온다(그 자체는 핵심이라 202).
> 사용자가 "단위를 hrs 로 바꿔줘" 라고 하면, 어느 소분류로 옮길지를 되묻는다.

> **403 은 이제 삭제·비활성(`_deleted`·`isActive`)에서만 난다.** 그때는
> `confirm_change` 를 찾지 말고 "성과는 지울 수 없습니다 — 지우면 그 성과를 쓰던 모든
> 과제의 연결이 함께 사라지고 복구해도 돌아오지 않습니다" 라고 그대로 안내한다.

### 새 성과를 만들 때 (`create_performance`)

**확인 대기가 없다. 부르면 바로 만들어진다.** 게다가 아래 세 가지는 **만든 뒤에 못 고친다**
(core, 403). 성과는 MCP 로 지울 수도 없다 — **틀리면 되돌릴 방법이 없다. 만들기 전에 묻는다.**

1. **`성과항목` 앞에 `[사업부] ` 를 붙인다.** 성과에는 사업부 컬럼이 없어서 화면이 이
   접두어로 사업부를 가른다. 예: `"[MX] 힌지 수명 예측 오차 저감"`
   - 어느 사업부인지 모르면 **연결할 과제의 사업부를 따른다**(`get_project` 의 `사업부`).
   - 모르는 접두어(`[무선]` 같은 오타)는 **400** 이다.
   - 안 붙이면 서버가 `[공통] ` 을 붙이고 `normalized` 로 알려준다 — **그 값으로 굳으므로**
     사용자에게 그대로 전한다.
2. **`대분류`·`소분류` 는 필수다.** 비면 400, **짝이 안 맞아도 400.**
   `describe_performance_fields` 의 `optionsByCategory` 에서 짝이 맞는 것을 고른다.
3. 만들 내용을 **표로 보여주고 동의를 받은 뒤** 부른다.

만들면 아직 **어느 과제에도 안 붙어 있다.** 과제에 붙이려면 이어서 `link_performances`.

### 과제에 붙일 때 (`link_performances`)

**1. `list_project_performances(uuid)` 로 지금 연결을 먼저 읽는다.** 통째 교체라,
한 건만 더하려 해도 **기존 연결을 전부 포함해서** 보내야 한다. 빠뜨리면 지워진다.

**2. 보낸다** — `items=[{"performanceUuid": "...", "contribution": "50"}, ...]`.
   순서가 곧 화면 표시 순서다.

**3. 202 가 온다.** `preview` 와 함께 **반드시 이 둘을 같이 보여준다:**
   - **`affectedProjects`** — 이 성과를 함께 쓰는 **다른 과제들.** 연결을 바꾸면 그 과제들의
     기여도 합도 흔들린다. **자기 과제만 보여주고 승인받으면 남의 과제가 조용히 틀어진다.**
   - `contributionWarnings` — 기여도 합이 100 이 아닌 성과

**4.** 동의를 받으면 `confirm_change(proposalId)`, 아니면 `cancel_change`.

⚠️ **`actualLevel`(실적수준)은 여기 넣지 않는다.** 실적은 성과 본체에 있고 화면은 거기서만
   읽는다 — 연결에 넣으면 **저장은 되는데 아무 데도 안 보인다.** 실적을 바꾸려면
   `patch_performance(uuid, {"실적수준": "12"})`. 그래도 보내면 `actualLevelWarnings` 가 온다.

## 고칠 수 없는 것

`describe_fields` 의 `risk` 가 답이다. 우회를 시도하지 말 것.

- **`derived` — `담당자` · `과제참여인력` · `담당부서`.** 보내도 들어가지 않는다.
  **다른 필드의 표시용 사본**이라 서버가 만든다:

  | 사본 | 정본 |
  |---|---|
  | `담당자`(배열) · `과제참여인력`(문자열) | **`과제참여인력목록`** 의 이름들 |
  | `담당부서`(문자열) | **`담당부서목록`** 을 이어 붙인 것 |

  → 바꾸려면 **정본을 바꾼다.** 사람을 넣는 것은 아래 '사람을 지정할 때'.
- **`소유자`는 관리자(admin·dt_office)만 지정할 수 있다** — 사람이든 AI 든 같다.
  일반 사용자가 부르면 403 이다. 소유자는 사용자 id 라 사람은 특정되지만, **그 사람에게
  이 과제의 권한이 통째로 넘어가기** 때문이다.
- **`relation` — 이미지.** `patch_project` 로 못 간다. 파일 업로드 API 가 따로 있다.
  > **`성과목록` 도 `relation` 이지만 도구가 있다** — `link_performances` 다.
  > `describe_fields` 의 `via` 가 그 API 를 가리킨다. 아래 '성과' 절 참고.
- **`unsupported` — 선행과제목록.** 쓰기 경로가 없다. 시도하지 말 것.
- **`immutable` — uuid · 과제코드 · createdAt · updatedAt · `관리자` 등.** 서버가 정한다.
  > `관리자` 는 **`과제PL` 의 사본**이다. 따로 바꿔 봐야 다음 저장 때 과제PL 값으로 덮인다.
  > 관리자를 바꾸라는 요청은 `과제PL` 을 바꾸는 것으로 안내한다.

## 값을 만들 때 주의할 것

- **배열·객체 필드는 통째로 교체된다.** `액션아이템목록` · `이슈목록` · `월간진척현황` 은
  일부만 보내면 **나머지가 전부 사라진다.** 반드시 `get_project` 로 현재 값을 받아
  거기에 더하거나 고쳐서 **전체를 보낸다.** 새 원소는 기존 원소의 모양을 그대로 흉내낸다
  (액션아이템은 `제목`·`목표일`·`완료여부`·`완료일`·`id`·`월별내용`·`세부항목목록` 같은
  한글 키를 쓴다).
  > 액션아이템의 **상위 `완료여부`·`완료일` 은 서버가 세부항목에서 파생시킨다.**
  > 세부항목이 전부 완료면 상위도 완료가 되고, 완료일은 세부항목 중 마지막 완료일이 된다.
  > 그래서 세부항목만 바꿔 보내면 되고, 상위를 직접 켜도 세부항목이 남아 있으면 도로 꺼진다.
  > ⚠️ 읽을 때와 쓸 때 **이름이 다르다.** 읽기는 `actionItems`·`issues`·`monthlyProgress`,
  > 쓰기는 `액션아이템목록`·`이슈목록`·`월간진척현황`(`describe_fields` 의 `key`).
- **선택지가 있는 필드는 그중 하나를 정확히** 쓴다 (`진행상태`·`사업부`·`프로세스`·
  `과제구분`·`과제영역`). `describe_fields` 의 `options` 가 정본이다.
- **`시작`·`종료` 는 날짜가 아니라 월 번호(1~12)** 다. 연도는 `과제년도`.
- **`진행률` 은 보내지 않는다 — 액션아이템에서 서버가 계산한다.** 액션아이템이 1건이라도
  있는 과제에 직접 보내면 **400** 이다. `액션아이템목록` 의 완료 표시를 바꾸면 진행률이
  따라온다. 액션아이템이 없는 과제에서만 직접 넣을 수 있다.
- **`진행상태` 가 액션아이템과 어긋나면 거절된다(400).** `완료` 로 두려면 액션아이템이
  **모두** 완료여야 하고, `미착수`·`계획`·`미배정` 이려면 완료된 액션아이템이 **없어야** 한다.
  > 그래서 **미착수·계획 과제의 액션아이템을 완료로 바꿀 때는 `진행상태` 를 같이 보낸다.**
  > 액션아이템만 보내면 400 이다. 같이 보내면 서버가 **둘 다 확인 대기로 묶어** 202 를
  > 준다 — 액션아이템만 먼저 반영되어 과제가 모순 상태로 잠기는 일이 없다.
  > 이때 응답의 `alsoPending` 에 함께 대기 중인 항목이 들어온다. **`applied` 가 비어
  > 있으므로 "액션아이템은 반영됐다" 고 말하면 안 된다.** 승인해야 둘 다 들어간다.
  > 반대로 `지연`·`정상진행` 과제라면 액션아이템만 보내면 된다(상태 제약이 없다).
- **모르는 값은 묻는다.** 추측으로 채우지 않는다.

## 찾기·세기 — 순서

수정에는 순서가 있듯이(위 '수정할 때 지키는 순서'), **조회에도 순서가 있다.**
이 순서를 건너뛰면 조용히 틀린 답이 나온다 — 틀렸다는 신호가 없어서 더 나쁘다.

### 1. 이름이 확실치 않으면 `describe_data` 부터

사업부·프로세스·진행상태 값을 **지어내지 않는다.** 여기 없는 값을 필터에 넣으면
오류가 아니라 **0건**이 나오고, 그러면 "그런 과제가 없다" 고 잘못 답하게 된다.

> 예: 진행상태에 `지연` 은 **없다**. 실제 값은 `describe_data` 의 `statuses` 가 말한다.

### 2. 세는 질문은 `aggregate_projects`

"몇 건" · "평균 진행률" · "사업부별로" · "가장 많은 곳" — 전부 집계 도구를 쓴다.
**목록을 받아 직접 세지 않는다.**

목록은 상한(`limit`)에 잘린다. 잘린 줄 모르고 세면 **틀렸다는 신호 없이 틀린 수**를
답하게 된다. 세는 일은 서버가 한다.

| 질문 | 이렇게 | 이러지 말 것 |
|---|---|---|
| MX 과제 몇 건? | `aggregate_projects(division='MX')` → `total` | `list_projects` 후 세기 |
| 사업부별 분포 | `aggregate_projects(group_by='division')` | 사업부마다 한 번씩 |
| 미연결 과제 | `aggregate_projects(kpi_linked=false)` | 전부 받아 걸러내기 |

### 3. `truncated` 를 확인한다

`list_projects` 응답의 `truncated` 가 `true` 면 **그 목록은 전부가 아니다.**
그 상태로 세거나 "이게 전부" 라고 말하지 않는다 — `aggregate_projects` 로 다시 묻거나,
정말 목록이 필요하면 조건을 좁힌다.

### 4. 조건은 한 번에 건다

필터는 겹쳐 쓸 수 있다. 하나만 걸고 나머지를 눈으로 고르지 않는다.

```
aggregate_projects(division='MX', process='개발', is_key=true, progress_max=30)
```

### 5. 다 찾았으면 멈춘다

필요한 것을 모았으면 도구를 더 부르지 말고 답한다. 못 찾았으면
**"자료에서 찾지 못했습니다" 라고 말한다 — 지어내지 않는다.**

## 읽기 — 무엇을 어디서 보나

**`get_project_changes` 와 `get_project_history` 는 다른 질문에 답한다.**

| | 답하는 질문 | 한 행이 뜻하는 것 |
|---|---|---|
| `changes` | **누가 무엇을 바꿨나** | 필드 하나. 같은 `rowVersion` 은 **한 번의 저장** |
| `history` | **지표가 어떻게 변했나** | 값이 바뀐 시점 하나 |

- `changes` 의 `source` 로 사람·AI·스크립트·이관을 가른다. `reason` 에 왜 고쳤는지 있다.
- `history` 의 진행률은 **그때 기록된 값**이라 안 바뀐다. 화면의 진척률은 액션아이템
  완료 비율로 **매번 다시 계산되어 소급 변경된다**(액션아이템을 추가하면 분모가 바뀌어
  과거 숫자까지 달라진다). **두 숫자가 다른 것이 정상이다.**
  → "진척률이 떨어진 게 일을 못 해서인지 일이 늘어서인지" 는 `actionTotal` 이 늘었는지 보면 된다.
- **기록이 시작된 시점이 있다.** `changes` 는 **2026-07-31**, `history` 는 **2026-07-29**
  이후만 있다. 그 전 이야기를 지어내지 말고, 자료가 없다고 말한다.

## 원칙

- **한 번에 한 과제.** 여러 과제를 훑어 고치지 않는다. 사용자가 여러 건을 원하면
  한 건씩 확인을 받으며 진행하고, 몇 건을 처리했는지 알린다.
- **사용자가 말하지 않은 필드는 건드리지 않는다.** 지나가다 눈에 띈 오류는 **말로 알리고**
  고칠지 묻는다.
- **누락·무시·실패를 숨기지 않는다.** `ignored`·403·409 는 그대로 보고한다.
- **세는 일은 서버에 맡긴다.** 목록을 눈으로 세지 않는다 (위 '찾기·세기' 절).
  숫자를 말할 때는 그 숫자가 **어느 도구의 어느 값**인지 알고 말한다.
  조용히 넘기면 사용자는 성공한 줄 안다.
- **서버 메시지를 그대로 전한다.** 다시 쓰거나 부드럽게 바꾸면 원인을 알 수 없게 된다.

## 예시

### 저위험 — 바로 반영된다

> "MX-12 이슈에 '해석 라이선스 부족' 추가해줘"

1. `describe_fields` → `이슈목록` 은 `low`
2. `list_projects(q="MX-12")` → uuid 확정
3. `get_project(uuid)` → `rowVersion=41`, `canEdit=true`, **현재 `issues` 배열 확보**
4. `patch_project(uuid, {"이슈목록": [<기존 전부>, <새 이슈>]},
   reason="담당자 요청 — 라이선스 이슈 등록", expected_version=41)`
5. 200 → "이슈 1건을 추가했습니다."

> **진행률을 같이 올려 달라고 해도 보내지 않는다.** 액션아이템이 있는 과제면 **400** 이다.
> "진행률은 액션아이템 완료에서 계산됩니다 — 어느 항목이 끝났는지 알려주시면 그걸 반영하겠습니다"
> 라고 되묻는다.

### 핵심 — 확인을 받아야 반영된다

> "MX-12 완료로 바꿔줘"

1~3. 위와 같다. `진행상태` 는 `core` 다.
4. **`get_project` 에서 액션아이템을 먼저 본다.** `완료` 는 액션아이템이 **모두** 완료여야
   통과한다 — 아니면 400 이다.
   - 이미 전부 완료 → `patch_project(uuid, {"진행상태": "완료"}, reason="…",
     expected_version=41)`
   - 아직 남았다 → **사용자에게 어느 항목이 안 끝났는지 보여주고 묻는다.** 다 끝난 게
     맞다면 `액션아이템목록`(완료 표시)과 `진행상태` 를 **같이** 보낸다.
     서버가 **둘 다 대기로 묶어** 202 를 준다(`applied` 가 비고 `alsoPending` 이 온다).
5. **202** → `preview` 를 그대로 보여주고 **"이대로 반영할까요?"**
6. 그렇다 → `confirm_change(proposalId)`.
   아니다 → `cancel_change(proposalId, note="사용자 취소")` 로 끝낸다.
7. **진행률은 손대지 않는다.** 액션아이템이 반영되면 서버가 알아서 계산한다.

### 성과 — 만들어서 과제에 붙인다

> "MX-12에 '힌지 수명 예측 오차 저감' 성과 만들어서 붙여줘"

1. `describe_performance_fields` → 접두어 규칙·`optionsByCategory` 확인
2. `get_project(uuid)` → **사업부 확인**(접두어에 쓴다)
3. 만들 내용을 표로 보여주고 동의 → `create_performance({"성과항목": "[MX] 힌지 수명
   예측 오차 저감", "대분류": "…", "소분류": "…", "단위": "%", "목표수준": 10}, reason="…")`
   → 201. `normalized` 가 있으면 **바뀐 이름을 그대로 알린다**
4. `list_project_performances(uuid)` → **기존 연결 확보**
5. `link_performances(uuid, [<기존 전부>, {"performanceUuid": <새 uuid>,
   "contribution": "50"}], reason="…")` → **202**
6. `preview` + **`affectedProjects`** + `contributionWarnings` 를 보여주고 묻는다
   → `confirm_change(proposalId)`

## 확인 대기 중인 것 보기

`list_proposals()` — **내가 승인할 수 있는 것만** 보인다. 대기 중인 것이 있으면
무엇이 걸려 있는지 알리고 어떻게 할지 묻는다.

`baseVersion` 과 `currentVersion` 이 다르면 그 사이 과제가 바뀐 것이다. 그것만으로
낡은 제안은 아니고, **제안이 건드리는 바로 그 항목**이 그 사이 바뀌었으면
`confirm_change` 가 **409** 로 막으며 상태가 `stale` 이 된다. 그때는 다시 만들어야 한다 —
`get_project` 로 지금 값을 보여주고 사용자에게 다시 물어 새로 `patch_project` 한다.
