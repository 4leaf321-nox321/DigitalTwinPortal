# 개발 디지털 트윈 성숙도 — 개발 계획

> 상태: **A~E 판 완료 (2026-08-28) — 시뮬레이션 부문이 화면까지 선다.** 남은 것: 설정 화면, F(정확도 엑셀)는 C 와 같은 틀이라 사실상 됨, 전사 판(부문×사업부 타일). 시뮬레이션 부문만 만든다 —
> 검증·설계 자동화는 미룸(3-1). 결정된 것은 11절, 남은 것은 12절.
> 관련: [로드맵 정보](../digital-twin-reference/) (「언제」를 말하는 형제 모듈),
> [전략 모듈 AUDIT_PLAN](../digital-twin-strategy/AUDIT_PLAN.md) (인텔 연결에서 가져온 규칙들)

한 줄 요지: **시험 하나에 대해 시뮬레이션이 어디까지 왔는가**를 연계 단위로 매기고,
사업부 화면 하나에서 읽게 한다. 시뮬레이션에서 시작하되, 상부 보고 구분인
**시뮬레이션 · 설계 자동화 · 검증 자동화**(그리고 디지털 스레드)를 한 엔진에
부문으로 담는다.

---

## 1. 왜 만드나

- 로드맵 정보 모듈은 시험과 DT 과제의 **연결**과 **연도**를 말한다. 「얼마나
  정확한가 · 얼마나 자동화됐나 · 어떤 불량까지 예측하나 · 어디까지 적용됐나 ·
  시험을 대체하나」는 어디에도 없다.
- CAE 부서의 일은 시뮬레이션을 다른 부서의 **검증 도구로 확산**시키는 것이고,
  CAE 가 아닌 부서로 디지털 트윈을 넓히려면 **데이터 기반 예측 모델 · 설계
  자동화 · 검증 자동화**가 같은 판에서 얘기돼야 한다. 그래서 시뮬레이션만의
  모듈이 아니라 **부문을 가진** 모듈이다.
- 세 부문은 상부에 보고되는 구분이다. 보고 구분과 화면 구분이 같아야 숫자가
  두 번 만들어지지 않는다.

## 2. 이름과 범위

- 모듈 이름: **개발 디지털 트윈 성숙도** (id `dev_dt_maturity`). 홈 카드는
  「개발 디지털 트윈 로드맵 정보」 옆.
- 부문(sector): **시뮬레이션 · 검증 자동화 · 설계 자동화 · 디지털 스레드**.
  앞 셋이 보고 구분, 디지털 스레드는 셋을 잇는 가로축(사내 시스템 연계)이라
  3차로 둔다(3-2). 검증·설계 자동화는 자료 조사 뒤 확정한다(3-1).
- **데이터 기반 예측 모델은 부문이 아니다.** 시뮬레이션(수단)의 **모델 종류**
  속성이다 — 물리 기반 / 데이터 기반 / 하이브리드. 보고 구분 셋을 그대로 두면서
  「데이터 기반이 몇 개인가」를 셀 수 있다. 부문으로 빼면 같은 시험에 걸린
  물리 모델과 데이터 모델이 다른 판에 놓여 비교가 안 된다.
- 가상 검증률 등 **DX KPI 와 무관하다.** 읽지도 쓰지도 않는다. 사업부 엑셀이
  정본인 숫자를 시험·시뮬레이션 옆에 놓아 보이게 하는 것뿐이다. 화면 도움말에
  이 관계를 한 줄로 적어 둔다 — 안 적으면 언젠가 누가 이 표를 보고 KPI 를 고친다.

## 3. 핵심 설계 — 한 엔진, 부문별 사다리 세트

부문마다 **대상**(무엇에 대해)과 **수단**(무엇으로)과 **축**(어떤 눈으로)이
다르지만, 「대상 × 수단 = 연계, 연계마다 축별 단계 + 근거 + 이력」이라는 뼈대는
같다. 그래서 부문마다 코드를 갈라 만들지 않고, **사다리 세트를 설정으로** 갈아
끼운다. 부문을 하나 더 붙이는 일이 설정 추가로 끝나야 한다.

| 부문 | 대상(subject) | 수단(agent) | 축 (초안) | 판 |
|---|---|---|---|---|
| **시뮬레이션** | 시험 항목 | 시뮬레이션 (엑셀 행 단위, 모델 종류 속성) | 정확도(값) · 자동화 · 모델링 수준 · 적용 범위 · 시험 대체 | 1차 |
| **검증 자동화** | 검증 대상 **로직**(제어·기능·SW 로직) — 가설 | 자동 검증 환경(테스트벤치·SIL/HIL·스크립트) — 가설 | 미정 — 자료 조사 뒤 (3-1) | 2차 |
| **설계 자동화** | 설계 업무 — 가설 | 자동화 도구/생성 모델 — 가설 | 미정 — 자료 조사 뒤 (3-1) | 2차 |
| **디지털 스레드** | **사내 시스템 연계 구간** (A 시스템 ↔ B 시스템) | — (연계 없이 대상만) | 연결 방식(문서→수동 전달→파일 교환→API 링크→자동 동기→폐루프) · 연계 범위(어느 데이터까지) · 운영 안정성 | 3차 |

⚠️ 축 문구는 **시뮬레이션 부문만 합의됐다**(4절). 디지털 스레드는 대상이
정해졌고 축은 초안이다. 검증·설계 자동화는 **대상·수단까지 가설**이다(3-1).

### 3-1. 검증 자동화 · 설계 자동화 — 자료 조사 뒤 확정

두 부문은 지금 정의하지 않는다. 사업부가 실제로 무엇을 「검증 자동화」
「설계 자동화」라 부르는지 자료를 봐야 대상과 수단이 정해진다. 지금 아는 것:

- **검증 자동화는 시험 절차의 자동화가 아니다.** 「로직 검증의 자동화」에
  가깝다 — 제어·기능·SW 로직이 요구대로 도는지를 사람 대신 환경이 돌려 보는 것.
  그래서 대상은 시험 항목이 아니라 **검증 대상 로직**일 가능성이 크고, 수단은
  자동 검증 환경(테스트벤치·SIL/HIL·스크립트)일 것이다. 가설이다.
- **시뮬레이션 부문의 「자동화」 축과 겹치지 않는다.** 그 축은 **해석
  파이프라인의 자동화**(전처리→실행→후처리)이고, 검증 자동화 부문은 검증
  로직 자체의 자동화다. 대상이 다르므로 같은 시험에 둘 다 걸려도 서로 다른
  것을 잰다. 문구에 이 구분을 적어 둔다 — 「자동화」라는 말이 두 곳에 있어서
  안 적으면 반드시 헷갈린다.
- 설계 자동화는 대상(설계 업무)의 목록이 어디서 오는지부터 미정이다. 로드맵의
  「설계 자동화」 구분 줄이 출발점이 될 수 있다.

엔진 설계(축 종류 둘 · 수단 없는 연계 · 부문별 사다리 설정)는 이 둘이 어떤
모양으로 오든 담을 수 있게 한다. 담을 수 없는 모양이 나오면 그때 엔진을 고친다
— 지금 가설로 엔진을 좁히지 않는다.

### 3-2. 디지털 스레드 — 대상은 사내 시스템 연계 구간

제품군이나 시험이 아니라 **시스템과 시스템 사이**가 대상이다. 예:
PLM ↔ SPDM · SPDM ↔ 해석 서버 · 시험 관리 시스템 ↔ SPDM · 설계 CAD ↔ 해석.
구간마다 「지금 어떻게 이어져 있나」를 사다리로 매긴다:

    문서로 끊김 → 사람이 옮김 → 파일 교환 → API 링크 → 자동 동기 → 폐루프(결과가 되돌아감)

- 구간 목록은 ⚙설정(사업부별). 시스템 이름은 포탈이 모르는 값이라 사람이 적는다.
- **연계이 아니라 대상 하나에 직접 매긴다.** 엔진이 「수단 없는 연계」을 허용해야
  한다 — 설계에 처음부터 넣어 두되 화면은 3차에.
- 한 구간이 여러 사업부에 걸치면(전사 PLM 등) 사업부마다 따로 매긴다 —
  같은 시스템이라도 MX 와 VD 의 연계 상태는 다르다(인텔의 사업부 줄과 같은 이유).
- SPDM 연계율·구축률 KPI · spdm-status 모듈과의 관계는 시뮬레이션의 가상
  검증률과 같다 — **무관.** 읽지도 쓰지도 않는다.

## 4. 시뮬레이션 부문의 사다리 (합의됨)

| 축 | 종류 | 단계 | 같이 적는 근거 |
|---|---|---|---|
| **정확도** | **값** (%) → 칸은 문턱으로 환산 | 미평가(값 없음) → 경향 일치 → 원인 분석 → 현상 재현 (한 줄 막대의 세 영역, 줄줄이 쌓임) | 비교 시험 건수, 오차, 첨부 |
| **자동화** | 칸 | 수동 → 전처리 자동 → 실행 자동(템플릿) → 후처리·보고까지 → 설계 변경→결과 파이프라인 | 1회 소요 시간(Hr) |
| **모델링 수준** | **표**(바탕 토글 + 불량 유형 × 시험·시장) | 바탕: 형상 재현 · 거동 재현 / 시뮬레이션의 불량 유형마다 「신뢰성 시험 불량 재현」「시장 불량 재현」을 켠다. 판의 서열: 없음 → 형상 → 거동 → 일부 시험 재현 → 전 유형 시험 재현 → 시장까지 | 재현 가능한 현상 태그 목록 |
| **적용 범위** | 칸 | 이슈 대응 → 대표(Basic) 모델 → 신규 개발 전 모델 → 파생·지역 변형까지 (기준: 개발 과제 흐름) | 대상 제품군 (비율은 화면이 셈) |
| **시험 대체** | 묶음 | 시험 병행(참고) = 아무것도 안 켬 · 원인 분석 · 사전 검증 · 신뢰성 인증 게이트 · 완전 대체 (겹쳐 켬, 오른쪽일수록 앞선 것) | 줄어든 시험 횟수/년 |

### 정확도 규칙

- **시뮬레이션 하나당 값 하나.** 사업부 엑셀이 그 단위로 낸다. 칸은 값에서
  나오고, 칸을 바꾸려면 값을 바꿔야 한다 — 값과 칸이 따로 놀면 정확도가 둘이 된다.
- 문턱은 ⚙설정, **사업부별**. 엑셀의 경계와 맞춰야 하므로 숫자를 코드에 박지
  않는다. 경계 방향(≥/>)은 남은 결정(12절).
- **항목 정확도 = 연결된 시뮬레이션 값의 집계.** 규칙은 시험 항목마다
  `single | mean`. 시뮬레이션이 하나면 자동 단일, 둘 이상이면 기본 평균, 사무국이
  항목별로 바꿀 수 있다 — 엑셀에서 「어떤 항목은 평균」이라 정한 것과 같은 자리.
- 평균은 **값 있는 것만**으로 낸다. 없는 것은 0 이 아니라 「N개 중 M개 미입력」.

### 축의 두 종류

엔진은 축을 `rung`(칸을 고른다)과 `value`(값을 적고 문턱으로 칸이 정해진다)
둘로 안다. 정확도가 value 이고 나머지는 rung 이다. 뒤 부문에서 오판율·연계율
같은 숫자 축이 나올 수 있어 — 가설이지만 — 축 종류는 처음부터 둘로 둔다.

## 5. 데이터

```
sector          부문 (시뮬레이션 · 검증 자동화 · 설계 자동화 · 디지털 스레드)
subject         대상 — 사업부 · 부문 · 이름 · 세부 · 적용 제품군 · [로드맵 항목 id, 참고]
agent           수단 — 사업부 · 부문 · 이름 · 종류 · 모델 종류 · [대시보드 과제 uuid, 참고]
pair            subject × agent  (디지털 스레드는 agent 없음)
assessment      pair × axis 한 줄 — rung · value · note(근거) · evidence(JSON) · assessed_at/by
change          이력 — pair · axis · before · after · note · actor · at
settings        부문별 사다리 세트 · 사업부별 문턱 · 사업부별 현상 태그 사전 · 재평가 기간(12개월)
```

- **연계이 일급이다.** 평가·이력·URL 이 전부 연계에 붙는다. 로드맵 정보의 JSON 배열
  방식은 쓰지 않는다 — 연결을 고칠 때마다 배열이 통째로 갈리고 평가가 사라진다.
- **축마다 한 줄.** 여섯 컬럼이 아니다. 셋만 매긴 상태가 자연스럽고, 축마다
  평가일이 따로 남고, 축을 더 붙여도 표가 안 바뀐다.
- 로드맵 항목 · 대시보드 과제로 가는 링크는 **FK 가 아니다.** 저쪽이 바뀌어도
  여기가 안 깨지고, 있으면 「로드맵에서 보기」「과제 열기」 문이 열린다.
- `evidence` 는 축마다 모양이 다른 근거 칸이다(4절 표의 오른쪽 열).
- 파생값(적용 범위 비율, 항목 정확도, 분포, 재평가 필요)은 **저장하지 않는다.** 매번
  센다. 전략 모듈의 「관측값은 저장하지 않는다」와 같은 이유 — 저장하면 원본이
  바뀐 뒤에도 재평가 필요한 값이 남는다.

## 6. 처음 채우기 — 한 번의 가져오기, 동기화 아님

```
① 로드맵에서 뽑기      시험 항목 · 세부 · 제품군 · 연결 과제  → 우리 틀(엑셀)로 내려받기
② 사람이 손보기        과제 단위로 묶인 것을 시뮬레이션 단위로 쪼개고, 이름을 엑셀과 맞춤
③ 미리보기 → 가져오기  못 맞춘 줄 · 겹친 이름 · 사업부 없는 줄을 먼저 세고, 0 이면 넣기
```

- ②는 사람만 할 수 있고 **한 번만** 한다. 그 뒤 이 모듈이 정본이고 로드맵과
  자동으로 맞추지 않는다 — 맞추려 들면 두 모듈이 서로를 알게 된다.
- 대신 **어긋남을 세는 읽기 전용 칸** 하나: 「로드맵에는 있는데 여기 없는 시험 N /
  여기만 있는 시험 M」. 고치라고 강제하지 않는다.
- 가져오기 틀은 **정확도 엑셀 가져오기와 같은 틀**이다 — 시험 · 시뮬레이션 ·
  정확도 세 열. 처음엔 정확도를 비워 올리고, 나중에 값만 채워 같은 틀로 올린다.
  가져오기 코드가 하나로 끝난다. 사업부 엑셀의 형식은 알 필요가 없다.
- 미리보기 → 실행 순서는 인텔 씨뿌리기(check → seed)와 같다. 운영 자료가 어떤
  모양인지 개발 DB 로는 알 수 없으니 세는 단계가 먼저다.

## 7. 화면 — 줌 세 단, 모드 세 개

### 7-1. 줌 세 단: 전사 → 사업부 → 연계

```
전사 판      부문 × 사업부 타일.  타일 = 대상 수 · 축별 분포 막대 · 미평가 · 재평가 필요
   ↓ 타일을 누르면
사업부 판    부문 하나 · 사업부 하나.  모드 셋(7-2)
   ↓ 칸을 누르면
연계 상세      사다리 6개 + 이력 + 근거.  모달 + ?pair=<id>
```

- 전사 판이 **상부 보고 화면**이다. 보고 구분(부문)이 행, 사업부가 열이다.
  타일 안의 분포 막대는 recharts `BarChart`(stacked) — 포탈이 이미 27곳에서 쓴다.
- 사업부는 왼쪽 위 **토글**로 고른다(드롭다운 아님 — 지금 어디를 보는지와 다른
  사업부가 무엇인지가 같이 보여야 한다). 「전체」도 있다(2026-08-28 요청): 모든
  사업부의 시험을 **사업부 딱지를 달아** 한 판에 놓고, 관리 창·목록도 사업부별로
  묶어 보이며, 새 항목은 사업부를 고른다. 셈(문턱·재평가 필요)은 사업부별로 그대로다.
  정돈·가져오기처럼 사업부 하나가 필요한 일은 전체에서는 사업부를 먼저 고른다.
- 연계 상세는 새 페이지가 아니라 **모달 + URL 파라미터**다. 공유·북마크·다른 모듈
  링크가 되고, 어느 판 위에서든 뜬다.

### 7-2. 사업부 판의 모드 셋 — 훑기 · 읽기 · 진전

시험 약 40개 × 시뮬레이션은 표로 **된다.** 접힌 40행이다. 다만 「한눈에」와
「조금 더 자세히」는 다른 그림이 필요하다. 모드로 가른다.

**① 훑기 — 히트맵**

```
              정확도  자동화  모델링  범위   대체
낙하 시험       ▪      ▪      ▪      ▫     ▪
유통환경 검사   ▪      ▪      ▪      ▪     ▪
온도 사이클     ▫      ▫      ▫      ▫     ▫     ← 회색 = 미평가
… (40행이 한 화면)
```

색 = 단계, 회색 = 미평가, 테두리 = 재평가 필요. 한 행 높이가 절반이라 40행이 스크롤
없이 들어간다. 대면 칩이 뜨고, 누르면 연계 상세. 색이 튀는 곳(빈 곳·재평가 필요한 곳)에
눈이 간다 — 이 모드의 일은 **다음 채울 곳 찾기**다. CSS grid 로 그린다(d3 불필요).

**② 읽기 — 표 (접힘/펼침)**

```
낙하 시험         정확도 84%  ●●●○  ●●○○  휨·깨짐 +2  기본   스크리닝   미평가 1  ▸
  └ 구조 해석       88%       ●●●○  ●●○○  휨·깨짐     기본   스크리닝
  └ CFD             60%       ●○○○  ●○○○  —           이슈1  참고               미평가 1
유통환경 검사     정확도 91%  ●●●●  ●●●○  공진·피로    전체   인증제외             ▸
```

- 기본은 **접힌 상태**. 시험 행은 항목 집계(정확도 평균, 축별 최고 칸, 미평가 수).
  ▸ 를 눌러야 시뮬레이션이 펼쳐진다 — 평균이 가리는 것(「84%인데 하나는 60%」)을
  펼침이 드러낸다.
- 머리 행·첫 열 **고정**(sticky). 대시보드 `AllProjectsView` 방식.
- 확대·축소는 **쓰지 않는다.** 줌 아웃은 글자가 안 읽히고 줌 인은 스크롤이 두
  방향이 된다. 표가 커지지 않게 하는 것(접힘·필터)이 답이다.

**③ 진전 — 타임라인**

```
2026   1월  2월  3월  4월  5월  6월  7월  8월
낙하 × 구조해석     정확도 ●─────────●(88)         대체 ○───●
유통환경 × 진동     모델링 ●──●
```

이력에서 「올해 어느 칸이 언제 올라갔나」를 그린다. 보고 때 「올해 무엇이
나아졌나」가 이 그림이다. recharts `ScatterChart` 또는 CSS 로 충분 — 점의 수가
수십이다.

### 7-3. 필터가 곧 뷰어

미평가만 · 재평가 필요만 · 축 고르기 · 제품군 · 모델 종류(물리/데이터/하이브리드).
필터가 40줄을 6줄로 줄인다. 이 화면에서 사람이 하는 일은 「전부 보기」가
아니라 「채울 것 찾기」와 「자랑할 것 찾기」다. 필터 상태는 URL 에 남긴다.

### 7-4. 그래프 원칙

- 축은 **순서형**이다. 평균을 내지 않는다 — 「정확도 평균 2.7단계」는 아무것도
  말하지 않고, 「3단계 이상 40% · 미평가 25%」는 다음 할 일을 말한다. 분포는
  **stacked bar**, 비교는 **소형 다중(small multiples)**.
- **레이더 차트는 안 쓴다.** 포탈에 5곳 있지만 순서형 여섯 축을 면적으로 그리면
  축 순서에 따라 모양이 바뀌고 면적이 뜻 없는 인상을 만든다.
- 합산 종합 점수를 만들지 않는다. 정확도와 대체 수준은 다른 척도다.
- 라이브러리: **recharts**(있음) + CSS grid 히트맵. 새 설치 없음. 행이 수백을
  넘는 사업부가 생기면 그때 `@tanstack/react-virtual` — 표 구조는 안 바뀐다.

### 7-5. 목록 화면과 다른 모듈의 문

- 토글은 둘: **성숙도**(7-1~7-3) · **목록**(좌 = 시험(셀 합침) × 시뮬레이션 표, 우 = 고른
  연계의 사다리 — 모달이 아니라 옆에 심는다. 둘이 화면을 다 쓰고 표만 스크롤). 시험 항목 관리 ·
  시뮬레이션 관리 · 가져오기는 **헤더 단추 셋**이 여는 창에서(로드맵 정보 헤더와 같은
  문법) — 어느 탭에 있든 열린다. 본문은 잇는 일에 집중한다.
- 대시보드 과제 모달에 「대체하는 시험」 섹션 하나(기존 섹션과 같은 틀). 줄마다
  시험 · 정확도 · 대체 칸, 누르면 이 모듈이 `?pair=` 로 새 탭에 열린다. 대시보드는
  읽기만 — 평가 입구가 둘이면 규칙이 갈린다.

## 8. 권한 · 근거 · 재평가 필요

- 평가: 로그인한 **USER 이상**, **자기 사업부의 연계만**. 사무국·관리자는 전 사업부.
  다른 사업부 연계은 단추가 사라지는 게 아니라 **이유가 적힌 채 꺼진다**
  (「VD 사업부 인력만 평가합니다」).
- **근거 필수** — 올릴 때도 내릴 때도. 내릴 때 사유가 없으면 이력이 「왜
  떨어졌는지」를 못 말한다.
- 재평가 필요 **12개월**(⚙설정). 마지막 평가가 그보다 오래면 히트맵 테두리, 표 딱지,
  전사 판 셈에 다 나타난다. 정확도는 모델이 바뀌면 다시 재야 하는 값이라 날짜
  없는 평가는 금방 거짓이 된다.
- 연결을 끊으면 평가·이력이 같이 지워진다. 확인 문구에 「평가 N건이 같이
  사라집니다」를 넣는다.

H 가 엔진의 시험대다. 부문 하나를 붙이는 데 코드가 갈리면 3절의 설계가 틀린 것이다.

## 9-1. 눌러 보는 시험 — `npm run test:ui`

`npm test`(node --test)는 번들러 없이 소스를 읽어 JSX 를 못 읽고, 서버 렌더(SSR 검사)는
useEffect 도 클릭도 안 돈다. 그래서 **저장 흐름**은 jsdom + react-dom/client 위에서 실제로
누른다(`frontend/test/ui/`). 2026-08-28 「근거를 적어도 저장이 안 된다」 점검에서 시작 —
저장 흐름 넷(칸→근거→저장 · Enter · 정확도 기록 추가 · 항목 상세 · 담당 부서)은 전부 정상이었고,
진짜 문제는 **거절 이유가 패널 맨 위에만 떠서 아래 축을 고칠 때 화면 밖**이었던 것.
지금은 저장 단추 옆에서 말한다. ⚠️ jsdom 은 React 보다 먼저 세워야 한다(setup-dom.mjs 가
첫 import) — 아니면 input 이벤트가 죽어 가짜 결함이 보인다.

## 10. 하지 않는 것

- **KPI 를 읽거나 쓰는 것.** 가상 검증률·SPDM 연계율은 사업부 엑셀과 KPI 관리가 정본.
- **로드맵 정보 모듈을 고치는 것.** 참고 링크만 두고 저쪽은 그대로 간다.
- **자동으로 단계를 매기는 것.** 과제 데이터에는 정확도·자동화를 말해 줄 자료가 없다.
- **확대·축소 뷰어.** 표가 커지지 않게 하는 것이 답이다(7-2).
- **합산 점수 · 레이더 차트.** 순서형 축을 뭉개는 두 가지 방법.
- **로드맵과의 동기화.** 한 번 가져오고 어긋남만 센다.
