> 상태: **4차 — 주요 사항 확정. 착수 가능** · 2026-08-14
> 확정 사항은 11절 표에 정리했습니다.
> 4차 반영: 합성 데이터 규격 · **MCP를 통한 AI 검증 경로** · 프롬프트 시드+오버라이드 ·

## 1. 무엇을 만드는가

조직 단위로 사람이 모여 진행하던 전략 수립을, **시스템이 진행 순서를 잡고 근거를
붙여주는 모듈**로 옮깁니다.

핵심은 "AI가 전략을 써준다"가 아니라 **"흩어진 근거를 전략 논리에 꿰어주고, 사람이
놓치는 선택지를 제시하는 것"** 입니다. 포탈에는 과제·성과·KPI·기술수준·로드맵이 쌓여
있는데, 전략 문서를 쓸 때는 아무도 그걸 열어보지 않습니다. 그 단절을 없앱니다.

## 2. 방법론 조사 결과와 권고안

실무에 정해진 절차가 없으니 처음부터 설계한다는 전제로, 최근 프레임워크들을
조사했습니다.

### 조사에서 확인한 것

| 출처 | 요지 | 이 모듈에 주는 시사점 |
|---|---|---|
| **AX-5R** (Systems, 2026) | AI 도입이 전환으로 이어지지 못하는 이유는 도구만 주고 **업무 재설계·책임·리스크·성과측정**을 안 하기 때문. 실패 유형을 readiness·redesign·role·risk·return 다섯 설계 기능에 대응 | 단계를 나열하는 것만으로는 부족. **각 단계에 품질 게이트가 필요** |
| **디지털 트윈 성숙도 모델** (다수 연구) | 5단계 성숙도 × 다차원 지표(데이터·모델·통합·분석·응용 등)로 **현재 위치와 목표를 먼저 정량화** | 전략의 출발점은 이슈가 아니라 **현재 상태 진단**. 포탈 데이터가 이걸 채울 수 있음 |
| **Reactore 4D** (Discover·Design·Deploy·Deepen) | 파일럿 → 확산의 단계적 로드맵 | 전략 산출물이 **로드맵 형태**로 끝나야 실행으로 이어짐 |
| **가치 오케스트레이션** 관점 | 2026년 산업 담론은 개별 자산이 아니라 **전사 관점의 시뮬레이션·의사결정** | 전략 단위가 개별 과제가 아니라 **포트폴리오** |

### 권고 — 5단계 척추 + 5개 횡단 게이트

조사 결과를 종합해 다음을 제안합니다. **말씀하신 4단계를 버리는 게 아니라,
앞에 진단을 붙이고 뒤에 검증 축을 얹은 것**입니다.

```
① 현재 상태 진단   ② 이슈 정의   ③ 전략 요소 분석   ④ 솔루션·포트폴리오   ⑤ 로드맵·기획서
      │                │                │                    │                    │
      └────────────────┴────────────────┴────────────────────┴────────────────────┘
                    횡단 게이트 (AX-5R): 준비도 · 재설계 · 역할 · 리스크 · 성과
```

**왜 ① 진단을 앞에 두는가.** 이슈부터 시작하면 "느낌상 문제"가 이슈가 됩니다. 성숙도
진단을 먼저 하면 이슈가 **격차(gap)** 로 정의되어 근거를 갖습니다. 그리고 이 진단은
포탈 데이터로 상당 부분 자동으로 채울 수 있습니다 — 이 모듈의 가장 큰 차별점입니다.

**왜 게이트를 횡단으로 두는가.** AX-5R의 다섯 기능은 순서가 아니라 **매 단계에서
물어야 할 질문**입니다. 예를 들어 ④에서 솔루션을 하나 도출하면 그때마다:

| 게이트 | 묻는 것 |
|---|---|
| 준비도 (readiness) | 데이터·인력·인프라가 되는가 |
| 재설계 (redesign) | 기존 업무 흐름을 어떻게 바꾸는가 |
| 역할 (role) | 누가 책임지는가 |
| 리스크 (risk) | 실패하면 무엇이 깨지는가 |
| 성과 (return) | 무엇으로 측정하는가 |

다섯 개가 다 답해지지 않은 항목은 **미완성으로 표시**됩니다. "그럴듯한 전략"과
"실행 가능한 전략"을 가르는 지점이 여기입니다.

> **[결정 필요]** 이 5+5 구조를 채택할지, 원래 4단계로 갈지. 진단 단계를 빼면 구현은
> 가벼워지지만 근거의 출발점이 사라집니다.

## 3. 방법론 — 데이터로 정의하고 교차검증한다

### 데이터로 정의

방법론을 코드에 박으면 추가할 때마다 개발이 필요합니다. **정의를 데이터로 두고
화면이 해석**합니다.

```jsonc
{
  "key": "swot",
  "name": "SWOT 분석",
  "stage": "analysis",
  "frames": [
    { "key": "S", "label": "강점", "hint": "내부 · 긍정" },
    { "key": "W", "label": "약점", "hint": "내부 · 부정" },
    { "key": "O", "label": "기회", "hint": "외부 · 긍정" },
    { "key": "T", "label": "위협", "hint": "외부 · 부정" }
  ],
  "evidenceHints": {
    "S": ["tech_level.high", "dashboard.completed"],
    "W": ["tech_level.low", "kpi.missed"],
    "O": ["reference.roadmap_upcoming"],
    "T": ["kpi.declining"]
  }
}
```

새 방법론 추가가 **데이터 입력**이 됩니다.

### 교차검증 — 같은 입력에 여러 방법론

리뷰에서 말씀하신 부분입니다. 하나의 이슈 집합에 **둘 이상의 방법론을 동시에
돌리고 결과를 비교**합니다.

```
        이슈 집합
        ├─ SWOT   으로 분석 → 요소 A, B, C
        ├─ 3C     으로 분석 → 요소 A, B, D
        └─ VRIO   으로 분석 → 요소 A, E

  합류점 : A     (세 방법론이 모두 지목 → 신뢰도 높음)
  분기점 : C, D, E  (한 방법론만 지목 → 검토 필요)
```

**분기점이 오히려 중요한 신호입니다.** 한 렌즈로만 보이는 것은 그 렌즈의 편향일 수도,
남들이 놓친 통찰일 수도 있습니다. 화면에서 이를 구분해 보여줍니다.

AI는 여기서 "왜 이 방법론에서만 나왔는지"를 설명하는 역할을 합니다.

### 1차 방법론 (제안)

| 단계 | 방법론 | 고른 이유 |
|---|---|---|
| ① 진단 | **DT 성숙도 5단계** (데이터·모델·통합·분석·응용) | 조사에서 가장 널리 쓰이는 축. 포탈 데이터로 채워짐 |
| ② 이슈 | **격차 분석**, **5 Whys**, **이슈 트리** | 진단 결과를 이슈로 전환 |
| ③ 분석 | **SWOT**, **3C**, **VRIO** | 서로 다른 렌즈 — 교차검증에 적합 |
| ④ 솔루션 | **TOWS**, **Three Horizons** | TOWS는 SWOT을 입력으로 받고, 3H는 단기/중기/장기로 가름 |
| ⑤ 로드맵 | **Pyramid 구조**, **역량 로드맵** | 문서 골격 + 실행 순서 |

> **[결정 필요]** VRIO·Three Horizons는 다소 무겁습니다. 1차는 각 단계 2개씩으로
> 줄이고, 교차검증 구조만 갖춰두는 것도 방법입니다.

## 4. 데이터 원천 — 우선순위와 접근 문제

### 우선순위 (리뷰 반영)

| 등급 | 모듈 | 백엔드 | 제공 근거 |
|---|---|---|---|
| **1차** | 디지털 트윈 과제 대시보드 | `digital_twin_dashboard` | 과제·성과·기여도·부서 분포 |
| **1차** | DX KPI 관리 | `dx_kpi_management` | KPI 목표 대비 실적, 미달 지점 |
| **보조** | 개발 디지털 트윈 로드맵 정보 | `digital_twin_reference` | 로드맵·계획된 방향 |
| **보조** | 제조 디지털 트윈 과제 관리 | `digital_twin_task_management` | 제조 시뮬레이션 현황 |
| 이후 | 메가 과제 기획 / 기술수준 | `digital_twin_tech_level` | 기술 수준 진단 |
| 이후 | 협업 게시판·회의 | `collaboration_board`, `meeting_management` | 현장 의견·결정사항 |

1차 둘만으로 진단과 이슈 정의가 성립합니다. 보조 둘은 **솔루션 실행 가능성 판단**에
씁니다.

### ⚠ 운영 데이터는 반출하지 않는다 — 이 계획의 최대 제약

**전제: 운영 데이터는 개발 환경으로 내보내지 않습니다.** 스냅샷 반입도, 운영 API
직접 호출도 없습니다. 의미 있는 데이터는 운영서버 안에만 있습니다.

이 제약이 뜻하는 바는 분명합니다. **전략 모듈은 데이터가 있는 곳에서 돌아야 하고,
개발은 실제 데이터를 못 본 채로 진행해야 합니다.**

#### 근거 계층 — 두 가지 모드만 둔다

```
전략 모듈
    │
    ▼
EvidenceSource  (인터페이스)
    ├─ LocalDbSource     로컬 DB 조회        — 운영서버. 진짜 데이터
    └─ FixtureSource     합성 데이터 조회     — 개발. 구조만 같은 가짜 데이터
```

```
STRATEGY_EVIDENCE_SOURCE=local | fixture     # 기본값 fixture
```

전략 모듈 코드는 어느 쪽인지 모릅니다. 운영에 배포되면 `local`, 개발에서는
`fixture`입니다. **데이터가 오가지 않습니다.**

#### 합성 데이터 규격 (확정)

운영 데이터를 보지 않고 만듭니다. 필요한 건 스키마(이미 `models.py`에 있음)와
분포 특성뿐입니다.

```
과제 수   2025년 150~170건
          2026년 150~170건
```

나머지(사업부 수, KPI 달성률 분포 등)는 기존 모델의 제약과 상식적인 범위로 채우고,
어긋나면 그때 조정합니다. 값은 가짜지만 **화면·집계·방법론 로직을 검증하기엔
충분**합니다.

#### AI 검증 경로 — MCP를 쓴다

사내 LLM은 **운영에서만** 접근됩니다. 하지만 **MCP는 개발·운영 양쪽에서 외부 AI를
붙일 수 있습니다.** 이미 `mcp_server/`가 도구 18종을 노출하고 있고, 사용자 JWT를
그대로 백엔드로 넘기는 구조라 권한도 그대로 지켜집니다.

그래서 AI 경로를 **둘로 나눕니다.**

| 경로 | 어디서 | 쓰임 |
|---|---|---|
| **① 사내 LLM** (백엔드 → `LLM_BASE_URL`) | 운영만 | 화면 안에서 버튼 누르면 도는 AI |
| **② MCP + 외부 AI** (Claude Code 등) | **개발·운영 둘 다** | 개발 중 검증, 운영에서 심층 분석 |

핵심은 **두 경로가 같은 것을 조작**하게 만드는 것입니다. AI가 무엇을 하든 결과는
`strategy_suggestion` 한 곳에 쌓이고, 사람이 채택/거부합니다.

```
① 사내 LLM ─┐
             ├─→  strategy_suggestion  ─→  사람이 확정
② 외부 AI  ─┘        (제안 큐)
   (MCP)
```

그러면 전략 모듈은 **전략용 MCP 도구**를 함께 제공해야 합니다.

```
strategy.get_plan(year)              전략 조회
strategy.list_evidence(target)       근거 조회
strategy.propose_issues(...)         이슈 제안 → 제안 큐로
strategy.propose_elements(...)       요소 제안
strategy.propose_solutions(...)      솔루션 제안
```

**쓰기 도구는 전부 "제안"입니다.** 외부 AI가 직접 확정하지 못합니다. 대시보드 모듈이
`actor_mode='ai'`로 위험 필드를 제안 큐에 보내는 것과 같은 방식입니다.

이 설계의 이점:

- 개발에서 **AI 동작 방식(도구 호출·제안 흐름)을 전부 검증**할 수 있습니다
- 운영에서는 같은 도구를 실제 데이터에 대고 씁니다
- 사내 LLM이 막혀 있어도 MCP로 대체 가능 — **단일 실패점이 없습니다**

다만 합성 데이터로는 **AI가 말이 되는 소리를 하는지**까지는 알 수 없습니다.
그건 여전히 운영에서 봐야 합니다.

#### 프롬프트 — 개발에서 만들고 운영에서 고친다

말씀하신 대로 둘 다 필요합니다. **시드 + 오버라이드** 구조로 갑니다.

```
git 저장소            운영 DB
seed_prompts.py  ──▶  strategy_prompt
(개발에서 작성)        (운영에서 편집)
                      · 편집하면 override=true
                      · "기본값으로 복원" 가능
                      · 버전 이력 보관
```

- **개발에서 초안을 만들어 커밋**합니다. 배포하면 시드로 들어갑니다.
- **운영에서 고치면 그 값이 우선**합니다. 원본은 남아 있어 언제든 되돌립니다.
- 다음 배포 때 시드가 바뀌어도 **운영에서 고친 것을 덮어쓰지 않습니다.** 대신
  "기본값이 바뀌었습니다" 표시를 띄워 사람이 판단하게 합니다.

방법론 정의도 같은 방식입니다.

왜 운영 편집이 꼭 필요한가:

| | 코드에만 둘 때 | 오버라이드가 있을 때 |
|---|---|---|
| 문구 한 줄 수정 | 커밋 → 태그 → 릴리스 → 배포 | **운영 화면에서 수정** |
| 반복 주기 | 수십 분 | 수 초 |

운영 데이터를 못 보는 개발자가 프롬프트를 완성할 수는 없습니다. **초안까지가 개발의
몫이고, 실제 데이터에 맞추는 것은 운영에서** 이루어져야 합니다.

버전을 남기므로 되돌릴 수 있고, 어떤 프롬프트로 만든 산출물인지도 추적됩니다.

#### 품질을 눈으로 보는 방법

AI 제안마다 **채택/거부와 사유**를 기록합니다.

```
strategy_ai_feedback
  id, suggestion_id, action(accept|reject|edit), reason, user_id, created_at
```

이건 운영 안에만 쌓이고, 화면에서 집계로 봅니다 — "이슈 추천 채택률 62%",
"방법론 추천 채택률 35%". **원자료를 꺼내지 않아도 어느 기능이 쓸 만한지** 보입니다.
낮은 항목의 프롬프트를 운영에서 고치면 됩니다.

#### LLM 접근

운영서버는 사내 LLM(`LLM_BASE_URL`)에 붙습니다. **개발 환경에서도 LLM 자체는
붙을 수 있어야** 합성 데이터로라도 호출 경로를 검증할 수 있습니다. 안 되면 AI 기능은
운영에서만 시험 가능합니다.

> **[결정 필요]** 개발 환경에서 사내 LLM에 접근 가능한지. 안 되면 Phase 4의 검증을
> 전부 운영에서 해야 하므로 배포 주기가 짧아야 합니다.

## 5. AI의 역할 — 연결에서 추천까지

리뷰 반영으로 **추천**을 정식 기능에 넣습니다. **확정은 언제나 사람**입니다.

### 하는 일

| 구분 | 기능 |
|---|---|
| **연결** | 근거 자동 매칭 · 단계 간 연결 제안 · 일관성 검사 |
| **추천** | **이슈 후보 도출** (진단 격차에서) · **방법론 추천** (이슈 성격에 맞는 렌즈) · **솔루션 후보 제시** · **우선순위 제안** (영향도×실행가능성) |
| **비평** | 누락 지적 · 교차검증 분기점 해설 · 게이트 미충족 항목 표시 |
| **초안** | 근거 기반 문장 생성 |

**방법론 추천**이 특히 유용할 것으로 봅니다. 사용자가 방법론을 몰라도, 이슈 성격을
보고 "이건 VRIO보다 3C가 맞습니다 — 외부 경쟁 관점이 필요한 이슈라서" 라고 제안할
수 있습니다.

### 하지 않는 일

- **결정하지 않습니다.** 모든 산출물은 사람이 확정해야 확정됩니다.
- **근거 없이 쓰지 않습니다.** 생성 문장에 출처를 답니다. 없으면 "근거 없음"으로
  눈에 띄게 표시하고, 확정 시 그 개수를 경고합니다.

백엔드가 이미 같은 태도를 갖고 있습니다 — 대시보드 AI 쓰기가 `actor_mode='ai'` 로
위험 필드를 제안 큐에 보내는 것과 같은 방향입니다.

### 재사용할 자산

**LLM 인프라를 새로 만들 필요가 없습니다.**

| 자산 | 위치 |
|---|---|
| LLM 호출 래퍼 (`chat`, tool call 파싱) | `backend/app/modules/digital_twin_dashboard/ai/llm.py` |
| 에이전트 루프 | `.../ai/agent.py` |
| 포탈 데이터 조회 도구 | `.../ai/agent_tools.py` |
| 페이지별 AI 컨텍스트 패턴 | `backend/app/modules/ai_context/` |
| MCP 도구 18종 | `mcp_server/server.py` |

전략용 도구 세트만 정의하면 됩니다.

> **[결정 필요]** AI 실행 시점. `LLM_TIMEOUT=120` 이고 응답이 수십 초 걸릴 수 있어
> **요청 시에만 + 비동기**를 제안합니다.

## 6. 설문 — 단계가 아니라 두 번째 근거 원천

리뷰 질문에 대한 답입니다. **설문은 특정 단계에 속하지 않습니다.** 게이트처럼
**모든 단계를 가로지릅니다.**

근거는 두 곳에서 옵니다.

```
포탈 데이터   시스템이 아는 것   — 과제 수, KPI 달성률, 로드맵
설문         사람만 아는 것     — 체감, 판단, 우선순위, 제약
```

둘 다 같은 `strategy_evidence` 테이블로 들어갑니다. 화면의 근거 패널에도 나란히
놓입니다. **시스템이 모르는 것을 사람에게 묻는 장치**라고 보면 정확합니다.

### 단계별로 무엇을 묻는가

| 단계 | 설문이 채우는 것 | 예시 문항 |
|---|---|---|
| ① 진단 | **체감 성숙도.** 시스템은 과제 수를 알지만 그게 잘 돌아가는지는 모름 | "우리 부서의 시뮬레이션 데이터 신뢰도는?" (1~5) |
| ② 이슈 | **현장이 느끼는 문제.** 데이터에 안 잡히는 병목 | "가장 큰 걸림돌 3개를 순서대로" |
| ③ 분석 | **인식 검증.** AI가 뽑은 강점/약점에 실제로 동의하는지 | "이 항목이 우리 강점이라는 데 동의?" |
| ④ 솔루션 | **실행 가능성·우선순위.** 영향도×난이도는 사람이 매겨야 함 | "이 솔루션의 실행 난이도는?" |
| ⑤ 기획서 | **검토 의견** | 자유서술 |

가장 무겁게 쓰이는 곳은 **① 진단과 ④ 우선순위**입니다. 진단은 시스템 데이터만으로는
반쪽이고, 우선순위는 애초에 판단의 영역입니다.

### 구현

포탈에 설문 기능이 **전혀 없습니다.** 이 모듈의 최대 신규 구현입니다.

- 유형: 객관식 · 척도(1~5) · 순위 · 자유서술
- 대상: 부서 / 역할 / 지정 인원
- **집계값과 원자료를 둘 다** 보관합니다. AI 요약은 원자료를 근거로 달아야 검증됩니다.
- 단계별 **문항 템플릿**을 두어 매번 설문을 새로 설계하지 않게 합니다.

### 제약 아래에서의 이점

설문은 **운영에서 생성되는 데이터**입니다. 반출 제약과 무관하게 운영 안에서
쌓이고 쓰입니다. 오히려 이 제약 때문에 설문의 값어치가 커집니다 — 개발이 못 보는
맥락을 운영 사용자가 직접 채워 넣는 통로이기 때문입니다.

### 익명 처리 (확정)

**응답자명은 숨기고 소속만 표시합니다. 단 관리자는 응답자를 확인할 수 있습니다.**

```
일반 열람   "생산기술팀 · 3점"
관리자      "생산기술팀 · 홍길동 · 3점"
```

⚠ **여기서 반드시 지켜야 할 것이 있습니다.** 이 구조는 진짜 익명이 아닙니다.
설문 화면에 **"관리자는 응답자를 확인할 수 있습니다"를 명시**해야 합니다.

익명이라고 안내하고 실제로는 추적 가능하면, 나중에 그 사실이 알려졌을 때 설문
자체의 신뢰가 무너집니다. 한 번 무너지면 이후 어떤 설문도 솔직한 답을 못 받습니다.
전략 수립에 쓸 데이터라면 이건 치명적입니다.

정직하게 안내하면 오히려 응답 품질이 예측 가능해집니다 — 사람들이 "이건 기록에
남는다"를 알고 답하니까요. 민감한 주제는 설문 대신 다른 방법을 쓰면 됩니다.

- 관리자 열람은 **감사 로그에 남깁니다** (누가 언제 어느 설문의 응답자를 봤는지)
- 자유서술은 특히 신원이 드러나기 쉬우므로, AI 요약 시 개인 특정 표현을 걸러냅니다

## 7. 데이터 모델 (초안)

```
strategy_plan            연도별 전략 1건
  id, year, title, status(draft|review|confirmed), owner_id

strategy_assessment      ① 진단
  id, plan_id, dimension, current_level, target_level,
  basis(auto|survey|manual), evidence_ids

strategy_issue           ② 이슈
  id, plan_id, title, description, priority,
  source_type(gap|survey|portal_data|ai|manual), source_ref

strategy_element         ③ 요소 분석
  id, plan_id, methodology_key, frame_key, content,
  issue_id, confidence,
  agreement_score        ← 교차검증: 몇 개 방법론이 지목했나

strategy_solution        ④ 솔루션
  id, plan_id, title, description, element_ids,
  horizon(h1|h2|h3), feasibility, expected_effect

strategy_gate            횡단 게이트 (AX-5R)
  id, target_type, target_id,
  gate(readiness|redesign|role|risk|return), answer, status

strategy_document        ⑤ 기획서
  id, plan_id, outline(JSON), body

strategy_evidence        모든 단계 공용 — 포탈 데이터와 설문이 함께 들어옴
  id, plan_id, target_type, target_id,
  kind(portal|survey), source_module, source_ref,
  source_mode(local|fixture),
  snapshot(JSON), captured_at

survey / survey_question / survey_response
  전략 단계에 연결. stage, target_type, target_id 로 어디에 쓰일지 지정

strategy_prompt          AI 프롬프트 — 운영에서 편집
  id, key, version, body, active, updated_by, updated_at

strategy_methodology     방법론 정의 — 운영에서 편집
  id, key, definition(JSON), active, updated_by, updated_at

strategy_suggestion      AI 제안 큐 — 사내 LLM·외부 AI(MCP) 공용
  id, plan_id, stage, target_type, target_id,
  origin(inapp_llm|mcp), content(JSON), rationale,
  evidence_ids, status(pending|accepted|rejected|edited)

strategy_ai_feedback     AI 제안 채택/거부 이력
  id, suggestion_id, action(accept|reject|edit), reason, user_id, created_at

strategy_prompt          AI 프롬프트 — 시드 + 운영 오버라이드
  id, key, version, body, is_override, seed_hash, active, updated_by

strategy_methodology     방법론 정의 — 시드 + 운영 오버라이드
  id, key, definition(JSON), is_override, seed_hash, active, updated_by
```

`strategy_suggestion`이 두 AI 경로의 합류점입니다. `origin`으로 어느 경로에서 왔는지
남기고, **어느 쪽이든 `pending` 으로 들어와 사람이 확정**합니다.

`seed_hash`는 배포된 기본값의 해시입니다. 다음 배포에서 기본값이 바뀌었는데 운영에서
이미 고쳐 놓았다면, 덮어쓰지 않고 **"기본값이 바뀌었습니다"만 표시**합니다.

`strategy_evidence.snapshot`이 핵심입니다. **근거로 삼은 시점의 값을 복사**해 둡니다.
원본이 나중에 바뀌어도 "그때 이 숫자를 보고 이렇게 판단했다"가 남아야 검증됩니다.
`source_mode`가 `fixture`인 근거는 **합성 데이터 기반**이므로 화면에서 확실히
구분해야 합니다 — 개발에서 만든 전략이 운영 산출물로 오인되면 안 됩니다.

위한 것이므로 AI 단계와 함께 들어갑니다.

### 접근 권한 (확정)

**사무국/관리자 전용**입니다. 포탈에 이미 쓰이는 방식을 그대로 씁니다.

```javascript
// MainPage.jsx 모듈 카드
allowedRoles: ['admin', 'dt_office']
```

- 홈 화면에서 **해당 역할이 아니면 카드 자체가 보이지 않습니다**
- 백엔드 API도 같은 기준으로 막습니다. 화면만 가리면 URL 직접 접근으로 뚫립니다
- **설문 응답자는 예외**입니다. 설문은 전사 대상이므로, 설문 응답 화면만 별도
  경로로 열어야 합니다 — 전략 산출물은 못 보고 자기가 받은 설문만 봅니다

> 나중에 열람 범위를 넓힐 때는 **확정된 전략만 전사 공개**하고 작업 중인 초안은
> 계속 비공개로 두는 방식이 자연스럽습니다. 지금 구조로 그대로 확장됩니다.

## 9. 구현 순서

각 단계는 **그 자체로 쓸 수 있는 상태**로 끝냅니다.

데이터 반출이 없으므로 **의미 있는 검증은 전부 운영에서** 일어납니다. 각 Phase는
운영에 배포해 확인할 수 있는 단위로 끊습니다.

### Phase 1 — 뼈대 + ① 진단
- 백엔드 모듈 `backend/app/modules/digital_twin_strategy/`
- `strategy_plan`, `strategy_assessment`, `strategy_evidence` 모델
- **EvidenceSource 계층** + `FixtureSource` (개발용 합성 데이터 생성기)
- 성숙도 진단 화면, 수동 입력
- 연도별 전략 생성/복제
- **합성 데이터 경고 띠**

### Phase 2 — 근거 연결
- 대시보드·KPI 커넥터 (`LocalDbSource`)
- 근거 패널, snapshot 저장
- 진단 자동 채움
- **여기서 처음 운영 배포해 실제 데이터로 확인**해야 합니다. 합성 데이터로는
  커넥터가 진짜 스키마와 맞는지 알 수 없습니다

### Phase 3 — 설문
- 설문 모델·배포·수집·집계, 단계별 문항 템플릿
- 진단·이슈 단계에 결과 연결
- **AI보다 먼저 둡니다.** 반출 제약 때문에 개발이 못 보는 맥락을 운영 사용자가
  채워 넣는 통로이고, AI가 쓸 근거를 미리 쌓아둡니다

### Phase 4 — ② 이슈 + ③ 분석 + 방법론 엔진
- 방법론 정의를 **DB에 두고 관리자 편집 화면** 제공
- SWOT·3C 등록, 격차 → 이슈 전환
- **교차검증 비교 화면**

### Phase 5 — AI 추천·연결
- **제안 큐**(`strategy_suggestion`) 먼저. 두 AI 경로의 합류점
- **전략용 MCP 도구** — 개발에서 외부 AI로 검증 가능한 유일한 경로
- 사내 LLM 경로 (기존 `llm.py` 재사용) — 운영에서만 동작
- 이슈 후보 · 방법론 추천 · 근거 매칭 · 분기점 해설
- **프롬프트 시드 + 운영 편집 화면 + 버전 관리**
- **채택/거부 피드백 기록과 집계 화면**
- 비동기 실행

> MCP 도구는 개발에서도 검증되므로 **Phase 3·4와 병행 착수 가능**합니다. 사내 LLM
> 경로만 운영 배포 후 확인하면 됩니다.

### Phase 6 — ④ 솔루션 + 게이트
- TOWS·Three Horizons
- AX-5R 게이트 UI 및 미충족 경고

### Phase 7 — ⑤ 로드맵·기획서
- 문서 구조 설계, 내보내기

**순서가 바뀐 이유.** 1차 계획은 AI(4) → 설문(5)이었는데 뒤집었습니다. 데이터를
반출할 수 없으니 AI 품질을 개발에서 가늠할 방법이 없고, 설문이 먼저 돌아 근거가
쌓여 있어야 운영에서 AI를 제대로 시험할 수 있습니다.

## 10. 위험

**형식만 남는 것.** 칸 채우기가 목적이 되면 아무도 안 씁니다.
→ 각 단계에서 채웠을 때의 **즉각적 이득**이 보여야 합니다. 진단을 채우면 이슈 후보가
자동으로 뜨고, 이슈에 근거를 붙이면 분석 요소가 추천되는 식.

**AI 초안이 그럴듯해서 검토가 형해화.**
→ 근거 없는 문장 시각 구분 + 확정 시 경고. 교차검증 분기점은 특히 사람이 봐야 합니다.

**합성 데이터로 만든 산출물이 진짜로 오인되는 것.**
→ `fixture` 모드는 화면 상단에 상시 경고 띠. 근거마다 `source_mode` 기록.
개발 환경 전략은 애초에 별도 DB이므로 섞이지 않지만, 화면에서도 분명해야 합니다.

**커넥터가 실제 스키마와 안 맞는 것.**
→ 합성 데이터로는 못 잡습니다. Phase 2에서 **반드시 운영 배포 후 확인**해야 합니다.
이게 이 계획에서 가장 늦게 발견될 수 있는 결함입니다.

**AI 품질을 개발에서 알 수 없는 것.**
→ 프롬프트를 DB에 두어 운영에서 즉시 고칩니다. 채택/거부 집계로 어느 기능이 쓸
만한지 판단합니다. 배포 없이 반복할 수 있어야 이 구조가 성립합니다.

**설문 피로.**
→ 단계별 최소 문항, 같은 대상 연속 배포 방지.

**LLM 응답 시간.** `LLM_TIMEOUT=120`. 긴 작업은 비동기로.

## 11. 확정 사항과 남은 결정

### 확정

| 항목 | 결정 |
|---|---|
| 진행 구조 | 5단계 척추 + AX-5R 횡단 게이트 |
| 운영 데이터 | **반출·반입 없음.** `local` / `fixture` 두 모드 |
| 합성 데이터 | 과제 2025년·2026년 각 150~170건 |
| AI 검증 경로 | 사내 LLM은 운영만. **MCP + 외부 AI로 개발에서도 검증** |
| 프롬프트 | 개발에서 시드 작성, **운영에서 오버라이드 편집** |
| 방법론 | 각 단계 3개 유지 |
| 설문 익명성 | 응답자명 숨김 · 소속 표시 · **관리자는 확인 가능(고지 필수)** |
| 접근 권한 | **사무국/관리자 전용** (`admin`, `dt_office`) |

### 남은 결정

1. **Phase 2 운영 배포 시점.** 커넥터가 실제 스키마와 맞는지는 운영에서만 확인됩니다.
   늦어질수록 위험이 커집니다 (9·10절)
2. **설문 응답자용 별도 경로** — 전사 대상 설문인데 모듈은 관리자 전용이므로,
   응답 화면을 어떻게 열지 정해야 합니다 (8절)
3. **관리자 열람 감사 로그**를 어디까지 남길지 (6절)
4. 합성 데이터의 나머지 항목(사업부 수, KPI 분포)은 일단 상식적 범위로 채우고
   어긋나면 조정 — 이대로 진행해도 되는지
