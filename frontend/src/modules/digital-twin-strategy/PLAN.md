## 1. 무엇을 만드는가

조직 단위로 사람이 모여 진행하던 전략 수립을, **시스템이 진행 순서를 잡고 근거를
붙여주는 모듈**로 옮깁니다.

핵심은 "AI가 전략을 써준다"가 아니라 **"흩어진 근거를 전략 논리에 꿰어주고, 사람이
놓치는 선택지를 제시하는 것"** 입니다. 포탈에는 과제·성과·KPI·기술수준·로드맵이 쌓여
있는데, 전략 문서를 쓸 때는 아무도 그걸 열어보지 않습니다. 그 단절을 없앱니다.

### 핵심 난제 — 이 모듈의 중심 개념

Rumelt 가 말하는 **crux** 를 옮긴 말입니다. 원래는 등반 용어로, 한 루트에서 가장
어려운 한 구간을 뜻합니다. 거기만 넘으면 나머지는 따라오고, 못 넘으면 다른 구간을
아무리 잘 올라도 소용이 없습니다.

> **화면에는 "핵심 난제"로 씁니다.** "크럭스"는 설명 없이는 통하지 않는 말이라
> 화면에 두면 안 됩니다. 코드 안의 식별자(`crux`, `strategy_crux`)는 그대로
> 두었습니다 — DB 컬럼과 API 까지 따라 바꿔서 얻을 것이 없습니다.

세 가지 성질을 갖습니다.

1. **풀면 다른 것들이 따라 풀린다.** 문제 목록 중 하나가 아니라, 그 지점을 넘어야
   나머지가 의미를 갖는 곳.
2. **풀 수 있어야 한다.** "시장이 어렵다"는 핵심 난제가 아니다. 어렵지만 손댈 수
   있는 지점이어야 한다.
3. **하나나 둘이다.** 다섯 개면 핵심 난제가 아니라 그냥 문제 목록이다.

예를 들어 "과제가 무엇을 이루려는지 정의하지 않고 돌아간다"가 풀리면 KPI 연결도
등급 지정도 성과 측정도 따라 풀립니다. 반면 "PL 한 사람에게 집중"은 진짜 문제지만
그것을 풀어도 나머지는 그대로입니다. 앞이 핵심 난제고 뒤는 아닙니다.

**진단의 산출물이 점수 75개가 아니라 몇 줄**인 이유가 이것입니다. 그래야 다음
단계가 백지에서 시작하지 않고 "이것을 쪼갠다"로 이어집니다.

## 2. 방법론 조사 결과와 권고안

실무에 정해진 절차가 없으니 처음부터 설계한다는 전제로, 최근 프레임워크들을
조사했습니다.

### 조사에서 확인한 것

| 출처 | 요지 | 이 모듈에 주는 시사점 |
|---|---|---|
| **AX-5R** (Systems, 2026) | AI 도입이 전환으로 이어지지 못하는 이유는 도구만 주고 **업무 재설계·책임·리스크·성과측정**을 안 하기 때문. 실패 유형을 readiness·redesign·role·risk·return 다섯 설계 기능에 대응 | 단계를 나열하는 것만으로는 부족. **각 단계에 품질 게이트가 필요** |
| **디지털 트윈 성숙도 모델** (다수 연구) | 5단계 성숙도 × 다차원 지표(데이터·모델·통합·분석·응용 등)로 **현재 위치와 목표를 먼저 정량화** | 전략의 출발점은 이슈가 아니라 **현재 상태 진단**. 포탈 데이터가 이걸 채울 수 있음 |
| **Reactore 4D** (Discover·Design·Deploy·Deepen) | 파일럿 → 확산의 단계적 로드맵 | 전략 산출물이 **로드맵 형태**로 끝나야 실행으로 이어짐 |
| **가치 오케스트레이션** 관점 | 2026년 산업 담론은 개별 자산이 아니라 **전사 관점의 시뮬레이션·의사결정** | 전략 단위가 개별 과제가 아니라 **포트폴리오** |

### 권고 — 5단계 척추 + 5개 횡단 게이트

조사 결과를 종합해 다음을 제안합니다. **말씀하신 4단계를 버리는 게 아니라,
앞에 진단을 붙이고 뒤에 검증 축을 얹은 것**입니다.

```
① 현재 상태 진단   ② 이슈 정의   ③ 전략 요소 분석   ④ 솔루션·포트폴리오   ⑤ 로드맵·기획서
      │                │                │                    │                    │
      └────────────────┴────────────────┴────────────────────┴────────────────────┘
                    횡단 게이트 (AX-5R): 준비도 · 업무 정착 · 역할 · 리스크 · 성과
```

**왜 ① 진단을 앞에 두는가.** 이슈부터 시작하면 "느낌상 문제"가 이슈가 됩니다. 성숙도
진단을 먼저 하면 이슈가 **격차(gap)** 로 정의되어 근거를 갖습니다. 그리고 이 진단은
포탈 데이터로 상당 부분 자동으로 채울 수 있습니다 — 이 모듈의 가장 큰 차별점입니다.

**왜 게이트를 횡단으로 두는가.** AX-5R의 다섯 기능은 순서가 아니라 **매 단계에서
물어야 할 질문**입니다. 예를 들어 ④에서 솔루션을 하나 도출하면 그때마다:

| 게이트 | 묻는 것 |
|---|---|
| 준비도 (readiness) | 데이터·인력·인프라가 되는가 |
| 업무 정착 (redesign) | 평소 일하는 과정 안에 어떻게 들어가는가 |
| 역할·책임 (role) | 누가 책임지는가 |
| 리스크 관리 (risk) | 실패하면 무엇이 깨지는가 |
| 성과 측정 (return) | 무엇으로 좋아졌다고 말할 것인가 |

⚠️ **'업무 재설계'라고 부르지 않습니다.** AX 맥락에서 그 말은 인력 감축 뉘앙스를
달고 다녀서, 그렇게 읽히면 답변 자체가 왜곡됩니다. 묻는 것은 조직 축소가 아니라
'실제 업무에 녹아들었는가'입니다. 진단의 조직 역량 축과 같은 말을 씁니다.

다섯 개가 다 답해지지 않은 항목은 **미완성으로 표시**됩니다. "그럴듯한 전략"과
"실행 가능한 전략"을 가르는 지점이 여기입니다.

> **[결정 필요]** 이 5+5 구조를 채택할지, 원래 4단계로 갈지. 진단 단계를 빼면 구현은
> 가벼워지지만 근거의 출발점이 사라집니다.

## 3. 방법론 — 데이터로 정의하고 교차검증한다

### 데이터로 정의

방법론을 코드에 박으면 추가할 때마다 개발이 필요합니다. **정의를 데이터로 두고
화면이 해석**합니다.

```jsonc
{
  "key": "swot",
  "name": "SWOT 분석",
  "stage": "analysis",
  "frames": [
    { "key": "S", "label": "강점", "hint": "내부 · 긍정" },
    { "key": "W", "label": "약점", "hint": "내부 · 부정" },
    { "key": "O", "label": "기회", "hint": "외부 · 긍정" },
    { "key": "T", "label": "위협", "hint": "외부 · 부정" }
  ],
  "evidenceHints": {
    "S": ["tech_level.high", "dashboard.completed"],
    "W": ["tech_level.low", "kpi.missed"],
    "O": ["reference.roadmap_upcoming"],
    "T": ["kpi.declining"]
  }
}
```

새 방법론 추가가 **데이터 입력**이 됩니다.

### 교차검증 — 같은 입력에 여러 방법론

리뷰에서 말씀하신 부분입니다. 하나의 이슈 집합에 **둘 이상의 방법론을 동시에
돌리고 결과를 비교**합니다.

```
        이슈 집합
        ├─ SWOT   으로 분석 → 요소 A, B, C
        ├─ 3C     으로 분석 → 요소 A, B, D
        └─ VRIO   으로 분석 → 요소 A, E

  합류점 : A     (세 방법론이 모두 지목 → 신뢰도 높음)
  분기점 : C, D, E  (한 방법론만 지목 → 검토 필요)
```

**분기점이 오히려 중요한 신호입니다.** 한 렌즈로만 보이는 것은 그 렌즈의 편향일 수도,
남들이 놓친 통찰일 수도 있습니다. 화면에서 이를 구분해 보여줍니다.

AI는 여기서 "왜 이 방법론에서만 나왔는지"를 설명하는 역할을 합니다.

### 1차 방법론 (제안)

| 단계 | 방법론 | 고른 이유 |
|---|---|---|
| ① 진단 | **DT 성숙도 5단계** (데이터·모델·통합·분석·응용) | 조사에서 가장 널리 쓰이는 축. 포탈 데이터로 채워짐 |
| ② 이슈 | **격차 분석**, **5 Whys**, **이슈 트리** | 진단 결과를 이슈로 전환 |
| ③ 분석 | **SWOT**, **3C**, **VRIO** | 서로 다른 렌즈 — 교차검증에 적합 |
| ④ 솔루션 | **TOWS**, **Three Horizons** | TOWS는 SWOT을 입력으로 받고, 3H는 단기/중기/장기로 가름 |
| ⑤ 로드맵 | **Pyramid 구조**, **역량 로드맵** | 문서 골격 + 실행 순서 |

> **[결정 필요]** VRIO·Three Horizons는 다소 무겁습니다. 1차는 각 단계 2개씩으로
> 줄이고, 교차검증 구조만 갖춰두는 것도 방법입니다.

씁니다.

### 무엇을 재는가 — 시간이 해결하는 것은 재지 않는다 (구현 반영)

처음에는 진행률·완료율을 넣었다가 뺐습니다. **연말이면 어차피 100% 에 가까워지므로
"지금 몇 %인가"는 날짜의 함수일 뿐** 전략 판단 근거가 못 됩니다. 대신 놔두면 그대로
남는 구조적 결함을 잽니다.

| 지표 | 무엇을 잡나 |
|---|---|
| 성과 미정의 비율 | 무엇을 이루려는지 안 적고 진행 중. 끝나도 성과를 말할 수 없다 |
| KPI 미연결 비율 | 어느 지표에도 안 걸린 과제. 전략과 실행이 끊긴 지점 |
| 연결 등급 미지정 | 주·보조·간접 미지정. 연결이 다 동등해 보여 못 읽는다 |
| 주기여 연결 비율 | 지표를 직접 미는 과제 없이 기반만 쌓고 있는가 |
| PL 집중도 | 사람 하나에 묶인 조직 |
| 부서 편중도 | 참여 부서가 많아도 한 곳이 대부분이면 확산이 아니다 |
| 일정 쏠림 | 종료가 한 분기에 몰려 검증 부하가 집중 |
| 고립 과제 비율 | 선후 관계 없이 따로 도는 과제 |
| KPI 달성률 | 목표 대비 실적 |

**지표 쪽에서 뒤집어 보는 것**도 함께 합니다. 사업부별 숫자가 다 멀쩡해도 어떤
지표를 아무도 주기여로 밀지 않을 수 있고, 그건 사업부 집계로는 드러나지 않습니다.

### 임계값은 한 곳에서만 관리한다 (구현 반영)

기준이 두 곳에 있으면 반드시 갈립니다. 실제로 그랬습니다 — **관측 표의 빨강/노랑은
`40/25`, `60/80` 이 코드에 박혀 있어 ⚙설정을 안 따랐습니다.** 설정에서 기준을 풀면
발견 사항에서는 사라지는데 표의 칸은 계속 붉은 상태가 됐습니다.

그래서 지표 ↔ 임계값 짝을 `definitions.METRIC_THRESHOLD_KEY` 에 두고 `/meta` 로
내려보내, 화면은 그것만 씁니다. 색의 뜻이 분명해집니다.

| | |
|---|---|
| 🔴 | 기준을 넘음 — **발견 사항에 뜨는 것과 같은 값** |
| 🟡 | 아직 안 넘었지만 기준의 10% 안쪽 |
| 🟢 | 여유 있음 |

칸에 대면 `KPI 미연결 비율: 42% · 기준 ≥ 30%` 처럼 기준까지 보입니다. 짝이 없거나
설정을 못 받았으면 **아예 안 칠합니다** — 근거 없이 칠하느니 안 칠하는 편이 낫습니다.

같은 작업에서 규칙 하나가 어긋난 것도 잡았습니다. `kpi_shortfall` 만 `<` 였고 높을수록
좋은 다른 두 규칙은 `<=` 였습니다. 달성률이 정확히 80% 면 표는 붉은데 목록엔 안 뜨는
상태였습니다. `<=` 로 맞췄습니다.

**지표를 새로 넣고 짝을 잊으면** 그 칸만 조용히 색이 안 칠해지고 아무 오류도 안 납니다.
눈으로는 못 잡으므로 `definitions.py` 임포트 시점에 터지는 `assert` 두 개를 넣었습니다.

### 임계값 미리보기 — 「이 값이면 몇 건인가」 (구현 완료)

⚠️ **조정 도구가 없으면 조정이 안 일어납니다.** 값 스물한 개가 전부 짐작인데,
지금까지는 값을 바꾸고 → 저장하고 → 진단 화면으로 가서 → 목록을 눈으로 세는
수밖에 없었습니다.

```
  성과 미정의 비율                     [30] %   ↺
  [📊 이 값이면 몇 건?]
     28   29   30   30   30   30   28
     ▁▁   ▃▃   ██   ██   ██   ██   ▁▁
      0   15   30   45   60   75   90
  막대는 발견 사항 건수입니다. 눌러서 그 값으로 넣을 수 있습니다.
```

⚠️ **규칙을 다시 구현하지 않습니다.** "이 값이면 대충 이 정도"를 따로 계산하면
미리보기와 실제 화면이 다른 숫자를 말하는 날이 옵니다. 대신
`build_plan_payload()` 를 **후보 값으로 다시 부릅니다** — 그래서 `thresholds` ·
`source` 를 밖에서 넣을 수 있게 열어 두었습니다. 테스트가 미리보기 건수와 진단
화면 건수가 같은지 봅니다.

⚠️ **한 번에 값 하나만 훑습니다.** 스물한 개를 전부 ±한 칸씩 보면 마흔 번 넘게
다시 계산해 2.8초가 걸립니다(실측). 사람은 어차피 한 번에 하나를 만지므로, 고른
값 하나를 **범위 전체로** 훑습니다 — 0.3~0.6초, 그리고 ±한 칸보다 정보가 많습니다.
그 근처에서 아무것도 안 바뀌는 값이 실제로 많은데, 한 칸씩만 보면 "안 바뀐다"만
알 뿐 어디로 가야 하는지는 모릅니다.

⚠️ **아무 일도 안 하는 값은 그렇다고 말합니다**(`flat`). 범위 전체에서 건수가
안 바뀌면 그 값은 지금 데이터에서 아무것도 하지 않습니다 — 그걸 안 알려주면
사람은 계속 만지며 시간을 씁니다.

근거 원천은 한 번만 읽습니다(`_ReadOnce`). 과제 목록을 아홉 번 읽을 이유가
없습니다. 편집 권한자만 봅니다 — 바꿀 수 없는 사람에게 「낮추면 몇 건」을
보여 줄 이유가 없습니다.

### 임계값은 설정 화면에서 조정한다 (구현 반영)

어떤 값이 맞는지는 실제 데이터를 봐야 알 수 있고, 그 판단은 운영에서 이뤄집니다.
코드에만 두면 조정할 때마다 배포가 필요해 반복이 끊깁니다.

- 기본값은 코드(`definitions.THRESHOLDS`), **기본값과 다른 항목만** DB 에 저장
- 전부 저장하면 배포로 기본값이 개선돼도 손대지 않은 항목이 과거에 묶인다
- 기존 `ModuleSettings` 표를 쓰므로 새 테이블이 없다

프롬프트도 같은 방식으로 갑니다(아래 AI 절).

### ⚠ 운영 데이터는 반출하지 않는다 — 이 계획의 최대 제약

**전제: 운영 데이터는 개발 환경으로 내보내지 않습니다.** 스냅샷 반입도, 운영 API
직접 호출도 없습니다. 의미 있는 데이터는 운영서버 안에만 있습니다.

이 제약이 뜻하는 바는 분명합니다. **전략 모듈은 데이터가 있는 곳에서 돌아야 하고,
개발은 실제 데이터를 못 본 채로 진행해야 합니다.**

#### 근거 계층 — 두 가지 모드만 둔다

```
전략 모듈
    │
    ▼
EvidenceSource  (인터페이스)
    ├─ LocalDbSource     로컬 DB 조회        — 운영서버. 진짜 데이터
    └─ FixtureSource     합성 데이터 조회     — 개발. 구조만 같은 가짜 데이터
```

```
STRATEGY_EVIDENCE_SOURCE=local | fixture     # 기본값 fixture
```

전략 모듈 코드는 어느 쪽인지 모릅니다. 운영에 배포되면 `local`, 개발에서는
`fixture`입니다. **데이터가 오가지 않습니다.**

> ⚠️ **이 스위치가 배선돼 있지 않았습니다(2026-08-14 발견·수정).**
> `evidence.py` 는 `current_app.config` 에서 읽는데 `app/config.py` 에 그 키가
> 없었습니다. Flask 는 환경변수를 자동으로 가져오지 않으므로 항상 `None` →
> **운영에 배포하고 `.env` 에 `local` 을 넣어도 합성 데이터가 나왔을 것**입니다.
>
> 안전장치는 화면 상단의 합성 데이터 경고 띠입니다. **운영에서 그 띠가 보이면
> 이 값이 안 들어간 것**이니 그때 알아챌 수 있게 되어 있습니다.

**`local` 은 "운영 DB"가 아니라 "지금 붙어 있는 DB"입니다.** 개발에서 켜면 개발
DB 를 읽고, 그 내용은 시드라 숫자가 현실이 아닙니다. 그래도 켜볼 값은 있습니다 —
`LocalDbSource` 의 조인·KPI 매칭 쿼리가 `fixture` 로는 **아예 안 타기** 때문에,
시드로라도 돌려봐야 쿼리 버그가 잡힙니다. 다만 합성 데이터는 진단 규칙 13종이
전부 발화하도록 일부러 만든 것이라, 화면 상태를 두루 보려면 `fixture` 가 낫습니다.

#### 합성 데이터 규격 (확정)

운영 데이터를 보지 않고 만듭니다. 필요한 건 스키마(이미 `models.py`에 있음)와
분포 특성뿐입니다.

```
과제 수   2025년 150~170건
          2026년 150~170건
```

나머지(사업부 수, KPI 달성률 분포 등)는 기존 모델의 제약과 상식적인 범위로 채우고,
어긋나면 그때 조정합니다. 값은 가짜지만 **화면·집계·방법론 로직을 검증하기엔
충분**합니다.

#### AI 검증 경로 — MCP를 쓴다

사내 LLM은 **운영에서만** 접근됩니다. 하지만 **MCP는 개발·운영 양쪽에서 외부 AI를
붙일 수 있습니다.** 이미 `mcp_server/`가 도구 18종을 노출하고 있고, 사용자 JWT를
그대로 백엔드로 넘기는 구조라 권한도 그대로 지켜집니다.

그래서 AI 경로를 **둘로 나눕니다.**

| 경로 | 어디서 | 쓰임 |
|---|---|---|
| **① 사내 LLM** (백엔드 → `LLM_BASE_URL`) | 운영만 | 화면 안에서 버튼 누르면 도는 AI |
| **② MCP + 외부 AI** (Claude Code 등) | **개발·운영 둘 다** | 개발 중 검증, 운영에서 심층 분석 |

핵심은 **두 경로가 같은 것을 조작**하게 만드는 것입니다. AI가 무엇을 하든 결과는
`strategy_suggestion` 한 곳에 쌓이고, 사람이 채택/거부합니다.

```
① 사내 LLM ─┐
             ├─→  strategy_suggestion  ─→  사람이 확정
② 외부 AI  ─┘        (제안 큐)
   (MCP)
```

그러면 전략 모듈은 **전략용 MCP 도구**를 함께 제공해야 합니다.

```
strategy.get_plan(year)              전략 조회
strategy.list_evidence(target)       근거 조회
strategy.propose_issues(...)         이슈 제안 → 제안 큐로
strategy.propose_elements(...)       요소 제안
strategy.propose_solutions(...)      솔루션 제안
```

**쓰기 도구는 전부 "제안"입니다.** 외부 AI가 직접 확정하지 못합니다. 대시보드 모듈이
`actor_mode='ai'`로 위험 필드를 제안 큐에 보내는 것과 같은 방식입니다.

이 설계의 이점:

- 개발에서 **AI 동작 방식(도구 호출·제안 흐름)을 전부 검증**할 수 있습니다
- 운영에서는 같은 도구를 실제 데이터에 대고 씁니다
- 사내 LLM이 막혀 있어도 MCP로 대체 가능 — **단일 실패점이 없습니다**

다만 합성 데이터로는 **AI가 말이 되는 소리를 하는지**까지는 알 수 없습니다.
그건 여전히 운영에서 봐야 합니다.

#### 프롬프트 — 개발에서 만들고 운영에서 고친다

말씀하신 대로 둘 다 필요합니다. **시드 + 오버라이드** 구조로 갑니다.

```
git 저장소            운영 DB
seed_prompts.py  ──▶  strategy_prompt
(개발에서 작성)        (운영에서 편집)
                      · 편집하면 override=true
                      · "기본값으로 복원" 가능
                      · 버전 이력 보관
```

- **개발에서 초안을 만들어 커밋**합니다. 배포하면 시드로 들어갑니다.
- **운영에서 고치면 그 값이 우선**합니다. 원본은 남아 있어 언제든 되돌립니다.
- 다음 배포 때 시드가 바뀌어도 **운영에서 고친 것을 덮어쓰지 않습니다.** 대신
  "기본값이 바뀌었습니다" 표시를 띄워 사람이 판단하게 합니다.

방법론 정의도 같은 방식입니다.

왜 운영 편집이 꼭 필요한가:

| | 코드에만 둘 때 | 오버라이드가 있을 때 |
|---|---|---|
| 문구 한 줄 수정 | 커밋 → 태그 → 릴리스 → 배포 | **운영 화면에서 수정** |
| 반복 주기 | 수십 분 | 수 초 |

운영 데이터를 못 보는 개발자가 프롬프트를 완성할 수는 없습니다. **초안까지가 개발의
몫이고, 실제 데이터에 맞추는 것은 운영에서** 이루어져야 합니다.

버전을 남기므로 되돌릴 수 있고, 어떤 프롬프트로 만든 산출물인지도 추적됩니다.

#### 품질을 눈으로 보는 방법

AI 제안마다 **채택/거부와 사유**를 기록합니다.

```
strategy_ai_feedback
  id, suggestion_id, action(accept|reject|edit), reason, user_id, created_at
```

이건 운영 안에만 쌓이고, 화면에서 집계로 봅니다 — "이슈 추천 채택률 62%",
"방법론 추천 채택률 35%". **원자료를 꺼내지 않아도 어느 기능이 쓸 만한지** 보입니다.
낮은 항목의 프롬프트를 운영에서 고치면 됩니다.

#### LLM 접근

운영서버는 사내 LLM(`LLM_BASE_URL`)에 붙습니다. **개발 환경에서도 LLM 자체는
붙을 수 있어야** 합성 데이터로라도 호출 경로를 검증할 수 있습니다. 안 되면 AI 기능은
운영에서만 시험 가능합니다.

> **[결정 필요]** 개발 환경에서 사내 LLM에 접근 가능한지. 안 되면 Phase 4의 검증을
> 전부 운영에서 해야 하므로 배포 주기가 짧아야 합니다.

## 4-1. 전략 도구 — 무엇을 채용하고 무엇을 버렸나 (2026-08-17)

외부 검토에서 신기술 도입 전략의 표준 도구 열두 가지를 제안받았습니다
(PESTEL · SWOT · TOWS · Maturity · Gap · Value Chain · Use Case Mapping ·
Impact-Effort · Portfolio · ROI · Strategy Map · Roadmap).

**절반은 이미 이 모듈의 뼈대입니다.** 이름이 달랐을 뿐입니다.

| 제안 | 우리 것 |
|---|---|
| Maturity Model | ① 진단의 기술 성숙도 5단계 + 조직 역량 5축 |
| Gap Analysis | 목표−현재 격차 → ② 이슈 후보 |
| Impact–Effort | 이슈의 `impact × feasibility` |
| SWOT | ③ 분석 |
| TOWS | ④ 로 계획됨 |
| Strategy Map | 「지표별 연결」이 과제→KPI 기여도를 이미 봄 |

### 채용한 것

**Value Chain — 우리 데이터로 채워집니다.** 과제 222건이 이미 프로세스에 붙어
있고, 설문도 프로세스로 분기합니다.

⚠️ **프로세스는 사업부와 같은 레벨이 아닙니다.** 먼저 사업부가 나뉘고 그 안에서
   프로세스가 나뉩니다 — **MX 의 개발과 VD 의 개발은 서로 독립적인 조직**입니다.
   처음에 평평한 축으로 만들었다가 고쳤습니다. 합쳐 놓으면 이렇게 됩니다:

```
평평하게 봤을 때   개발 109건 · 성과 미정의 49.5%
사업부 안에서      MX 40건 70.0% · VD 28건 64.3% · DA 13건 0.0% · NW 11건 9.1%
```

49.5% 는 **어느 조직의 숫자도 아닙니다.** 그래서 화면에서 프로세스를 볼 때
「어느 사업부 안에서」를 함께 고릅니다. 전사 합계도 볼 수 있게 두되 **합친
값이라고 적습니다.**

⚠️ **사람이 채울 격자를 늘리지 않습니다.** 같은 과제를 다르게 자르는 것뿐이라
   추가 입력이 없습니다. 이 모듈이 격자를 경계하는 이유가 그것입니다.

발견 사항도 **사업부 안에서** 짚습니다 — 「의료기기 · 품질 과제 62.5% 가 성과를
정의하지 않았습니다」처럼, 그 사업부의 다른 프로세스는 기준 아래일 때만 냅니다.
전부 나쁘면 프로세스 문제가 아니라 그 사업부의 문제이고 사업부 축이 이미
짚습니다. 과제 5건 미만인 칸은 판정하지 않습니다 — 3건 중 3건이면 100% 지만
그 100% 는 조직의 성질이 아니라 표본의 성질입니다.

⚠️ 용어는 **프로세스**입니다. 한동안 「공정 단계」라고 적었는데, 개발·제조·품질은
   생산 라인의 순서가 아니라 일의 분야이고, 무엇보다 대시보드와 설문이 이미
   「프로세스」로 부르고 있습니다. 한 가지에 두 이름을 두면 안 됩니다.

**Portfolio 사분면 · 솔루션→KPI 연결** — ✅ ④ 에서 같이 만들었습니다.
`impact × feasibility` 는 이슈와 같은 1~5 척도를 씁니다. 8절 ④ 참고.

### 버린 것과 이유

**PESTEL — 안 만듭니다.** 여섯 칸이 **전부 백지**입니다. 지금 O·T 두 칸이
백지라 설문으로 메우는 중인데, PESTEL 은 그 백지를 여섯 칸으로 늘립니다.
「근거 없는 칸은 인상평으로 채워지고, 그 인상평이 데이터에서 나온 숫자 옆에서
같은 무게로 보인다」는 이 모듈의 원칙에 정면으로 어긋납니다. 필요하면 O·T
안에서 다룹니다.

**ROI / Business Case — 지금은 아닙니다.** 진단이 지금 "MX 과제 70% 가 성과를
정의하지 않았습니다"를 짚고 있습니다. **그 상태에서 ROI 를 계산하면 우리가
방금 지적한 문제를 우리가 반복하는 것**입니다. 성과 정의가 채워진 뒤에 붙입니다.

**Use Case Mapping — 과제가 이미 그 역할입니다.** `dt2_projects` 가 use case
목록입니다. 새로 만들면 두 벌이 되고 어느 쪽이 정본인지 갈립니다.

**Maturity Model 재정의 — 불필요합니다.** 제안받은 Lv.1~5(Digitization →
Autonomous)는 우리 기술 성숙도 5단계와 사실상 같습니다.

## 4-2. 난제는 위에서도 아래에서도 만들어진다

진단이 난제를 남기고 그것을 쪼개는 것이 본줄기지만, **반대 방향도 실제로
일어납니다** — 진단의 여러 곳에서 나온 것을 각각 적어 놓고 보니 그것들을
관통하는 하나가 보이는 경우입니다. 그게 난제입니다.

그래서 ② 이슈 화면에 **묶는 길을 둘** 둡니다.

```
난제에 안 걸린 이슈  → 골라서 「난제로 묶기」
진단 격차·설문 후보  → 골라서 「새 난제로」     ← 이슈를 거치지 않고 바로
```

⚠️ **후보를 바로 묶는 길이 없으면 사실상 막힙니다.** 후보를 하나씩 「난제
비움」으로 저장해 고아로 만든 뒤 다시 골라 묶어야 하는데, 세 건이면 대화상자를
네 번 엽니다. 같은 일이라 한 번에 합니다.

⚠️ **한 트랜잭션입니다.** 난제만 만들어지고 이슈가 안 붙으면 빈 난제가 남아
   "넘겠다고 해놓고 아무것도 안 하는" 난제처럼 보입니다. 후보 하나가 잘못돼도
   난제를 안 만듭니다.

## 5. AI의 역할 — 연결에서 추천까지

리뷰 반영으로 **추천**을 정식 기능에 넣습니다. **확정은 언제나 사람**입니다.

### 하는 일

| 구분 | 기능 |
|---|---|
| **연결** | 근거 자동 매칭 · 단계 간 연결 제안 · 일관성 검사 |
| **추천** | **이슈 후보 도출** (진단 격차에서) · **방법론 추천** (이슈 성격에 맞는 렌즈) · **솔루션 후보 제시** · **우선순위 제안** (영향도×실행가능성) |
| **비평** | 누락 지적 · 교차검증 분기점 해설 · 게이트 미충족 항목 표시 |
| **초안** | 근거 기반 문장 생성 |

**방법론 추천**이 특히 유용할 것으로 봅니다. 사용자가 방법론을 몰라도, 이슈 성격을
보고 "이건 VRIO보다 3C가 맞습니다 — 외부 경쟁 관점이 필요한 이슈라서" 라고 제안할
수 있습니다.

### 하지 않는 일

- **결정하지 않습니다.** 모든 산출물은 사람이 확정해야 확정됩니다.
- **근거 없이 쓰지 않습니다.** 생성 문장에 출처를 답니다. 없으면 "근거 없음"으로
  눈에 띄게 표시하고, 확정 시 그 개수를 경고합니다.

백엔드가 이미 같은 태도를 갖고 있습니다 — 대시보드 AI 쓰기가 `actor_mode='ai'` 로
위험 필드를 제안 큐에 보내는 것과 같은 방향입니다.

### 재사용할 자산

**LLM 인프라를 새로 만들 필요가 없습니다.**

| 자산 | 위치 |
|---|---|
| LLM 호출 래퍼 (`chat`, tool call 파싱) | `backend/app/modules/digital_twin_dashboard/ai/llm.py` |
| 에이전트 루프 | `.../ai/agent.py` |
| 포탈 데이터 조회 도구 | `.../ai/agent_tools.py` |
| 페이지별 AI 컨텍스트 패턴 | `backend/app/modules/ai_context/` |
| MCP 도구 18종 | `mcp_server/server.py` |

전략용 도구 세트만 정의하면 됩니다.

> **[결정 필요]** AI 실행 시점. `LLM_TIMEOUT=120` 이고 응답이 수십 초 걸릴 수 있어
> **요청 시에만 + 비동기**를 제안합니다.

## 6. 설문 — 단계가 아니라 두 번째 근거 원천

> **📄 상세 계획은 [SURVEY_PLAN.md](./SURVEY_PLAN.md) 로 옮겼습니다.**
> 진입점 설계, 데이터 모델, API 설계, 남은 작업이 거기 있습니다.
> 이 절에는 **왜 그렇게 정했는가**만 남깁니다.
>
> 진행 상황: **데이터 모델 5표 완료**(`6e4d7588e875`). API 부터 남음.

**설문은 특정 단계에 속하지 않습니다.** 게이트처럼 **모든 단계를 가로지릅니다.**

근거는 두 곳에서 옵니다.

```
포탈 데이터   시스템이 아는 것   — 과제 수, KPI 달성률, 로드맵
설문         사람만 아는 것     — 체감, 판단, 우선순위, 제약
```

둘 다 같은 `strategy_evidence` 테이블로 들어갑니다. 화면의 근거 패널에도 나란히
놓입니다. **시스템이 모르는 것을 사람에게 묻는 장치**라고 보면 정확합니다.

### 단계별로 무엇을 묻는가

| 단계 | 설문이 채우는 것 | 예시 문항 |
|---|---|---|
| ① 진단 | **체감 성숙도.** 시스템은 과제 수를 알지만 그게 잘 돌아가는지는 모름 | "우리 부서의 시뮬레이션 데이터 신뢰도는?" (1~5) |
| ② 이슈 | **현장이 느끼는 문제.** 데이터에 안 잡히는 병목 | "가장 큰 걸림돌 3개를 순서대로" |
| ③ 분석 | **인식 검증.** AI가 뽑은 강점/약점에 실제로 동의하는지 | "이 항목이 우리 강점이라는 데 동의?" |
| ④ 솔루션 | **실행 가능성·우선순위.** 영향도×난이도는 사람이 매겨야 함 | "이 솔루션의 실행 난이도는?" |
| ⑤ 기획서 | **검토 의견** | 자유서술 |

가장 무겁게 쓰이는 곳은 **① 진단과 ④ 우선순위**입니다. 진단은 시스템 데이터만으로는
반쪽이고, 우선순위는 애초에 판단의 영역입니다.

### 구현

`collaboration_board` 에 설문 모델이 **이미 있지만 만들다 만 것이라 쓰지
않습니다**(2026-08-15 확인). 방향도 다릅니다 — 그쪽은 익명 여부를 설문마다
켜고 끄는 게시판형이고, 여기서 필요한 것은 익명 방식이 하나로 고정되고 문항이
진단 축에 연결되는 설문입니다.

⚠️ 대신 **클래스·표 이름이 겹치지 않아야 합니다.** 겹치면 매퍼 설정이 실패해
DB 질의가 전부 죽습니다 — 실제로 v0.1.22 가 그 상태로 릴리스됐습니다.
그래서 `StrategySurvey*` / `strategy_survey_*` 로 짓고, CI 에
`backend/scripts/check_models.py` 검사를 넣었습니다. 자세한 것은
[SURVEY_PLAN.md](./SURVEY_PLAN.md) 0·4절.

- 유형: 객관식 · 척도(1~5) · 순위 · 자유서술
- 대상: 부서 / 역할 / 지정 인원
- **집계값과 원자료를 둘 다** 보관합니다. AI 요약은 원자료를 근거로 달아야 검증됩니다.
- 단계별 **문항 템플릿**을 두어 매번 설문을 새로 설계하지 않게 합니다.
- **진입점은 두 개입니다.** 만들기·집계는 전략 모듈 안(관리자 전용), 응답은
  홈의 별도 카드(전원 공개). 하나로 묶으면 권한이 꼬입니다 — SURVEY_PLAN 2절.

### ⚠ 응답을 사업부로 묶을 방법이 지금은 없다

진단이 사업부 단위인데, 응답자에게서 사업부를 알아낼 경로가 확인되지 않았습니다.
개발 DB 에서 `users.department` 는 8명 전부 `NULL`, `departments.division_id` 도
100행 전부 `NULL` 입니다. 운영은 다를 수 있지만 **반출 제약 때문에 확인할 수 없습니다.**

그래서 `survey_response.division_source` 에 `profile|picked|unknown` 을 남기고,
집계 화면에 **「소속 미확인 N건」을 반드시 표시**합니다. 숨기면 그럴듯한 사업부별
평균이 나오는데 실은 절반이 어디 것인지 모르는 상태가 됩니다. 자세한 것은
SURVEY_PLAN 5절.

### 제약 아래에서의 이점

설문은 **운영에서 생성되는 데이터**입니다. 반출 제약과 무관하게 운영 안에서
쌓이고 쓰입니다. 오히려 이 제약 때문에 설문의 값어치가 커집니다 — 개발이 못 보는
맥락을 운영 사용자가 직접 채워 넣는 통로이기 때문입니다.

### 익명 처리 (확정)

**응답자명은 숨기고 소속만 표시합니다. 단 관리자는 응답자를 확인할 수 있습니다.**

```
일반 열람   "생산기술팀 · 3점"
관리자      "생산기술팀 · 홍길동 · 3점"
```

⚠ **여기서 반드시 지켜야 할 것이 있습니다.** 이 구조는 진짜 익명이 아닙니다.
설문 화면에 **"관리자는 응답자를 확인할 수 있습니다"를 명시**해야 합니다.

익명이라고 안내하고 실제로는 추적 가능하면, 나중에 그 사실이 알려졌을 때 설문
자체의 신뢰가 무너집니다. 한 번 무너지면 이후 어떤 설문도 솔직한 답을 못 받습니다.
전략 수립에 쓸 데이터라면 이건 치명적입니다.

정직하게 안내하면 오히려 응답 품질이 예측 가능해집니다 — 사람들이 "이건 기록에
남는다"를 알고 답하니까요. 민감한 주제는 설문 대신 다른 방법을 쓰면 됩니다.

- 관리자 열람은 **감사 로그에 남깁니다** (누가 언제 어느 설문의 응답자를 봤는지)
- 자유서술은 특히 신원이 드러나기 쉬우므로, AI 요약 시 개인 특정 표현을 걸러냅니다

  id, year, title, status(draft|confirmed), owner_id
  ⚠️ status 는 ⑤ 기획서 확정을 따라간다. 두 곳에서 정하면 "전략은 확정인데

strategy_assessment      ① 진단

strategy_issue           ② 이슈  ← 구현됨

strategy_element         ③ 요소 분석

strategy_solution        ④ 솔루션
  id, plan_id, title, description, element_ids,

strategy_gate            횡단 게이트 (AX-5R)

strategy_document        ⑤ 기획서

strategy_document        ⑤ 기획서  ← 구현됨

  ⚠️ 본문은 안 담는다. 볼 때마다 ①~④ 를 조립한다

⚠️ strategy_evidence 는 **만들었다가 지웠습니다.** Phase 1 에 넣고 한 번도 안
   썼습니다. 원래 목적이던 「근거 시점 스냅샷」은 이미 다른 것들이 합니다 —
   확정본은 `strategy_document.snapshot` 이, 설문 근거는 볼 때마다 계산이.
   안 쓰는 표가 남아 있으면 다음 사람이 그게 쓰이는 줄 알고 거기 맞춰 짭니다.

survey / survey_question / survey_response
  전략 단계에 연결. stage, target_type, target_id 로 어디에 쓰일지 지정

strategy_prompt          AI 프롬프트 — 운영에서 편집
  id, key, version, body, active, updated_by, updated_at

strategy_methodology     방법론 정의 — 운영에서 편집
  id, key, definition(JSON), active, updated_by, updated_at

strategy_suggestion      AI 제안 큐 — 사내 LLM·외부 AI(MCP) 공용
  id, plan_id, stage, target_type, target_id,

strategy_methodology     방법론 정의 — 시드 + 운영 오버라이드

```

`strategy_suggestion`이 두 AI 경로의 합류점입니다. `origin`으로 어느 경로에서 왔는지
남기고, **어느 쪽이든 `pending` 으로 들어와 사람이 확정**합니다.

`seed_hash`는 배포된 기본값의 해시입니다. 다음 배포에서 기본값이 바뀌었는데 운영에서
이미 고쳐 놓았다면, 덮어쓰지 않고 **"기본값이 바뀌었습니다"만 표시**합니다.

`strategy_evidence.snapshot`이 핵심입니다. **근거로 삼은 시점의 값을 복사**해 둡니다.
원본이 나중에 바뀌어도 "그때 이 숫자를 보고 이렇게 판단했다"가 남아야 검증됩니다.
`source_mode`가 `fixture`인 근거는 **합성 데이터 기반**이므로 화면에서 확실히
구분해야 합니다 — 개발에서 만든 전략이 운영 산출물로 오인되면 안 됩니다.

## 8. 화면 구성

### 공통 규칙 (구현 반영)

**폭을 잡되, 글줄에만 잡는다.** 이 모듈은 글이 많아서 폭을 안 잡으면 넓은
모니터에서 짧은 문장 한 줄이 2000px 를 차지해 눈이 줄을 놓칩니다.

⚠️ 한동안 그 상한(1440px)을 **바깥 상자**에 걸었는데, 그러면 곁가지(흐름도·후보
열)까지 같이 묶입니다. 1920 화면에서 **좌우 480px 를 버리면서 정작 안에서는
서로 폭을 뺏는** 상태였습니다 — 후보를 옆에 세우려면 흐름도를 접어야 하나 같은
질문이 거기서 나왔습니다.

지금은 이렇습니다:

```
바깥 상자   1860px   흐름도 208 + 본문 1120 + 후보 열 480 + 여백
본문 열     1200px   ← 글줄 상한은 여기에만 (② 이슈만 1120)
후보 열     22~30rem  남는 폭을 먹되 30rem 에서 멈춘다
```

후보 열이 **남는 폭을 먹습니다.** 본문은 상한에서 멈추므로 그 위로 남는 자리는
후보 쪽이 쓰는 편이 낫습니다 — 후보 제목은 「MX · 조직 역량 · 성과 측정 2단계 →
4단계」처럼 깁니다. 다만 **30rem 에서 멈춥니다**: 더 넓히면 그 안의 글줄이 다시
길어져서, 상한을 안쪽으로 옮긴 이유가 무색해집니다.

곁가지는 상한 **밖**이라 서로 폭을 안 뺏습니다. 고정 바도 같은 바깥 폭이라
왼쪽 세로줄이 맞습니다.

`지표별 연결` 은 가운데 4칸이 고정폭이라 남는 폭을 지표명 칸이 다 먹어서,
그 표만 940px 로 따로 잡았습니다.

**발견 사항과 핵심 난제는 세로로 쌓습니다**(2026-08-16 변경). 한동안 가로로 나란히
두었습니다 — `[핵심 난제로 →]` 가 왼쪽에서 오른쪽으로 보내는 흐름이라서요. 그런데
둘 다 목록이라 나란히 두면 **한쪽이 길어질 때 다른 쪽 아래가 텅 빕니다.** 게다가
1200px 미만에서는 어차피 세로로 떨어져서, 규칙이 화면 폭마다 달랐습니다. 흐름은
`[핵심 난제로 ↓]` 버튼과 왼쪽 목차의 ②③ 이 말해 줍니다.

이슈의 난제 카드는 두 칸을 유지합니다 — 난제는 설계상 많아야 서넛이라 세로로만
쌓으면 하나가 1400px 를 쓰면서 짧은 이슈 몇 줄만 놓입니다. 본문 열 1200px 안에서
`520 × 2 + 여백 = 1060` 이라 후보 열을 세워도 두 칸이 유지됩니다.

**후보는 1760px 이상에서 오른쪽 곁열로** 갑니다. 난제 목록을 보면서 골라야 묶기
판단이 되기 때문입니다 — 바닥에 있으면 어느 난제와 겹치는지 보려고 위아래로
오갑니다. 좁으면 지금까지처럼 바닥에 붙습니다.

⚠️ **두 곳에 그리지 않습니다.** CSS 로 한쪽을 감추면 같은 컴포넌트가 두 벌
   그려져서, 곁열에서 고른 후보가 바닥 것에는 없습니다. 자바스크립트로 판단해
   한 곳만 그립니다(`useWideScreen`).

**왼쪽에 흐름도를 띄웁니다**(1280px 이상). 화면에 패널이 여섯인데 **서로 어떻게
이어지는지가 안 보였습니다** — "반영을 누르면 무엇이 바뀌나", "발견 사항은 어디서
나오나", "핵심 난제는 발견 사항에서만 오나" 를 매번 되물어야 했습니다. 문서로 답하면
그 문서를 아무도 안 폅니다.

처음에는 목차와 흐름도를 양쪽에 하나씩 두었는데, **이름이 겹쳐 두 벌이 나란히 있는
꼴**이라 목차를 걷어내고 흐름도 하나로 합쳤습니다. 길잡이 노릇(지금 어디인가·거기로
가자)도 이것이 합니다.

`position: fixed` 가 아니라 **스크롤 영역 안의 sticky** 입니다 — 이 앱은 창이 아니라
`MainContent` 가 스크롤되므로, sticky 면 위치를 계산할 필요가 없고 본문과 겹치지도
않습니다. **다른 단계로 나가는 칸(② 이슈)은 안 눌립니다** — 눌러도 아무 일이 없으면
고장으로 보이고, 여기서 단계를 바꾸면 보던 자리를 잃습니다. **화면에 없는 것은 안
그립니다** — 안 도는 화살표를 그려 두면 왜 안 되는지 찾느라 시간이 갑니다.

**단계 탭과 연도는 스크롤 밖에 고정.** 지금 어느 단계의 몇 년도를 보고 있는지는
아래로 내려가도 계속 보여야 합니다. `position: sticky` 로 겹치지 않고 **스크롤 영역
자체를 탭 아래로** 옮겼습니다. 오류 메시지도 이 고정 바 안에 둡니다 — 화면 아래에서
저장하다 실패했는데 오류가 맨 위에만 뜨면 아무도 못 보고, 저장이 안 된 줄 모르고
넘어갑니다.

**저장할 때 화면을 덮지 않는다.** 처음엔 저장할 때마다 전체를 "불러오는 중" 패널로
갈아끼웠는데, 스크롤 컨테이너의 내용이 통째로 사라졌다 돌아오면서 **스크롤이 맨 위로
튀었습니다.** 항목 하나 추가했을 뿐인데 보던 자리를 잃습니다. 읽기 함수를 둘로
나눴습니다.

| | 언제 | 화면 |
|---|---|---|
| `loadPlan` | 처음 열 때 · 연도 바꿀 때 · 전략 생성 | 전체를 덮음 (그때는 맞다) |
| `fetchPlan` | **저장 후 다시 읽기** | 안 덮음 → 보던 자리 유지 |



### ① 진단 (구현 완료)

**순서가 설계입니다.** 사람에게 격자부터 채우게 하면 근거 없는 점수가 3점으로
수렴하고, 채우는 것 자체가 목적이 됩니다. 그래서 데이터가 먼저 말하고, 사람은
발견 사항에 답하며, 결과로 핵심 난제를 고릅니다.

```
디지털 트윈 전략 기획                              [⚙ 설정]  [🏠 홈]
────────────────────────────────────────────────────────────────────
⚠ 개발용 합성 데이터로 동작 중입니다      ← fixture 모드일 때만
────────────────────────────────────────────────────────────────────
 [① 진단] [② 이슈] [③ 분석] [④ 솔루션] [⑤ 기획서]      ‹ 2026년 ›

 ① 관측          포탈 데이터로 계산. 사람이 매기지 않음
    지표 × 사업부 행렬. 나쁜 값은 색으로 드러남

 ① 지표별 연결   사업부에서 보면 안 드러나는 것
    지표 × (주·보조·간접·미지정). 주기여 0 인 지표는 붉게

 ② 발견 사항  N건  결론이 아니라 눈에 띄는 사실
    [높음] VD 과제 72.5% 가 어느 KPI 에도 걸려 있지 않습니다  [핵심 난제로 ↓]

 ③ 핵심 난제     올해 넘어야 할 결정적 지점 → 다음 단계의 입력
    ① 성과 정의 없이 과제가 돌아간다
       왜 이것이 핵심 난제인가 …

 ▸ 세부 판단     0/50 입력됨 — 전부 채울 의무는 없습니다   (접혀 있음)
```

- **격자는 맨 아래로 내리고 기본으로 접었습니다.** 화면을 열면 할 일이 "채우기"가
  아니라 "보기"로 시작합니다.
- 발견 사항에서 **한 번의 클릭으로 핵심 난제가 됩니다.** 제목과 근거가 그대로
  넘어가고 어느 관측에서 출발했는지(`source_finding`)도 남습니다.
- 핵심 난제가 3개를 넘으면 경고합니다. 전부가 중요하면 아무것도 중요하지 않습니다.
- **합성 데이터 경고 띠**는 `fixture` 모드에서 상시 표시됩니다.
- **[⚙ 설정]** 에서 진단 임계값을 조정합니다.

### ② 이슈 (구현 완료)

**난제가 축입니다.** 난제는 "넘어야 할 지점"이라 그대로는 손댈 수 없고, 이슈는
손댈 수 있는 단위여야 합니다. 그래서 난제를 세워두고 그 아래에 이슈를 매답니다.

```
② 이슈   핵심 난제마다, 그것을 넘으려면 무엇을 해야 하는지 적습니다.
         이슈 7건 · 할 일이 없는 난제 1개 · 난제에 안 걸린 이슈 2건

 ┃ 성과 정의 없이 과제가 돌아간다
 ┃   등록 시 성과 정의를 필수로 만든다
 ┃     왜 안 풀렸나 · 입력 화면이 선택으로 열려 있음
 ┃     [MX] [진단 격차] [영향 4 × 실행 3 = 12]
 ┃   [+ 이슈 추가]

 ┃ 지표를 직접 미는 과제가 없다
 ┃   ⚠ 이 난제를 넘으려면 무엇을 해야 합니까?
 ┃      올해 넘겠다고 정해놓고 할 일은 아직 하나도 적지 않았습니다.
 ┃      할 일이 안 떠오르면 난제가 너무 크거나, 애초에 난제가 아닐 수 있습니다.

 ▌어느 난제에도 안 걸린 이슈 · 2건
 ▌  전략과 무관한 일을 하고 있다는 신호입니다. 다만 난제 쪽이 틀렸을 수도
 ▌  있습니다 — 이슈를 지울지, 난제를 새로 세울지 판단하세요.

 ▸ 진단 격차에서 가져오기  3건        (접혀 있음)
 ▸ 올해는 안 하기로 한 것  1건        (접혀 있음)
```

이 화면이 반드시 드러내야 하는 두 가지가 **이슈가 없는 난제**와 **난제 없는
이슈**입니다. 둘 다 "틀렸다"고 말하지 않습니다 — 난제 쪽이 틀렸을 수도 있으니
보이게만 합니다.

**난제 없이 이슈를 추가하는 입구는 두지 않습니다.** 화면 위에 '이슈 추가'
버튼을 두면 그것이 고아 이슈를 만드는 주 경로가 됩니다 — 화면이 빨갛게 경고하는
바로 그 상태를요. 추가는 **난제 아래에서만**, 또는 진단 격차에서 옵니다.

그래서 **난제를 두 번 고르게 하지 않습니다.** 난제 카드 안의 [+ 이슈 추가]로
열면 난제는 이름표로 박혀 있고, 옮길 때만 [옮기기]를 눌러 드롭다운을 꺼냅니다.
이미 고른 것을 드롭다운으로 다시 보여주면 또 고르라는 말로 읽힙니다. 난제를
**묻는 곳은 격차 후보에서 가져올 때 하나뿐**입니다 — 그때는 정말로 안 정해져
있습니다.

### 화면에 쓰는 말

**'쪼개기' 같은 말은 버튼에 두지 않습니다.** 이 모듈의 설계에서 이슈는 난제를
손댈 수 있는 크기로 나눈 것이 맞지만, 그건 **설계의 언어지 사용자의 언어가
아닙니다.** 라벨을 이해해야 누를 수 있는 버튼이 되면 안 됩니다.

| 자리 | 쓰는 말 |
|---|---|
| 난제 카드 안의 버튼 | **[+ 이슈 추가]** — 위치가 이미 "이 난제의"를 말해줍니다 |
| 이슈가 없을 때 | **"이 난제를 넘으려면 무엇을 해야 합니까?"** |
| 입력칸 | **"무엇을 해야 합니까?"** |
| 상단 요약 | "할 일이 없는 난제 N개" |

설명이 필요한 곳은 **빈 상태**입니다. 거기엔 자리가 있고, 그때가 사람이 실제로
막혀 있는 순간입니다. 이미 이슈가 있으면 아무 설명도 띄우지 않습니다.

같은 이유로 `crux`(핵심 난제)와 마찬가지로 **코드 식별자는 그대로 둡니다.**
`SplitButton` 같은 이름은 화면에 안 나옵니다.

**④ 의 항목은 「솔루션」이라고 부릅니다.** 한동안 「수」(바둑의 수)라고 적었는데,
한 글자짜리 말이라 화면에서 '과제 수'·'건수'와 섞여 읽혔습니다. 단계 이름이 이미
「④ 솔루션」이므로 새 낱말을 늘리지 않고 그대로 씁니다.

⚠️ **「전략 과제」는 안 씁니다.** 포탈의 「과제」는 `dt2_projects` 의 실물 과제이고,
   화면 곳곳에서 '과제 5,000건'처럼 쓰입니다. 같은 말을 다른 뜻으로 두면 이 모듈이
   피해 온 「같은 기준이 두 곳에 있는 것」과 같은 종류의 혼선이 생깁니다.

**격차는 이슈 후보로만 내밉니다.** 자동으로 이슈가 되지 않습니다. 목표를 높게
잡아서 생긴 격차일 수도 있고, 그건 이슈가 아니라 목표를 고칠 일입니다. 후보를
누르면 **편집기가 채워진 채로 열립니다** — 바로 만들면 난제에 안 걸린 채 생겨
곧장 빨간 경고로 떨어지고, 그러면 그 경고가 무뎌집니다.

- 후보는 저장하지 않고 매번 계산합니다. 목표를 고치면 후보도 따라 바뀝니다.
- 이미 이슈로 만든 후보는 목록에서 빠집니다(`source_type:source_ref:division_id`).
- 격차가 **2단계 미만이면 후보로 안 내밉니다.** 한 단계 차이는 대개 늘 있는
  것이라, 그것까지 늘어놓으면 목록이 25줄이 되고 아무도 안 읽습니다.
- 지표는 방향을 봅니다. '성과 미정의 비율'은 관측이 목표보다 **높을 때** 문제입니다.
- **'올해는 안 한다'는 삭제가 아니라 `dropped`** 입니다. 지우면 왜 안 하기로
  했는지가 안 남습니다 — 그것도 전략의 일부입니다.
- 난제를 지워도 이슈는 남습니다(`SET NULL`). 딸려 지우면 사람이 쓴 것이 조용히
  사라집니다. 남은 이슈는 고아 구역으로 내려가 눈에 띕니다.
- **영향도·실행가능성은 비워둘 수 있습니다.** 진단 격자와 같은 이유입니다.

'발견 사항(findings)'은 여기서 다시 뽑지 않습니다. 그쪽은 진단 화면에서 한 번의
클릭으로 **핵심 난제**가 되는 길이 이미 있습니다. 같은 사실이 두 경로로 들어오면
목록에 중복이 쌓이고 어느 쪽이 정본인지 갈립니다.

        │  │  S 강점        W 약점          │  │  │ S  준비도 4단계     │
        │  └────────────────────────────────┘  │  │        [강점으로] │
        │  ┌ 포탈에 없는 정보입니다 ────────┐  │  │ W  성과 측정 2단계  │
        │  │  O 기회        T 위협          │  │  │        [약점으로] │
        │  └────────────────────────────────┘  │  └────────────────────┘
```

⚠️ **후보를 오른쪽 곁열로 옮겼습니다** (이슈 화면과 같은 구조). 바닥에 있으면
   이미 올린 것과 겹치는지 보려고 위아래로 오갑니다 — 「고르는 일」은 네 칸을
   **보면서** 해야 판단이 됩니다. 폭이 안 되면(1800px 미만) 지금까지처럼 바닥에
   붙고, 그때만 접힙니다.

⚠️ **여기서는 카드 전체가 표적이 아닙니다.** 이슈 쪽은 카드 전체가 「고르기」라
   표적을 넓혔지만, 여기는 누르는 즉시 요소가 생깁니다. 목록을 훑다가 잘못 눌러
   요소가 만들어지면 되돌리려면 지워야 합니다. 버튼만 누르는 자리입니다.

나머지 규칙(근거 있는 절반과 없는 절반을 선으로 가르는 것, 사업부 필터)은
`AnalysisView.jsx` 주석에 있습니다.

### ④ 솔루션 (구현 완료)

TOWS 네 갈래를 **바구니**로 둡니다. 솔루션을 적을 때 무엇과 무엇을 엮은 것인지를
고릅니다.

```
  ┌ SO 강점으로 기회를 잡는다 ──── 3건 ┐  ┌ WO 기회를 빌려 약점을 메운다 ─ 1건 ┐
  │ · 가상검증 범위를 신모델까지        │  │ · …                                │
  │   [S CAE 해석 역량] [O 생성형 AI]   │  │                                    │
  │ [+ 솔루션 추가]                        │  │ [+ 솔루션 추가]                        │
  └────────────────────────────────────┘  └────────────────────────────────────┘
  ┌ ST 강점으로 위협을 막는다 ─────────┐  ┌ WT 약점과 위협이 겹친다 ───────────┐
```

⚠️ **조합 격자를 그리지 않습니다.** 강점 5개 × 기회 5개면 25칸이고, 그걸 채우라고
   내밀면 이 모듈이 계속 피해 온 「격자 채우기」가 그대로 재현됩니다. 스물다섯 개의
   솔루션을 적을 조직은 없고, 억지로 채운 것은 읽히지 않습니다. 바구니는 **빈 칸이
   아니라 빈 목록**이라 채울 의무가 없습니다.

- **갈래마다 엮을 수 있는 요소가 정해져 있습니다.** SO 는 S·O 만입니다. 이름 자체가
  「무엇을 무엇으로 푸는가」라서, 거기에 위협을 엮으면 그 솔루션이 무엇을 푸는 것인지
  이름과 내용이 어긋납니다. 서버도 거절합니다(`TOWS_ELEMENTS`).
- **엮는 것을 강요하지 않습니다.** 근거를 대야만 저장되게 막으면 사람은 아무거나
  골라 붙이고, 그러면 근거란이 거짓말을 시작합니다. O·T 는 설문을 돌리기 전에는
  빌 수밖에 없기도 합니다.
- **요소를 지워도 솔루션은 남습니다.** 근거가 없어진 것이지 솔루션이 틀린 것은 아닙니다.
  화면은 못 찾는 요소를 조용히 뺍니다(난제와 이슈의 관계와 같은 규칙).
- 사업부 필터는 ③ 과 같습니다. 엮을 후보도 지금 보는 범위에 맞춥니다 — MX 를
  보면서 NW 의 약점을 엮으면 그 솔루션은 MX 화면에서 근거가 안 보입니다.

#### AX-5R 게이트 — 솔루션마다 다섯 질문

솔루션 하나를 적을 때마다 다섯을 묻습니다. 카드 아래 띠로 보이고, 누르면 다섯 칸이
열립니다.

```
  [✓ 준비도] [✓ 업무 정착] [─ 역할·책임] [✓ 리스크 관리] [─ 성과 측정]   3/5
```

⚠️ **같은 다섯 축인데 시제가 다릅니다.**

| | 묻는 것 |
|---|---|
| ① 진단의 조직 역량 | "지금 되어 있는가" — 조직의 현재 상태 |
| ④ 의 게이트 | "이 솔루션을 하면 어떻게 되는가" — 이 솔루션의 실행 조건 |

축 정의는 `definitions.ORGANIZATION_DIMENSIONS` **한 곳에서 끌어옵니다**(`GATES`).
질문 문장만 따로 둡니다 — 진단 문장을 그대로 쓰면 "준비도가 3단계"라는 답이
게이트에도 들어오고, 그건 이 솔루션에 대해 아무것도 말해주지 않습니다. 둘이 갈라지면
`assert` 가 임포트 시점에 터지고 테스트도 잡습니다.

- ⚠️ **막는 관문이 아닙니다.** 다섯을 다 채워야 저장되게 하면 사람은 아무 말이나
  적어 넣고, 그러면 게이트란 전체가 거짓말이 됩니다. 안 채워진 것은 세어서
  보여주기만 합니다.
- **답한 게이트만 행이 생깁니다.** 빈 다섯 줄을 미리 깔면 그 빈 줄이 "답했는데
  내용이 없는 것"과 구별되지 않습니다.
- **'해당 없음'도 이유를 적어야 합니다.** 이유 없는 해당 없음은 안 답한 것과
  구별이 안 되면서 화면에서는 다 채운 것처럼 보입니다.
- ⚠️ `strategy_gate.target_id` 에는 외래키가 없습니다(횡단이라 붙을 곳이 여럿).
  **대상을 지울 때 게이트도 같이 지웁니다** — 안 지우면 나중에 같은 번호를 받은
  다른 솔루션에 남의 답이 붙습니다. 테스트가 이것을 지킵니다.

#### 사분면 — 무엇부터 하는가

```
  ┌ 먼저 한다      영향 큼·할 만함 ┐ ┌ 준비해서 한다   영향 큼·어려움 ┐
  ┌ 틈틈이        영향 작음·할 만함 ┐ ┌ 하지 않는다   영향 작음·어려움 ┐

  아직 안 매긴 솔루션이 2건 있어 어느 칸에도 올라가지 않았습니다: …
```

`impact × feasibility` 는 이슈와 **같은 1~5 척도**입니다. 4 이상을 「큼·할 만함」
으로 보고, **그 규칙을 화면에 적습니다** — 어디서 갈렸는지 안 보이면 칸 배치가
임의로 읽힙니다. (이 값이 실제와 안 맞으면 임계값 설정으로 내릴 자리입니다.)

⚠️ **안 매긴 것을 0 으로 두지 않습니다.** 그러면 아직 판단하지 않은 솔루션이
「영향 작음 × 어려움」 칸으로 굴러떨어져 '하지 않는다'로 읽힙니다. 안 매긴 것은
칸 밖에 따로 세어 이름까지 적습니다. 진단 격자·이슈와 같은 규칙입니다.

「하지 않는다」도 칸으로 둡니다. 안 하기로 한 것도 판단이고, 그게 안 남으면 내년에
같은 것을 다시 검토합니다(이슈의 `dropped` 와 같은 이유).

#### 솔루션 → 과제 — 전략과 실행이 닫히는 자리

⚠️ **지표 연결만으로는 폐루프가 안 닫힙니다.** 「가상검증률을 올리겠다」는
겨냥이고, 그것을 **누가 무엇으로 하는가**는 과제입니다. 솔루션에 실제 과제
(`dt2_projects.uuid`)를 겁니다.

- 지표처럼 칩으로 다 펴 놓지 않고 **검색해서 고릅니다.** 검색어가 없으면 그
  전략 연도(+솔루션의 사업부)부터, 있으면 그 범위를 넘어 찾습니다 — 연도를
  걸치는 과제가 있어서입니다.

  > 규모는 **한 해 200여 건, 사업부별 30~100건**입니다(개발 DB 실측 2026-08-17:
  > 전체 436건 / 2025년 205 · 2026년 222 · 2027년 7 · 2028년 2). 다 펴 놓아도
  > 못 볼 양은 아니지만 바구니 하나가 화면을 덮고, 200줄을 훑는 것보다 그
  > 사업부 것부터 보는 편이 빠릅니다.
- **외래키를 걸지 않습니다.** 과제는 대시보드의 것이고 전략이 그 표의 수명을
  좌우해서는 안 됩니다. 과제가 지워지면 화면에서 조용히 빠지고 솔루션은
  남습니다 — 전략 요소와 같은 규칙입니다.
- ④ 화면이 **「해낼 과제가 안 걸린 솔루션 N건」**을 셉니다. 지표는 겨냥이고
  과제는 실행이라, 여기가 비면 그 솔루션은 아직 말뿐입니다.

**뒤집어 보는 쪽이 ① 진단에 들어갑니다** — 「어느 솔루션에도 안 걸린 과제」.
기존 「KPI 미연결 과제」와 **다른 것**을 봅니다.

| 규칙 | 무엇이 문제인가 |
|---|---|
| KPI 미연결 | 과제가 무엇을 올리려는지 안 적혔다 (과제 쪽) |
| 전략 미연결 | 전략이 그 과제를 자기 것이라 안 했다 (전략 쪽) |

⚠️ **과제를 나무라는 규칙이 아닙니다.** 비율이 높다고 현장이 잘못한 게 아니라,
전략이 현장에서 이미 벌어지는 일을 안 담은 것일 수 있습니다. 그리고 **솔루션이
하나도 없으면 안 짚습니다** — 전부 미연결이라 "아직 시작 안 했다"는 말밖에 안
됩니다. **합성 데이터에서도 안 짚습니다** — fixture 과제에는 uuid 가 없어 고를
수가 없고, 그러면 무조건 100% 가 나옵니다.

#### 「먼저 한다」가 몇 건까지인가

⚠️ **다 1순위면 순위를 안 정한 것과 같습니다.** 사분면은 무엇이 급한지 가르지만
조직이 한 해에 해내는 양은 못 봅니다. `solution_now_max`(기본 5건)를 넘으면
짚습니다 — 막지는 않습니다.

**지금 보는 범위로 셉니다.** 사업부를 골라 놓고 전사 숫자를 띄우면 화면에 세
건이 보이는데 "열두 건"이라고 말하는 꼴이 됩니다.

#### 솔루션 → KPI — 무엇을 겨냥하는가

솔루션을 지표(`kpi_definitions`)에 겁니다. **이름이 아니라 번호로** 겁니다 —
`kpi_records` 가 지표를 이름 문자열로 물고 있어 라벨이 바뀌면 조용히 끊기는
문제를 여기서까지 반복하지 않습니다.

여기까지 와야 ① 진단이 짚는 「KPI 에 안 걸린 과제」가 **반대편에서 닫힙니다.**
과제 쪽에서 "이 과제는 어느 지표에도 안 걸렸다"를 보던 것을, 전략 쪽에서 "이
지표를 움직이려는 솔루션이 없다"로도 볼 수 있게 됩니다.

`platform` 종류 지표도 목록에 냅니다. 달성률이 없을 뿐 전략이 겨누는 대상이기는
같아서, 빼면 시스템을 만드는 솔루션만 걸 곳이 없어집니다.

### ⑤ 기획서 (구현 완료)

```
  흐름도 │  [초안 — 앞 단계를 고치면 따라 바뀝니다]  [확정] [Word 내보내기]
        │  ┌──────────────────────────────────────────────┐
        │  │        2026년 디지털 트윈 전략 기획서         │
        │  │  1. 배경과 목적          [직접 작성]  [빼기]  │
        │  │  2. 현재 상태 진단       [자동 조립]  [빼기]  │
        │  │  4. 핵심 난제  ← 아직 비어 있습니다           │
        │  └──────────────────────────────────────────────┘
```

⚠️ **다시 적지 않습니다.** 진단·이슈·SWOT·솔루션은 이미 각 단계에 있습니다.
   문서가 그것을 옮겨 적게 하면 그 순간부터 둘이 갈라지고, 며칠 뒤에는 어느 쪽이
   맞는지 아무도 모릅니다. 본문을 **저장하지 않고** 볼 때마다 조립합니다
   (`document.assemble`). 사람이 쓰는 것은 어느 단계도 만들어 줄 수 없는
   것(배경·맺음말)뿐이고, 조립 구간에 글을 넣으려 하면 서버가 거절합니다.

⚠️ **화면과 문서가 같은 것을 봅니다.** `build_plan_payload()` 를 `get_plan` 과
   기획서가 함께 씁니다. 문서가 따로 계산하면 "화면에는 발견 사항 12건인데
   기획서에는 9건"인 날이 오고, 그때 어느 쪽이 맞는지 아무도 모릅니다. 조립
   결과도 **블록 목록 하나**라 화면 미리보기와 Word 가 같은 것을 그립니다.

⚠️ **빈 장을 감추지 않습니다.** 이슈가 없으면 그 장을 빼는 것이 문서로는
   깔끔하지만, 읽는 사람은 그 장이 없다는 것 자체를 모른 채 "검토했겠거니"
   합니다. 화면에도 문서에도 **「아직 비어 있습니다」로 찍힙니다.** 뺀 장도
   목차에는 남습니다 — 왜 빠졌는지 다음 사람이 알아야 합니다.

⚠️ **확정하면 굳습니다.** 평소에는 살아 있어서 진단을 고치면 문서도 따라
   바뀌지만, 「확정」하면 그 시점의 조립 결과를 통째로 복사해 둡니다
   (`strategy_document.snapshot`). 승인받은 기획서가 뒤에서 조용히 달라지면 그
   문서로 한 결정을 되짚을 수 없습니다 — `StrategyEvidence.snapshot` 과 같은
   이유입니다. 확정본은 못 고치고(409), 되돌리면 굳은 것을 버립니다.

⚠️ **초안임을 문서에 박습니다.** 확정 전에 내보낸 .docx 첫 장에 「초안 — 확정
   전입니다」가 찍힙니다. 초안이 승인본처럼 돌아다니는 것을 막는 방법은 문서
   자체가 그렇게 말하는 것뿐입니다.

#### 0. 한 장 요약 — 첫 장만 보는 사람을 위해

⚠️ **임원은 첫 장만 봅니다.** 본문을 다 읽게 만드는 문서는 안 읽힙니다. 넘으려는
것(핵심 난제 + 이슈 수) · 먼저 할 일(「먼저 한다」 칸 + 걸린 과제 수) ·
**아직 비어 있는 장**을 싣습니다.

⚠️ **요약도 조립입니다.** 손으로 쓰게 두면 본문과 갈라지고, 그때 갈라진 쪽은 늘
요약입니다.

⚠️ **비었다는 사실을 첫 장에 적습니다.** 문서로는 불편하지만, 안 적으면 읽는
사람은 그 장이 비었다는 걸 열 장 뒤에서야 알거나 끝내 모릅니다.

구현 주의: 요약은 **다른 장이 다 조립된 뒤에야** 쓸 수 있습니다(무엇이 비었는지가
내용이라서). `assemble()` 이 두 바퀴를 돕니다 — 한 바퀴로는 자기 자신을 세는
셈이 됩니다.

#### 로드맵은 날짜가 아니라 순서입니다

일정 데이터가 없습니다. 분기 격자를 그리면 그 칸을 채우는 것이 목적이 되고,
근거 없는 날짜가 문서에 박힙니다. 우리가 아는 것은 **무엇부터 하는가**(④
사분면)이므로 「먼저 한다 → 준비해서 한다 → 틈틈이」 순서만 적습니다. 날짜가
정말 필요해지면 솔루션에 시기를 받는 칸을 두는 것이 맞고, 그건 그때 정합니다.

#### 슬라이드가 아니라 문서입니다

Word(.docx)로 내보냅니다(`docx_writer.py`, python-docx). 난제·발견 사항·솔루션의
근거는 문장이라 슬라이드에 넣으면 글자만 빽빽한 장이 됩니다. 발표용이 필요하면
이 문서에서 추려 만드는 것이 맞습니다.

### ⑤ 이후 (예정)

```
  작업 영역                              │   근거 패널
  (방법론 정의에 따라 렌더링)             │   · 포탈 데이터
  교차검증 시 방법론 탭으로 전환          │   · 설문 결과   [설문 만들기]
                                        │   · AI 추천
  ─────────────────────────             │
  게이트: 준비도 업무정착 역할 리스크 성과 │
          ✓     ✓     ─    ✓     ─      │
```

- 근거 패널에 **포탈 데이터와 설문 결과가 나란히** 놓입니다.
- 하단 게이트 표시줄이 미충족 항목을 항상 노출합니다.

관리자 전용으로 **프롬프트·방법론 편집 화면**이 따로 필요합니다. 운영에서 튜닝하기
위한 것이므로 AI 단계와 함께 들어갑니다.

### 접근 권한 (확정)

**조회는 로그인한 모두, 편집은 매니저 이상**입니다.

| | 역할 | 무엇을 하나 |
|---|---|---|
| 편집 | 관리자(100) · 사무국(70) · 매니저(50) | 전부 |
| 조회 | 사용자(20) · 뷰어(10) | 읽기 · 사업부 필터 · 기획서 Word 내보내기 |

⚠️ **한동안 전 화면이 사무국 전용이었습니다.** 그러면 사업부장이 자기 사업부
   진단조차 못 보고, 전략은 「사무국이 만든 남의 문서」가 됩니다 — 정작 실행할
   조직이 안 읽습니다. 설문으로 의견은 받으면서 결과는 안 보여주는 구조이기도
   했습니다.

⚠️ **화면에서 단추를 감추는 것은 방어가 아닙니다.** 방어선은 라우트의
   `edit_required` 이고, `meta.canEdit` 은 단추를 감추는 편의일 뿐입니다.
   화면 쪽은 하나쯤 빠뜨리기 마련이라 `runAndReload` 에서도 한 번 더 막습니다 —
   서버도 막지만 그건 403 이고, 사람에게는 이쪽 문구가 더 친절합니다.

⚠️ **서술형 설문 요약만은 편집 권한자 전용입니다.** 응답자에게 「관리자는 확인
   가능」이라고 고지하고 받은 답변이지 「전 직원이 확인 가능」이라고 하지
   않았습니다. 원문 인용을 읽고 감사 로그에도 남습니다. 사업부별 **집계**는
   표본 하한(`survey_min_sample`)을 넘은 것만 나오므로 모두에게 보입니다 —
   설문 결과를 조직에 돌려주는 것이 원래 정상입니다.

```javascript
// MainPage.jsx 모듈 카드
allowedRoles: ['admin', 'dt_office']
```

- 홈 화면에서 **카드는 모두에게 보이고, 누를 때 거부됩니다**
  ("⚠️ 접근 권한이 없습니다" 토스트). 이 포탈의 기존 방식이고 그대로 따릅니다.

  > 이전 판에 "해당 역할이 아니면 카드 자체가 보이지 않습니다"라고 적혀
  > 있었는데 **틀린 서술이었습니다**(2026-08-15 확인). `MainPage.jsx` 의
  > `filtered` 는 검색어·상태·역할필터로만 거르고 `allowedRoles` 는 보지
  > 않습니다. 권한 검사는 `onOpen` 에만 있습니다.

- 백엔드 API도 같은 기준으로 막습니다. **화면만 가리면 URL 직접 접근으로
  뚫립니다** — 카드가 보이든 안 보이든 이건 별개로 반드시 필요합니다
- **설문 응답자는 예외**입니다. 설문은 전사 대상이므로 응답 화면은 **별도 모듈**
  (`/survey`, 전원 공개 카드)로 엽니다 — 전략 산출물은 못 보고 자기가 받은
  설문만 봅니다. [SURVEY_PLAN.md](./SURVEY_PLAN.md) 2절

> 나중에 열람 범위를 넓힐 때는 **확정된 전략만 전사 공개**하고 작업 중인 초안은
> 계속 비공개로 두는 방식이 자연스럽습니다. 지금 구조로 그대로 확장됩니다.

## 9. 구현 순서

각 단계는 **그 자체로 쓸 수 있는 상태**로 끝냅니다.

데이터 반출이 없으므로 **의미 있는 검증은 전부 운영에서** 일어납니다. 각 Phase는
운영에 배포해 확인할 수 있는 단위로 끊습니다.

### ✅ Phase 1 — 뼈대 + ① 진단 (완료)
- 백엔드 모듈 `backend/app/modules/digital_twin_strategy/`
- `strategy_plan` · `strategy_assessment` · `strategy_metric_target` ·
  `strategy_crux` · `strategy_evidence`
- **EvidenceSource 계층** + `FixtureSource`, 합성 데이터 경고 띠
- 진단 3층: 기술 성숙도(사업부×5) · 조직 역량(사업부×5) · 활용과 성과(자동 산출)
- **구조적 발견 규칙 13종**, 핵심 난제 CRUD, 임계값 설정 화면
- 연도별 전략 생성

계획과 달라진 점: 진단의 산출물을 점수 격자가 아니라 **핵심 난제**로 바꿨고,
격자는 접어서 선택 사항으로 내렸습니다. 이유는 1·8절.

### ✅ Phase 2 — 근거 연결 (완료)
- `LocalDbSource` — `dt2_projects` 및 연결 표(성과·KPI·선행)에서 읽음
- KPI 목표/실적은 `kpi_targets` × `kpi_records` 를 (사업부, 지표)로 맞춤
- 지표 쪽에서 뒤집어 보는 `compute_kpi_coverage`

**스키마 검증은 개발 DB 로 마쳤습니다.** 운영 배포를 기다릴 필요가 없었던 이유는
개발 DB 에 시드 데이터가 들어 있어 표 구조가 실물과 같았기 때문입니다.

⚠️ 다만 **그 데이터는 시드라 내용은 현실이 아닙니다.** 임계값 감을 잡으려면
운영에서 `STRATEGY_EVIDENCE_SOURCE=local` 로 한 번 봐야 합니다.

### ✅ Phase 3 — ② 이슈 (완료)
- `strategy_issue` — 난제에 매다는 구조, `SET NULL` 로 고아를 남김
- 진단 격차(성숙도·지표)에서 **이슈 후보** 도출 (`issues.py`)
- 이슈가 없는 난제 / 난제 없는 이슈를 화면이 항상 드러냄
- `dropped` 로 "올해는 안 한다"를 판단의 기록으로 남김

계획을 앞당긴 것입니다. 원래 설문 다음이었는데, 핵심 난제가 갈 곳이 없는 것이
가장 큰 빈틈이었습니다. **이제 진단부터 이슈까지 한 사이클이 설문·AI 없이 돕니다.**

방법론 엔진(DB 정의 + 관리자 편집)은 여기 넣지 않았습니다. 이슈는 트리 하나면
되고, 정의를 데이터로 두는 구조는 ③ 분석부터 실제로 필요합니다.

## 9-1. 한 사이클을 실제로 돌려 본 것 (2026-08-17)

배포 전에 개발 DB 에서 **① 진단부터 ⑤ Word 까지 한 번 끝까지** 채워 봤습니다.
근거는 `local`(시드 과제 436건), 화면이 부르는 API 만 썼습니다.

**돌긴 돌았습니다** — 막힌 데 없이 Word 44KB(206문단·표 4개)까지 나왔고,
「먼저 할 일 · SO · 영향 4 × 실행 4 · 과제 2건」처럼 회의에 들고 갈 만한 줄이
요약 장에 찍혔습니다. 전략 미연결 규칙도 실제로 잡았습니다.

**그런데 기획서 첫 장이 이랬습니다.**

```
【넘으려는 것】
 · NW 과제 55.0% 가 성과를 정의하지 않았습니다      이슈 없음
 · DA 과제의 72.2% 를 DA1팀이 맡고 있습니다        이슈 없음
 · test                                       이슈 4건
```

찾은 것과 고친 것:

| 무엇 | 왜 | 고침 |
|---|---|---|
| 난제 10개 중 8개가 **관측 문장 그대로** | 「핵심 난제로」가 제목을 복사했다. 관측은 할 일이 안 나와 이슈 0건으로 남는다 | `PromoteCrux` — **제목을 다시 쓰게** 하고 원문은 근거로 내린다. 서술형 요약(AI 제목)도 같은 길로 |
| 진단 31칸을 채워도 **이슈 후보가 0건** | `GAP_MIN=2` 인데 사람은 목표를 「올해 한 단계」로 잡는다 → 격차가 늘 1 | `issue_gap_min` 임계값(기본 **1**). 격차 후보 0 → 31건 |
| **강점 후보 0건** | 기준이 5단계로 저장돼 있고 진단 최고가 4단계 — 아무리 기다려도 안 나오는 상태인데 화면은 그냥 비어 있었다 | `elementSummary` 가 기준·최고/최저 레벨을 실어 보내고, 화면이 **「기준이 5단계인데 진단 최고가 4단계입니다」** 라고 말한다 |
| 전략 미연결 발견 사항 제목에 **사업부가 없음** | 「과제 21건(100%)이…」가 사업부 수만큼 똑같이 뜬다 | 제목에 사업부를 넣는다 |

⚠️ **셋째 것은 코드가 아니라 설정 문제였습니다.** 그래서 고친 것도 규칙이
아니라 **「왜 없는지 말하는 것」**입니다. 마침 ⚙ 미리보기가 같은 것을 숫자로
보여줍니다 — `element_strong_at: 4→45 5→40`.

### 걸으면서 더 나온 것 (같이 고침)

| 무엇 | 고침 |
|---|---|
| 이슈 후보 31건이 **전부 격차 1** 이라 순서가 없음 | **여러 사업부가 같이 낮은 축**을 위로. 무게 = 사업부 수 + 격차/10. 카드에 「사업부 5곳」 배지 |
| 진단 첫 채움이 **클릭 100번** | 「목표를 전부 한 단계 위로」. **현재 수준은 안 건드리고** 목표가 빈 칸만 채운다 |
| 발견 사항 35건 중 다섯 줄이 **사업부만 다르고 문장이 같음** | 규칙별로 묶는다(`RULE_LABELS`). 화면은 2건 이상만 접을 수 있게 하되 **기본은 펼침**, 문서는 접을 수 없으니 **묶고 건수를 적는다** |
| 탭이 진행을 안 보여줌 | `① 진단 50/50` `④ 솔루션 5` `⑤ 기획서 초안`. **비면 노란색** |
| 잘못 올린 난제를 **지우는 수밖에 없음** | **난제 → 이슈 강등**(`cruxes/<id>/demote`). 딸린 이슈도 같이 옮긴다 — 안 옮기면 정리하려다 고아를 만든다 |
| 요소가 늘면 ④ 엮기가 무너짐 | 종류별 8개 넘으면 **검색창**(서버에 안 묻는다 — 이미 화면에 있다). **고른 것은 검색어와 무관하게 늘 보인다** |

⚠️ `RULE_LABELS` 에는 **assert 를 안 걸었습니다.** 규칙을 새로 넣을 때 이름
적는 걸 잊어도 화면이 깨지면 안 됩니다 — 이름이 없으면 그 묶음의 첫 제목을
씁니다.

⚠️ **이 절이 남아 있는 이유**는 다음에 큰 것을 붙일 때도 **한 번 끝까지 걸어
보라는 것**입니다. 테스트 186건이 다 통과하는 상태에서 나온 문제들입니다.

## 10. 위험

**형식만 남는 것.** 칸 채우기가 목적이 되면 아무도 안 씁니다.
→ 각 단계에서 채웠을 때의 **즉각적 이득**이 보여야 합니다. 진단을 채우면 이슈 후보가
자동으로 뜨고, 이슈에 근거를 붙이면 분석 요소가 추천되는 식.

**AI 초안이 그럴듯해서 검토가 형해화.**
→ 근거 없는 문장 시각 구분 + 확정 시 경고. 교차검증 분기점은 특히 사람이 봐야 합니다.

**합성 데이터로 만든 산출물이 진짜로 오인되는 것.**
→ `fixture` 모드는 화면 상단에 상시 경고 띠. 근거마다 `source_mode` 기록.
개발 환경 전략은 애초에 별도 DB이므로 섞이지 않지만, 화면에서도 분명해야 합니다.

**커넥터가 실제 스키마와 안 맞는 것.** → **해소됨.** 개발 DB 에 시드 데이터가 있어
표 구조가 실물과 같았고, `LocalDbSource` 를 그것으로 검증했습니다.

**시드 데이터를 실제 데이터로 착각하는 것.** ← 실제로 한 번 겪었습니다.
개발 DB 값으로 "규칙 두 개가 쓸모없다"고 판단했는데, 그 값들은 시드가 만든 것이라
현실을 말해주지 않았습니다. `dt3_seed_*.py` 는 **운영에서 돌리지 말라고 명시된
개발 전용 스크립트**입니다.
→ 개발 DB 숫자로 규칙의 유용성을 판단하지 않습니다. 판단은 운영에서 합니다.

**임계값이 실제와 안 맞는 것.**
→ 설정 화면에서 조정합니다(4절). 기본값과 다른 항목만 저장하므로, 배포로 기본값이
개선되면 손대지 않은 항목은 새 값을 따라갑니다.

**같은 기준이 두 곳에 있는 것.** ← 실제로 겪었습니다.
관측 표의 색이 코드에 박힌 숫자를 쓰고 있어, 설정에서 기준을 바꿔도 색은 안 따라
갔습니다. 발견 사항에서는 사라졌는데 칸은 계속 붉은 상태였습니다.
→ 기준은 한 곳(`THRESHOLDS`)에만 두고 짝은 `METRIC_THRESHOLD_KEY` 로 명시합니다.
새 지표를 넣고 짝을 잊으면 `assert` 가 임포트 시점에 터집니다(4절).

**설정이 배선되지 않는 것.** ← 실제로 겪었습니다.
`STRATEGY_EVIDENCE_SOURCE` 를 읽는 코드는 있는데 `app/config.py` 에 그 키가 없어
**운영에 배포하고 `.env` 를 넣어도 합성 데이터가 나올 상태**였습니다. Flask 는
환경변수를 자동으로 가져오지 않습니다.
→ 안전장치는 화면 상단의 합성 데이터 경고 띠입니다. **운영에서 그 띠가 보이면
설정이 안 먹은 것**이니 그때 알아챌 수 있습니다. 새 설정을 넣을 때는 config 에
키를 등록했는지 반드시 확인합니다.

**AI 품질을 개발에서 알 수 없는 것.**
→ 프롬프트를 DB에 두어 운영에서 즉시 고칩니다. 채택/거부 집계로 어느 기능이 쓸
만한지 판단합니다. 배포 없이 반복할 수 있어야 이 구조가 성립합니다.

**설문 피로.**
→ 단계별 최소 문항, 같은 대상 연속 배포 방지.

**LLM 응답 시간.** `LLM_TIMEOUT=120`. 긴 작업은 비동기로.
