# 설문 → 진단 연결 계획

작성 2026-08-16. 관련 문서: [SURVEY_PLAN.md](./SURVEY_PLAN.md), [PLAN.md](./PLAN.md)

설문 문항에 `link_key = 'organization:readiness'` 가 저장되고 있지만 **읽는
코드가 없습니다.** 화면은 「진단 연결」이라는 꼬리표까지 달아 보여주는데
실제로는 아무 데도 연결되지 않습니다. 그 약속을 지키는 것이 이 작업입니다.

---

## 1. 이미 자리가 잡혀 있는 것

연결이 들어갈 홈은 설계 단계에서 이미 뚫려 있습니다. 새 표를 만들 필요가
없습니다.

```
StrategyAssessment
    plan_id, division_id
    category      'organization'          ← 조직 역량
    dimension     readiness / redesign / role / risk / return
    current_level 1~5
    target_level  1~5
    basis         auto | survey | manual  ← 'survey' 가 이미 있다
    note
    UNIQUE (plan_id, division_id, category, dimension)
```

조직 축 5개는 전부 `survey_recommended: True` 로 정의돼 있습니다
(`definitions.py`). 즉 **설문으로 채우라고 만들어 둔 자리**입니다.

설문 쪽도 갖춰져 있습니다.

| 있는 것 | 값 |
|---|---|
| 문항의 연결 | `link_type='strategy_dimension'`, `link_key='organization:readiness'` |
| 설문의 소속 | `context_type='strategy_plan'`, `context_id=<plan.id>` |
| 응답의 사업부 | `division_id` (계정에서 유도, 자칭 불가) |
| 응답의 역할 | `respondent_role` + `role_source` |
| 집계 | `compute_results()` — 문항별 평균·분포, 사업부별 |

**연결에 필요한 데이터는 전부 이미 쌓이고 있습니다.** 없는 것은 읽는 쪽뿐입니다.

---

## 2. 먼저 고쳐야 하는 것 (0단계) — **완료 2026-08-16**

연결을 만들기 전에 **연결키가 제대로 저장되는지**부터 고쳐야 합니다. 지금은
두 군데가 새고 있습니다.

### 2-1. 연결키를 손으로 타이핑한다

표의 `연결키` 열에 사람이 `organization:readiness` 를 직접 적습니다. 오타
하나면 조용히 안 붙고, 그 사실은 **진단을 만들 때가 되어서야** 드러납니다.

역할·프로세스를 목록에서만 고르게 한 것과 **완전히 같은 문제**입니다. 같은
방식으로 고칩니다 — 서버의 `/options` 가 축 목록을 실어 주고, 편집기는
드롭다운으로, 표는 아는 값인지 검증합니다.

```
GET /api/surveys/manage/options
  + link_keys: [
      {key: 'organization:readiness', label: '조직 역량 · 준비도',
       question: '할 수 있는 여건이 되는가'},
      ... 5개
    ]
```

⚠️ 설문 모듈이 전략 모듈의 정의를 **import 하지 않습니다.** 그러면 설문이 다시
전략에 매입니다. `try/except` 로 읽어 오되, 못 읽으면 빈 목록을 주고 연결
기능만 조용히 빠집니다 — 설문 자체는 전략 없이도 돌아야 합니다.

### 2-2. `link_type` 이 전부 아니면 전무다

`SurveyImport.jsx` 가 **표 전체**를 보고 판단합니다.

```js
const linkType = linkKeys.every(k => k.startsWith('organization:'))
  ? STRATEGY_DIMENSION_LINK : null;
```

연결키 10개 중 **하나가 오타면 10개 전부** 연결이 NULL 로 저장되고, 화면은
아무 말도 안 합니다. 2-1 을 하면 오타 자체가 막히므로 이 판정은 **행 단위로**
내려가면 됩니다(`rows_to_questions` 가 이미 행마다 `link_key` 유무를 봅니다).

## 3. 설문은 근거지 결론이 아니다

**이 계획에서 가장 중요한 결정입니다.**

설문 평균이 3.4 라고 해서 그 사업부의 준비도가 자동으로 3 이 되지는 않습니다.

- 조직 레벨은 **서술로 정의된 단계**입니다 — '개인 차원', '부서 표준' 같은.
  1~5 응답의 평균을 반올림한 것과 뜻이 같지 않습니다.
- 사업부마다 응답자 수가 크게 다릅니다. 3명이 답한 사업부와 40명이 답한
  사업부의 평균을 같은 무게로 쓸 수 없습니다.
- 사무국이 이미 손으로 매겨 둔 값이 있을 수 있습니다. **조용히 덮어쓰면**
  왜 숫자가 바뀌었는지 아무도 설명하지 못합니다.

그래서 **자동으로 반영하지 않습니다.**

```
설문 집계  →  제안값(suggested_level) + 표본 수 + 근거
                    ↓  사람이 보고 「반영」을 누른다
              current_level, basis='survey', note 에 근거 스탬프
```

제안값을 만드는 값어치는 그대로입니다 — **모든 사업부가 같은 방식으로**
계산되고, 표본 수가 항상 숫자 옆에 붙고, 사무국이 자기가 매긴 값과 나란히
놓고 볼 수 있습니다.

## 4. 어떻게 숫자를 만드는가

### 4-1. 1인 1표

한 응답자의 **그 축 문항 평균**을 먼저 내고, 그 사람 값들을 다시 평균 냅니다.

```
사람A: readiness 문항 3개 → (4+3+4)/3 = 3.67
사람B: readiness 문항 1개 → 3.00
축 평균 = (3.67 + 3.00) / 2 = 3.34
```

⚠️ **답 단위로 그냥 평균 내면 안 됩니다.** 이 설문은 역할마다 문항 수가 다른
것이 설계입니다 — PL 에게 5문항, 참여인력에게 1문항을 묻는 축이 나옵니다.
답 단위로 세면 PL 한 사람이 참여인력 다섯 사람만큼 셉니다. 그건 집계가 아니라
설계의 부작용입니다.

### 4-2. 척도 문항만 레벨에 들어간다

객관식·순위·서술형은 **레벨을 만들지 않습니다.** 1~5 로 환산할 방법이 없고,
억지로 매기면 그 매핑을 아무도 설명하지 못합니다.

대신 근거 패널에 **그대로** 붙습니다. "왜 3인가"에 답하는 것은 오히려 서술형과
선택지 분포입니다.

### 4-3. 표본이 모자라면 제안하지 않는다

`N < min_sample`(기본 5) 이면 제안값을 비우고 **"표본 부족 (N=2, 최소 5)"** 을
그 자리에 씁니다.

두 가지를 동시에 막습니다 — 세 명의 의견이 사업부의 진단이 되는 것과, 사업부별
칸의 표본이 한둘로 내려가 **익명이라던 응답이 사실상 지목이 되는 것.**

임계값은 전략 모듈이 이미 쓰는 `ModuleSettings` 에 둡니다(임계값을 코드에
박지 않는 기존 방식 그대로).

### 4-4. 마감된 설문만, 그리고 **설문을 섞지 않는다**

진행 중인 설문을 반영하면 사람이 답할 때마다 진단이 움직입니다. 어제 본 숫자와
오늘 숫자가 다른데 아무도 왜인지 모릅니다. `status='closed'` 인 설문만
근거가 됩니다.

⚠️ **여러 설문의 같은 축을 한 평균으로 뭉치지 않습니다.** 「과제 애로사항
조사」의 준비도 문항과 「조직 역량 진단」의 준비도 문항은 같은 축을 가리켜도
묻는 맥락이 다릅니다 — 앞뒤 문항이 다르고 응답자 집단이 다르면 답이 달라집니다.
합쳐 놓으면 숫자는 나오는데 **그게 무엇의 평균인지 아무도 말할 수 없습니다.**

그래서 **설문별로 갈라서** 냅니다.

```
조직 역량 · 준비도        MX 사업부
  ├ 조직 역량 진단(3월 마감)      3.2   N=22   ← 이걸로 반영
  └ 과제 애로사항 조사(5월 마감)   2.8   N=9
```

반영은 **설문 하나를 골라서** 합니다. 두 설문의 숫자가 벌어져 있다면 그 사실
자체가 볼 만한 것이고, 평균을 내서 3.0 으로 만들면 그 정보가 사라집니다.

한 설문 안에서는 합칩니다 — 그건 같은 맥락에서 같은 사람들에게 물은 것이라
문항 여러 개가 한 축을 재는 것이 정상입니다(4-1 의 1인 1표).

**어느 설문을 볼 것인가**는 `context_type='strategy_plan'`, `context_id=plan.id`
로 좁힙니다. 그 전략에 매달아 만든 설문만 후보가 됩니다 — 설문 모듈은
전사용이라, 전략과 무관한 설문까지 후보에 올리면 목록이 금세 못 쓰게 됩니다.

⚠️ 다만 **꼬리표가 곧 후보 자격입니다.** 그 설문에 `link_key` 가 달린 척도
문항이 하나도 없으면 애초에 목록에 안 나옵니다. 설문 종류로 거르는 것이 아니라
**문항에 달린 꼬리표로** 거릅니다.

### 4-5. 목표 레벨은 설문으로 정하지 않는다

설문은 **현재 상태**를 묻습니다. `target_level` 은 사무국이 정하는 의지이지
관찰이 아닙니다. 이 연결은 `current_level` 만 건드립니다.

---

## 5. 진단 대상 밖 응답을 버리지 않는다

진단은 `is_kpi_owner=True` 인 사업부만 합니다(GTR·SR·CS 는 기능조직이라 제외).
그런데 **설문은 전사가 답합니다.**

그 응답들은 어느 진단 칸에도 안 들어갑니다. 그냥 빠지게 두면 "답했는데 아무
데도 안 잡힌" 사람이 생기고, 응답 수 합계가 진단의 표본 합과 안 맞는데 화면
어디에도 그 이유가 없습니다.

→ **「진단 대상 밖 N건」을 따로 셉니다.** 「소속 미확인」을 따로 세는 것과 같은
이유입니다. 그 응답들도 집계 화면과 원자료에는 그대로 남습니다.

---

## 6. 화면 — 숫자보다 근거가 먼저다

진단 화면의 조직 역량 칸에서:

```
준비도   현재 3   목표 4        [조직 역량 진단 · 3.3 → 3]  N=18
                                └ 누르면 근거 패널
                                  (같은 축에 설문이 둘 이상이면 나란히 뜬다)
```

근거 패널에 들어가는 것:

- **어느 설문의 어느 문항**이 이 숫자를 만들었나 (문항별 응답 수)
- 1인 1표 평균과 **분포**
- **역할별 차이** — PL 2.8 / 참여인력 3.6 처럼 갈리면 그 자체가 발견이다
- 같은 축의 **객관식 분포와 서술형 원문** 몇 건
- **「반영」 버튼** — 누르면 `current_level` 이 바뀌고 `basis='survey'`

⚠️ **덮어쓰기 전에 기존 값을 `note` 에 남깁니다.** "2026-08-16 설문 반영: 4 →
3 (이전 값은 수기 4)". 남기지 않으면 나중에 "왜 3이지?" 에 답할 수 없습니다.

25칸(5사업부 × 5축)을 하나씩 누르는 것은 고역이므로 **「전부 반영」**도 둡니다.
다만 표본 부족 칸과 **이미 사람이 손으로 매긴 칸은 건너뛰고**, 몇 개를
건너뛰었는지 말해 줍니다.

## 7. API

```
GET  /api/digital-twin-strategy/plans/<year>/survey-evidence
     → { surveys: [{id, title, closed_at, response_count}],  ← 후보 설문
         min_sample: 5,
         cells: [{ survey_id,                   ← **설문마다 한 줄**
                   division_id, dimension,
                   respondent_count, average, suggested_level,
                   current_level, basis,        ← 지금 진단값 (비교용)
                   questions: [...], by_role: {...},
                   insufficient: false }],
         out_of_scope: [{division_id, name, respondent_count}] }

POST /api/digital-twin-strategy/plans/<year>/assessments/apply-survey
     { cells: [{survey_id, division_id, dimension}, ...] }   ← 어느 설문인지 명시
     → 반영된 칸과 건너뛴 칸(사유 포함)
```

⚠️ 읽기(`survey-evidence`)와 쓰기(`apply-survey`)를 **가릅니다.** 한 엔드포인트가
보여주면서 저장하면, 화면을 열어 본 것만으로 진단이 바뀝니다.

집계 자체는 설문 모듈의 `compute_results()` 를 씁니다. 전략 모듈이 응답을 직접
세면 화면의 숫자와 진단의 숫자가 갈립니다.

## 8. 순서

| 단계 | 내용 | 크기 |
|---|---|---|
| **0** | 연결키 목록화 + `link_type` 행 단위 판정 | **완료** |
| **1** | `survey-evidence` 집계 (1인 1표, 표본 하한, 대상 밖 분리) | 중간 |
| **2** | 진단 화면 근거 패널 + 제안값 표시 | 중간 |
| **3** | `apply-survey` 반영 + `note` 스탬프 + 「전부 반영」 | 작음 |
| **4** | (선택) 설문에서 나온 낮은 축을 이슈 후보로 | 나중 |

**0단계는 끝났습니다**(2026-08-16). 연결키는 편집기에서 목록으로 고르고, 표는
모르는 키를 **몇 번 문항인지 짚어** 거절하며, 종류는 서버가 키마다 따로
정합니다. 이제 표를 넣어도 연결이 비거나 틀린 채로 쌓이지 않습니다.

1~3단계는 **운영에 설문이 한 번 돌고 난 뒤**가 맞습니다. 응답이 없으면 화면을
만들어도 빈 칸만 보이고, 무엇이 어색한지 알 수 없습니다.

## 9. 위험

| 위험 | 대응 |
|---|---|
| 평균 3.4 를 "레벨 3" 이라 부르는 순간 정밀해 보인다 | 평균과 제안 레벨을 **같이** 표시. 반올림했다는 사실을 숨기지 않는다 |
| 응답률이 낮은 사업부가 낮은 점수로 보인다 | 표본 수를 숫자 옆에 항상 붙인다. 하한 미만은 제안 자체를 안 한다 |
| 설문이 진단의 유일한 근거가 된다 | 조직 축만 설문이다. 기술 성숙도(A)와 활용·성과(B)는 그대로 |
| 한 번 반영하고 나면 근거를 못 찾는다 | `note` 스탬프 + 근거 패널이 **항상** 원 설문으로 되짚어 간다 |
| 사람이 매긴 값을 설문이 덮어쓴다 | 「전부 반영」은 수기 칸을 건너뛴다. 개별 반영은 이전 값을 남긴다 |
| 맥락이 다른 설문이 한 숫자로 뭉쳐진다 | 설문별로 갈라서 보여주고, 반영은 **설문 하나를 골라서** 한다 (4-4) |
