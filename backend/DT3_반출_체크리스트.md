### 20 — 상태 코드가 **전부 400 으로 나가고 있었다**
`error_response(message, errors=None, status_code=400)` 인데 호출부가
`error_response(msg, 403)` 처럼 **위치 인자**로 줘서, 403·404·500 이 전부 `errors` 에
들어가고 HTTP 는 400 이 됐다. `digital_twin_dashboard/routes.py` **115건**을
`status_code=` 로 바로잡았다.

⚠️ **그중 하나는 200 을 내보내고 있었다.** 버전 충돌(`PUT /data`)이
`error_response(msg, 409, {conflict…})` 라 dict 가 status_code 자리에 들어갔고,
Flask 는 dict 를 **헤더**로 해석한다 → **HTTP 200 + 충돌 정보가 헤더로 유출**.
화면의 `if (response.ok)` 가 **버전 충돌을 성공으로 처리**하고 있었다.
V1 전체 업로드 경로라 컷오버 후 주 경로는 아니지만, V2 가 503 일 때 폴백으로 살아 있다.

> **아직 안 고친 같은 패턴 71건** — 상세와 판단은 §7 참조.
> `auth` 의 20건은 **로그인 경로가 아니다**(401 은 0건, 공지사항·통계·접속이력이다).

### 21 — 탭으로 뺐다. 연결률을 지켜볼 것
원래 **기본정보 탭**에 있었다. 그 탭은 모두가 열기 때문에 연결이 저절로 쌓였다.
탭으로 빼면 **안 여는 사람은 영영 안 연다** — 그래서 탭에 **연결 건수 배지**를 달았다
(열지 않아도 몇 개 걸려 있는지는 보인다).

동작은 그대로다. `ModalLayout.jsx:621` 이 **비활성 탭도 마운트를 유지**하므로,
탭을 열지 않아도 KPI 목록을 서버에서 불러오고 저장 시 변경 판정도 전과 같이 돈다.

같이 지운 문구 — 플랫폼 구축 박스의
"이 과제가 지표를 올리는 게 아니라 플랫폼·시스템을 만드는 일이라면 여기를 고르세요.
목표·실적으로 측정하지 않습니다." (소제목과 보라색 박스는 그대로라 구분은 남는다)

### 22 — DB 는 원래 됐고 **화면만 막고 있었다**
`dt2_project_kpi` 는 처음부터 `(과제, 지표, 대상사업부)` 단위다(유니크 제약도 셋).
모델 주석에도 "대상까지 포함해야 GTR 과제가 MX 와 VD 를 동시에 지원 이 표현된다" 고
적혀 있다. 그런데 화면이 지표를 체크할 때 **고른 대상 전부에 곱해서** 걸었다
(`KpiLinkSection.jsx` `toggleKpi`) — 대상 2 × 지표 3 이면 무조건 6줄.
개발서버 실측으로 **지표별로 대상이 다른 과제는 0건**이었다(만들 방법이 없었다).

**흔한 경우는 그대로 둔다.** 지표를 체크하면 여전히 고른 대상 전부에 걸린다.
거기서 **빼는 예외만** 만들 수 있게 했다 — 대상이 **2개 이상일 때만** 지표 줄에
작은 대상 칩이 나오고, 끄면 그 (지표, 대상) 한 줄만 사라진다(끈 것은 취소선).
마지막 하나까지 끄면 지표 자체를 뗀 것으로 본다. 서버·DB·마이그레이션 변경 없음.

⚠️ **매트릭스 숫자가 줄 수 있다.** `kpi_matrix` 는 (지표 × 사업부) 셀로 집계하는데,
   이제 기능조직 과제가 **실제로 기여하는 칸에만** 찍힌다. 전에는 곱집합이라
   기여하지 않는 칸에도 걸려 있었다 — 줄어든 값이 사실에 가깝다.

### 15 의 제약 — 공지에 넣을 것
- 복구해도 **과제 연결은 안 돌아온다** (삭제 시 연결 행을 지우기 때문). 다시 연결해야 한다
- 복구는 **관리자 또는 그 성과를 만든 사람만** 가능 (연결이 끊겨 '담당 과제' 로 판단할 수 없다)
- 완전 삭제는 **관리자만**, **휴지통에 있는 것만**, 되돌릴 수 없다 (행은 이력 때문에 남긴다)

      > 서버 파생 규칙은 **세부항목(액티비티) → 상위 액션아이템** 이다. 그런데 운영의
      > 일정·완료 **보고가 상위 액션아이템 완료일 기준으로 이미 나갔다.** 그대로 돌리면
      > 그 날짜가 세부항목 기준으로 덮여 **이미 보고한 숫자와 어긋난다**

      >
      > 그래서 **상위 완료일을 정본으로 두고 세부항목을 맞추는** 역방향 도구를 쓴다.

      ```
      :: ① 상위 완료일을 지키며 세부항목 날짜를 맞춘다
      set PYTHONIOENCODING=utf-8
      python scripts\dt3_align_subitems_to_action.py            :: 조사
      python scripts\dt3_align_subitems_to_action.py --commit   :: 반영

      :: ② 재조사 — date-earlier / date-later 가 사라져야 한다
      python scripts\dt3_backfill_action_items.py

      :: ③ 남은 표기 정리(None → '' · 화면 동일)만 마무리
      python scripts\dt3_backfill_action_items.py --only date-null --commit
      ```

      · ②에서 `date-earlier`·`date-later` 가 **남아 있으면 ③으로 넘어가지 말 것.**
        정렬이 못 맞춘 건이 있다는 뜻이다.
      · `건드리지 않은 과제 N건`(액션아이템 0건)은 **계속 남는 것이 정상**이다 —
        맞출 정본이 없어 진행률을 손대지 않는다. 손대면 그 과제들의 진행률이 0 이 된다.
      · 2026-08-07 운영 실적: 정렬 33건(당김 27 · 밈 44) → 표기정리 30건(59항목) → 0건.

      ⚠️ **앞으로 새로 입력되는 것은 여전히 세부항목이 정본이다.** 이 역방향 정렬은
         **과거 데이터를 한 번 맞추는** 것이고, 나중에 누가 그 과제의 세부항목 날짜를
         고치면 상위 완료일은 다시 세부 기준으로 계산된다. 규칙 자체를 바꾸려면
         별도 논의가 필요하다.
