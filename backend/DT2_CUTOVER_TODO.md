### ⚠️ 설정 화면에서 확인할 것 — 이름 변경 파급이 V2 에서 끊긴다 (코드상 확인, 클릭 확인 필요)

설정 자체는 컷오버와 **무관하다.** `PUT /digital-twin-dashboard/settings` 는 `Division` ·
`Department` · `ProcessCategory` · `ModuleSettings` 같은 **자기 테이블**에 쓴다 —
`dashboard_data`(V1)도 `dt2_*` 도 거치지 않는다. 그래서 옵션 추가·삭제·순서는 V1/V2 차이가 없다.

**문제는 이름을 바꿀 때다.** `DigitalTwinDashboardApp.jsx:2307~2416` 에서 부서 · 프로세스 ·
과제구분 이름이 바뀌면 **모든 과제의 이름 문자열을 치환**한다(`과제참여인력목록[].부서` ·
`담당부서목록[]` · `프로세스` · `과제구분`). 그런데 그 끝은 `saveProjects(updatedProjects)` —
`utils/dataStructure.js:306` 의 **IndexedDB 저장이라 서버로 안 간다.**

| | V1 | V2 |
|---|---|---|
| 치환 직후 | 로컬만 | 로컬만 (같음) |
| 그 뒤 아무 과제나 한 건 수정하면 | `upsertTracked({projects})` 가 **전체 배열**을 올려서 치환분이 **함께 반영됨** | `PATCH /projects/<uuid>` 가 **그 과제의 diff 만** 보내서 치환분이 **안 올라감** |

즉 V1 에서는 다음 저장에 **편승해서** 서버에 반영되던 것이 V2 에서는 영영 안 올라간다.
화면·IndexedDB 에는 새 이름이 보이므로 **새로고침 전까지 아무도 눈치채지 못한다.**

**재현 절차** — 설정에서 부서(또는 프로세스·과제구분) 이름 하나를 바꾼다 → 그 이름을 쓰던
과제 목록에 새 이름이 보이는지 확인 → **아무 과제나 한 건 열어서 다른 필드를 수정·저장** →
**F5 새로고침** → 그 과제의 부서명이 **옛 이름으로 돌아오면 재현된 것이다.**

✅ **2026-07-31 재현 확정** — 프로세스 이름 변경으로 실측. 설정 저장 직후 화면은 즉시 새 이름이
되고, 과제 한 건을 수정·저장한 뒤 F5 하면 **옛 이름으로 돌아온다.** V2 회귀가 맞다.

**필드를 제대로 골랐는지는 1단계에서 갈린다.** 설정 저장 직후 목록·간트가 **즉시 새 이름으로
바뀌면** 캐스케이드가 있는 필드다(부서·프로세스·과제구분). **화면이 그대로면 사업부를 고른
것이거나 그 값을 쓰는 과제가 없는 것이다** — 그 상태로는 2단계를 해도 아무것도 판정 못 한다.
관찰은 **프로세스·과제구분**이 쉽다(과제의 단일 최상위 필드라 목록에 바로 보인다).
부서는 `과제참여인력목록[].부서` 안에 중첩돼 있어 눈에 덜 띈다.

**F5 만으로는 판정이 안 된다.** 마운트 훅(`DigitalTwinDashboardApp.jsx:203~241`)이 진입할 때마다
`downloadServerData()` 로 서버 데이터를 받아 `saveProjects()` 로 **IndexedDB 를 덮어쓴다.**
그래서 이름변경 직후 그냥 F5 하면 V1·V2 어느 쪽이든 옛 이름으로 돌아온다.
가운데 **"과제 한 건 수정·저장"** 이 있어야 둘이 갈린다.

고치는 방향(재현되면 결정): ① 치환된 과제들을 `PATCH` 로 순차 전송(일괄추가·createdAt 백필과
같은 정책) 또는 ② 서버에 이름변경 일괄치환 엔드포인트를 두기. ①이 기존 정책과 일관된다.

### 🐞 사업부(division)는 이름변경 파급이 **아예 없다** — 별개의 기존 결함 (2026-07-31 실측)

`mx` → `mx2` 로 바꿔 확인했다. **컷오버 회귀가 아니다. V1 에서도 똑같았다.**

`DigitalTwinDashboardApp.jsx:2307~2347` 의 이름변경 감지는 **부서 · 프로세스 · 과제구분 셋뿐**이고
`divisionNameChanges` 라는 것은 **존재하지 않는다.** 그래서 사업부는 로컬 IndexedDB 조차 안 바뀐다
— V1 의 전체배열 upsert 에 편승할 것도 없었다는 뜻이라, 위 부서·프로세스 건과는 원인이 다르다.

관측된 증상 셋:

1. 설정만 `mx2` 가 되고 **과제 데이터는 전부 `mx` 로 남는다** (간트·목록에 `mx` 그대로)
2. 과제 편집창의 **사업부가 미선택으로 보인다** — `BasicInfoSection.jsx:518~528` 은 컨트롤드
   `<select value={formData.사업부}>` 인데 옵션 목록이 `mx2` 뿐이라 `mx` 가 어디에도 안 맞는다.
   **화면만 빈칸이고 state 는 `mx` 를 그대로 들고 있다.**
3. 그래서 그냥 저장하면 `사업부: 'mx'` 가 그대로 나가 **값이 날아가지는 않는다** (실측 일치)

⚠️ **진짜 위험은 3번이 아니라 사람이다.** 미선택을 본 담당자가 `mx2` 를 고르면 **그 과제만**
`mx2` 가 된다. 편집하는 과제마다 조금씩 옮겨가서 **데이터가 `mx`/`mx2` 로 쪼개진다.**
필터·집계·간트가 두 값을 다른 사업부로 세므로 조용히 숫자가 갈린다.

**개발 DB 가 지금 그 상태다** (설정 `mx2` / 과제 `mx`). 다음 작업 전에 설정에서 이름을 `mx` 로
되돌리거나, 과제쪽을 `mx2` 로 맞춰야 한다. 안 그러면 이후 리허설 결과가 오염된다.

고치는 방향: 사업부를 부서·프로세스·과제구분과 **같은 캐스케이드에 넣는다**(치환 대상은
`사업부` 필드). 그리고 위 V2 회귀와 **같은 문제를 공유하므로 서버 전송까지 한 번에 설계한다** —
따로 고치면 사업부만 로컬에서 바뀌고 서버엔 안 가는 상태가 된다.

### 🚨 사업부 이름을 바꾸면 **컷오버 후 그 사업부 manager 의 편집 권한이 끊긴다**

위 결함의 파생인데 성격이 다르다 — 표시 문제가 아니라 **권한 문제**다.

`permissions.py:196~221` 의 `resolve_division_id` 는 **활성 사업부 이름과 정확히 일치**할 때만
id 를 준다. 그런데 설정 저장은 옛 이름 행을 **비활성으로 남긴다**(같은 파일 208행 주석).
그래서 `mx` → `mx2` 로 바꾸면:

과제의 `division` 텍스트는 `mx` 인데 활성 사업부에 `mx` 가 없다 → `resolve_division_id` 가
**None** → `can_edit_project` 의 manager 분기가 **비교 자체를 건너뛴다**(211행) →
**그 사업부 manager 가 자기 사업부 과제를 못 고친다.** (소유자·참여인력·admin·dt_office 는 됨)

**지금은 안 드러난다.** 컷오버 공지 3번대로 과제 수정 권한 검사가 **사실상 무검사**라서다.
컷오버 직후에 드러난다 — `소유자 없는 활성 과제 정리`(2절)와 **같은 종류의 블로커**다.

서버는 이미 대비돼 있다. `routes_v2.py:1757~1759` 가 **모든 쓰기 경로가 지나는 한 곳**에서
`division` 이 patch 에 있으면 `division_id` 를 다시 풀어준다. 즉 **프론트가 `사업부` 를 PATCH 로
보내주기만 하면 권한도 같이 복구된다.** 위 캐스케이드 수정이 이것까지 해결한다.

### 고치는 방법은 ① 로 정한다 (프론트 N × PATCH) — 근거 확인 완료

| 확인한 것 | 결과 |
|---|---|
| 네 필드가 PATCH 가능한가 | ✅ `division`·`process`·`category`·`members_json`/`depts_json` 전부 **CORE** (`permissions.py:57~83`) |
| 이력이 폭증하지 않는가 | ✅ **0건 증가.** `record_project_history` 는 진척 지표(status·progress·기간·건수)만 해싱하고 값이 같으면 행을 안 쓴다 (`history.py:40~82`) |
| `division_id` 를 따로 보내야 하나 | ✅ 불필요. 서버가 자동으로 다시 푼다 (`routes_v2.py:1757`) |
| 기존 정책과 맞는가 | ✅ 일괄추가·createdAt 백필과 **같은 순차 PATCH 정책** |

②(서버 일괄치환 엔드포인트)는 채택하지 않는다 — 컷오버 직전에 새 API 표면을 늘리게 되고,
위 네 가지가 다 통과해서 ① 로 충분하다.

⚠️ 구현 시 주의: 전역 rename 은 **바뀐 과제 전부에 CORE PATCH** 를 날린다. 즉 admin·dt_office
가 아니면 자기 권한 밖 과제에서 403 이 난다. **부분 실패를 조용히 넘기지 말 것** — 몇 건 성공/
몇 건 실패인지 사람에게 보여줘야 한다(안 그러면 일부만 바뀐 채로 갈라진다).

**설계 결정 3가지**

1. **V1 은 일부러 no-op 이다.** `saveSettingsRename` 은 V1 에서 아무것도 안 보내고
   `{skipped:true}` 만 돌려준다. 컷오버 직전에 **운영(V1) 경로의 동작을 바꾸지 않으려는 것**이다.
   V1 은 예전처럼 다음 저장의 전체배열 upsert 에 편승한다. 플래그 false 로 반입해도 운영 동작은
   오늘과 완전히 같다.
2. **`bulkSaveV2` 를 그대로 재사용했다** — 일괄추가·createdAt 백필과 같은 함수다. 전체 과제를
   넘기면 **before 와 달라진 것만** 골라 순차 PATCH 하고, 정책(순차 · 첫 실패에서 중단 ·
   되돌리지 않음 · 어디서 멈췄는지 에러에 담기)도 그대로 따라온다. 새로 만든 규칙이 없다.
3. **성공 문구를 서버 전송 뒤로 옮겼다.** 전에는 로컬 저장 직후 바로 "업데이트되었습니다" 가
   떴다 — 서버에 안 갔는데도 성공으로 보였다는 뜻이고, 그게 이 결함이 오래 안 보인 이유다.

⚠️ **실패 안내 문구에 "다시 저장" 이라고 쓰면 안 된다.** 설정은 이미 새 이름으로 저장돼 있어서
다시 저장해도 옛 이름/새 이름 비교에 걸리는 게 없어 **캐스케이드가 아예 안 돈다.**
**이름을 되돌렸다가 다시 바꾸는 것**이 유일하게 통하는 복구 방법이고, 코드에 그렇게 안내해 뒀다.

## ⚠️ 2-5. 첫 컷오버 시도에서 실제로 터진 것 (2026-07-31)

**증상** — 컷오버 후 **전체 과제 수는 같은데 완료 과제 수가 줄었다.** 구버전으로 되돌리면
다시 올라갔다.

**원인** — `v2_sync` 는 **백그라운드 스레드**다(`v2_sync._worker`). 누가 저장한 직후 서비스를
내리면 **마지막 동기화가 안 끝난 채 끊긴다.** 그 상태로 컷오버하면 `v2_sync` 가 멈추므로
**dt2 는 영영 따라잡지 못한다.** `dt2_compare_api.py` 대조 결과도 최근 변경분에만 몰려 있었다
(과제 값 불일치 62 · V2 누락 12 / 성과 값 불일치 3(`updatedAt` 2 · `설명` 1) ·
V2 누락 2(`디지털트윈기여도`)).

**조치** — 컷오버를 중단하고 구버전으로 복귀(R-1, 무손실 — 사용자를 안 들였다).
구버전에서는 `v2_sync` 가 다시 살아나므로 **아무 저장이나 한 번 일어나면 전체가 재이관된다**
(`_sync_once` 는 V1 페이로드 **전체**로 `import_*` 를 부른다). 별도 스크립트 불필요.

**원인이 하나 더 있었다** — 재이관(`--commit`)만으로는 `dt2_verify` 의 **과제-성과 연결이
`[FAIL]`** 이었다. `V2 에만 있음 2건`.

🐞 **`dt2_import.py` 에는 `DELETE` 가 한 줄도 없다 — upsert 만 한다.**
그래서 **V1 에서 끊은 성과 연결이 dt2 에 그대로 남는다.** `v2_sync` 도 같은 코드라 마찬가지다.
2026-07-29 Phase 2 때는 `--truncate` 로 비우고 새로 만들어서 유령 행이 0 이었고, 그 뒤 누가
연결 2개를 끊으면서 어긋난 것이다. (첨부·선행과제도 같은 구조라 원리상 같은 일이 생긴다)

**→ `--commit --truncate` 로 비우고 다시 이관하니 전항 `[OK]`.**
(`고아 참조 3 · 중복 참조 1` 은 V1 데이터 자체의 특성이라 그대로 남는다 — 2026-07-29 에도
같은 값이었고 그때도 `[OK]` 였다)

✅ **이 결함은 컷오버로 사라진다.** 문제의 경로가 "V1 에서 삭제 → dt2 에 미반영" 인데,
컷오버 후에는 V1 에서 삭제가 일어나지 않고 연결 삭제는 `PUT …/performances`(**통째 교체**)가
정확히 반영한다. **한 번만 깨끗이 맞추면 다시 안 생긴다.**

**재발 방지** — 런북 **4-0 단계**: 서비스를 멈춘 직후 `dt2_import.py --commit --truncate` +
`dt2_verify.py` 전항 `[OK]` 확인을 **필수**로 넣었다. (`--truncate-history` 는 절대 금지)

> 이 검사는 **컷오버 전에만** 가능하다. 컷오버 후에는 V1 이 멈춰서 비교 대상이 못 된다.

**✅ 전부 해소 확인** — `--commit --truncate` 재이관 후:
· `dt2_verify.py` **전항 `[OK]`**
· `dt2_compare_api.py --detail` **V2 응답 = V1 응답** (화면 읽기를 옮겨도 된다는 판정)
· 화면의 **완료 과제 수가 컷오버 전과 일치**

`디지털트윈기여도` 2건 누락은 **매핑 문제가 아니라 동기화 지연이었다** — 재이관으로 사라졌다.

**이 두 도구는 여기까지가 마지막 유효 시점이다.** 사용자가 저장을 시작하면 V1 은 멈춘 채
V2 만 움직여 두 쪽이 정당하게 갈라진다. 그 뒤로는 판정 근거가 되지 못한다.

⚠️ **개발 DB 의 `dashboard_data`(V1 싱글톤)는 2026-07-31 에 재구성된 줄이다.** 검증 중에 원본을
지웠고(`/dt-v2/data/download` 가 내부에서 commit 하는 바람에 delete 가 함께 확정됐다),

**그래서 개발에서 `dt2_compare_api.py` 를 돌리면 무조건 일치한다 — V1 쪽이 dt2 에서 나왔기
때문이다. 판정 도구로 쓰면 안 된다.** 운영 DB 는 손대지 않았으므로 운영 대조는 유효하다.

배포 순서는 지금까지와 같다: 폴더 통째 압축 → 운영에 풀기 → `backend` 에서 `flask db upgrade`
→ 기동. **`.env` 도 같이 따라간다.**

**`.env` 를 되돌릴 필요는 없다** — 이 프로젝트는 **개발과 운영의 DB 이름·계정을 일부러
맞춰 뒀다.** 운영에서 손대는 것은 **`FLASK_ENV=production` 한 줄뿐**이다
(`run.py:13` 이 이 값으로 설정 클래스를 고른다 — `development` 로 두면 디버그·SQL 에코가
켜지고 **시험용 쓰기 우회 헤더까지 열린다**).

되돌려 넣어야 하는 것은 **`backend\templates` 와 `backend\uploads` 둘뿐**이다.
압축본의 것으로 덮이면 운영 파일이 사라진다.

그래서 preflight 의 `개발 기본 DSN 이 아니다` 는 **이 환경에서 항상 `[FAIL]` 이다** — DSN 을
일부러 맞춰 뒀기 때문이다. secret key 2건과 함께 **예상된 실패 3건**이고, 런북 6장에
그렇게 적어 뒀다.

## 5. 헷갈리기 쉬운 것

**스위치가 셋인데 서로 다른 곳에 있다.**

| 스위치 | 어디 | 바꾸려면 |
|---|---|---|
| `DT2_WRITE_ENABLED` | 서버 `.env` | 재기동 |
| `DEFAULT_V2_READ/WRITE` | 프론트 **소스** | `npm run build` 다시 |
| `dtV2Read/dtV2Write` | 브라우저 localStorage | URL 에 `?dtV2Read=1` |

**`DT2_WRITE_ENABLED` 를 켜면 `v2_sync` 가 스스로 멈춘다** — 둘이 동시에 켜지는 일은 없다.

**읽는 모양은 컷오버로 바뀌지 않는다.** `assemble.py` 가 dt2 테이블을 V1 응답 모양 그대로
다시 조립하므로 프론트는 손댈 게 없다. 화면을 V2 모양으로 옮기는 건 그 다음 이야기다.
