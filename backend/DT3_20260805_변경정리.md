## 1. 이날 나온 문제는 두 종류였다

흩어져 보이지만 실은 **같은 실수가 반복된 것**이다. 다음에 비슷한 것을 만들 때
이 두 가지를 먼저 의심하면 된다.

### ① "사본이 정본과 갈린다" — 세 번 나왔다

화면은 저장할 때마다 정본에서 사본을 다시 만드는데, **서버에는 그 규칙이 없었다.**
그래서 화면을 안 거친 쓰기(MCP·API·시드·이관)로 들어온 것은 갈라져 있었다.

| 사본 | 정본 | 갈라져 있던 정도 |
|---|---|---|
| 성과 `단위`·`달성형여부` | 소분류 | 112건 중 **35건(31%)** |
| `담당자`·`과제참여인력` | 과제참여인력목록 | 110건 중 **105건이 비어 있었다** |
| `담당부서` | 담당부서목록 | 100건 중 **44건**(첫 부서만 남음) |
| (이전) `관리자` | 과제PL | 226건 중 207건 빈 값 |

**더 나쁜 것은 화면에서 고칠 수도 없다는 점이다.** 화면은 사본 칸을 읽기 전용으로
잠그고 저장된 값을 그대로 보여준다 — 틀린 채로 굳는다.

→ **입력을 막는 것만으로는 부족하다. 서버가 파생시켜야 한다.**

### ② "같은 일에 권한 기준이 두 곳" — 두 번 나왔다

기준이 둘이면 **반드시 느슨한 쪽으로 샌다.**

| 무엇 | 엄격한 쪽 | 느슨한 쪽(구멍) |
|---|---|---|
| 과제 영구삭제 | 전용 라우트 = admin·dt_office | `patch_project` = **아무 편집자나** |
| 소유자 지정 | 생성 = admin만 | **수정 = 검사 없음** |

둘 다 실측으로 확인했다 — 일반 사용자(role=user)가 자기 과제를 영구삭제했고,
소유권도 남에게 넘겼다.

```
1) 반출 전 — 지금 얼마나 어긋나 있는지 센다 (읽기만, 안전)
     python scripts\dt3_backfill_derived.py

2) 반입 — 폴더 통째 압축. 백엔드·프론트를 **반드시 함께**
     (구 프론트 + 신 백엔드는 저장이 400 이다)
     .env 도 같이 가므로 압축 전에 값 확인

3) flask db upgrade                     ← 이번엔 **필요하다** (8c4d2b02a4a2)

4) 백엔드·프론트 재시작

5) MCP 서버 재시작                       ← 도구 설명이 파일에서 읽힌다.
                                          안 하면 AI 가 옛 규칙으로 답한다

6) 반출 후 — 이미 어긋나 있던 것을 한 번에 정리
     python scripts\dt3_backfill_derived.py --commit
```

⚠️ **6번을 건너뛰면** 몇 달 뒤 **아무 상관없는 이유로** 그 행을 저장하는 순간 값이
바뀐다. 저장한 사람은 자기가 안 건드린 값이 바뀐 것을 보게 된다. 한 번에 알고
맞추는 편이 낫다.

## 4. 데이터도 바꿨다 (개발서버)

코드와 달리 **데이터는 반출로 안 넘어간다.** 운영에서는 다시 판단해야 한다.

| 무엇 | 개발에서 한 것 |
|---|---|
| 소분류 단위 통일 | `억`→`억원`(6행) · `day`→`hrs`(1행) |
| 2026 성과 재생성 | 100 → **112건**(비용절감 12건 신설). 시간은 `hrs`, 금액은 `억원` |
| 성과 30건 지표 재작성 | 절대오차(도·dB) → **오차율(%)**, 감소율(%) → **절대시간(hrs)** |
| 파생 사본 백필 | 담당자 107건 · 담당부서 56건 · 성과 단위 30건 |
| 잔여 연결 정리 | 삭제된 성과를 가리키던 218건 |
| 시험 잔여물 정리 | 과제 12건 (08-01·08-02 것 10건 포함) |

> `예측 정확도` 소분류에 온도(도)·음향(dB)이 섞이는 문제는 **운영은 다르게 운영되어
> 해당 없음**으로 정리했다(2026-08-05 확인).

## 7. 다음 사람에게

이날 얻은 판단 기준 셋. 비슷한 것을 만들 때 그대로 쓰면 된다.

**① 어떤 값이 다른 값의 사본이면, 막지 말고 파생시켜라.**
입력을 막는 것(`immutable`)만으로는 부족하다 — 정본이 바뀔 때 사본이 **따라와야**
하기 때문이다. 다만 **정본이 저장될 때만** 만들어라. "항상 맞춘다" 로 했더니 저장할
때마다 그 필드가 바뀌어서 변경 이력이 오염되고, 서로 다른 필드를 고친 두 사람이
자동 병합 대신 **409** 로 부딪혔다.

**② 금지(403)는 마지막 수단이다.**
`AI_FORBIDDEN_FIELDS` 는 이제 비어 있다. 셋이 있었는데 —
권한이 문제면 **권한 검사**로, 사본이면 **파생**으로 풀렸다.
금지가 맞는 경우는 **값의 모양 자체가 확인을 불가능하게 만들 때**뿐이다
(예: 이름만 담겨서 어느 홍길동인지 못 가린다).

**③ 서버가 값을 손댔으면 반드시 알려라.**
`normalized`·`ignored`·`alsoPending`·`cascaded` 가 전부 그 장치다.
조용히 고치면 부르는 쪽은 **자기가 보낸 그대로 저장된 줄 안다.**
"변경된 값이 없습니다" 만 주는 것도 같은 잘못이다 — **왜** 안 바뀌었는지 말해야 한다.
